# REST API — «Слово.Проповеди»

Внешний контракт REST API приложения. **Подробный список эндпоинтов, типов и Zod-схем — в сгенерированном клиенте** `src/shared/api/generated/` (Orval из OpenAPI v0.15.1, заголовок спецификации «API — Слово.Проповеди»); этот документ не дублирует его, а фиксирует **настройку фронта** и **карту реального использования** эндпоинтов. См. также [storage.md](./storage.md) (токены) и [local-db.md](./local-db.md) (временный источник данных для раздела книг).

## Base URL

- По умолчанию: `https://api.slovo-propovedi.ru` — константа `DEFAULT_API_URL` в `src/shared/config/config.ts`.
- `axiosInstance` создаётся с этим base URL в `src/shared/api/axiosInstance.ts` (`axios.create({ baseURL: DEFAULT_API_URL })`).
- **Можно менять в Настройках**: атом `serverUrlAtom` (`src/entities/settings/model.ts`). Экшены `setServerUrlAction` / `initServerUrlAction` синхронизируют `axiosInstance.defaults.baseURL` с выбранным URL и персистят его в AsyncStorage (ключ `SERVER_URL`, см. [storage.md](./storage.md)).

## Аутентификация — Bearer JWT

Реализация — `src/shared/api/axiosInstance.ts`:

- **Request-interceptor** читает access-токен из AsyncStorage (`ACCESS_TOKEN_KEY`) и добавляет заголовок `Authorization: Bearer <accessToken>`; для запросов `POST /auth/refresh` заголовок не добавляется (refresh аутентифицируется токеном из тела).
- **Response-interceptor**:
  - при успешном ответе отмечает сервер доступным (`reportServerReachable(ctx)`, см. `src/shared/model/network`);
  - при сетевой ошибке (сервер не ответил) отмечает недоступным (`reportServerUnreachable(ctx)`);
  - при `401` (кроме самого запроса refresh — guard `isRefreshRequest`, чтобы refresh-запрос не запускал повторный refresh) помечает запрос `_retry` и вызывает `performTokenRefresh()`: отправляет `POST /auth/refresh` **напрямую** через тот же `axiosInstance` (`axiosInstance.post(REFRESH_ENDPOINT, { refreshToken })`) — запрос проходит через оба интерцептора, guard `isRefreshRequest` пропускает его без `Authorization` и без повторного refresh при 401; сохраняет новую пару токенов через `tokenStorage.setTokens`, повторяет оригинальный запрос с новым access-токеном;
  - при неудачном refresh очищает токены (`AsyncStorage.multiRemove([ACCESS_TOKEN_KEY, REFRESH_TOKEN_KEY])`) и отклоняет запрос. TODO: переход на экран логина не реализован (см. комментарий в `axiosInstance.ts`).

> ✅ **Инвариант:** `axiosInstance.ts` не имеет runtime-импортов из `./generated/**` — только type-only (стираются при сборке). Раньше файл импортировал `getAuth` из `generated/auth/auth` ради `authControllerRefresh`, что создавало require cycle (`axiosInstance ⇄ generated/auth/auth`: generated импортирует `customInstance` отсюда через mutator Orval). Теперь refresh вызывается напрямую: константа `REFRESH_ENDPOINT = '/auth/refresh'` в `axiosInstance.ts` — единственный источник правды об эндпоинте и используется и в guard'ах интерцепторов, и в самом запросе. Обратное ребро (`generated/*` → `customInstance` → `axiosInstance`) сохраняется — это гарантирует, что первый импорт любого generated-модуля регистрирует интерцепторы.

## Хранилище токенов — `tokenStorage`

`src/shared/api/axiosInstance.ts`, объект `tokenStorage`:

- `setTokens(accessToken, refreshToken)` — сохраняет обе пары в AsyncStorage (`@access_token`, `@refresh_token`).
- `getAccessToken()` — возвращает access-токен.
- `clearTokens()` — удаляет обе пары (`multiRemove`).

Ключи: `@access_token` (`ACCESS_TOKEN_KEY`), `@refresh_token` (`REFRESH_TOKEN_KEY`). Подробно — [storage.md](./storage.md).

## Генерация клиента (Orval)

- **Команда:** `yarn api:generate`.
- **Источник:** OpenAPI-спецификация v0.15.1 — **удалённый URL** `https://docs.slovo-propovedi.ru/openAPI.yaml` (задан в `orval.config.ts`). Спецификация ведётся вне этого репозитория; в проекте лежит только результат генерации.
- **Сгенерировано:** `src/shared/api/generated/` — **не редактировать вручную** (все файлы помечены «Generated by orval, Do not edit manually»).
- **Реэкспорт наружу:** `src/shared/api/index.ts` (`export * from './generated'`).
- **Типы:** все TS-интерфейсы — в `src/shared/api/generated/api.schemas.ts`, реэкспортированы как `APITypes`. Основные: `SermonEntity`, `PlaylistEntity`, `SectionEntity`, `UserResponse`, `AllUsersResponse`, `StreamUrlResponse`, `SermonDistinctValuesResponse`, `AllSectionsResponse`, `AllSermonsResponse`, `AllPlaylistsResponse`, `AllFilesResponse` и DTO (`Create*Dto`, `Update*Dto`, `Reorder*Dto`). За актуальными полями обращайся к файлу напрямую.
- **Zod-схемы (runtime-валидация):** в `src/shared/api/generated/model/` (по модулям). Доменные Zod-схемы приложения — в `src/shared/model/domain/common.ts` (`sectionSchema`, `sermonSchema`, `playlistSchema`), см. [storage.md](./storage.md).

### Структура `src/shared/api/generated/`

```
generated/
├── index.ts                 # Агрегатор: authApi, filesApi, playlistsApi, sectionsApi, sermonsApi, usersApi, *Mocks, APITypes
├── api.schemas.ts           # Все TS-интерфейсы (APITypes)
├── auth/auth.ts             # getAuth() → signIn/refresh/logout/getProfile
├── basic/basic.ts           # getBasic() → healthControllerCheck
├── files/files.ts           # getFiles() → upload, list, stream-url, file url
├── playlists/playlists.ts   # getPlaylists() → CRUD + reorder sermons
├── sections/sections.ts     # getSections() → CRUD раздела + reorder разделов и плейлистов
├── sermons/sermons.ts       # getSermons() → CRUD + stream-url + distinct-values
├── users/users.ts           # getUsers() → CRUD пользователей + change-password
└── model/                   # Zod-схемы для runtime-валидации (по модулям)
```

Каждый модуль экспортирует фабрику (`getAuth()`, `getSermons()` и т.д.), возвращающую функции-обёртки над `customInstance` из `src/shared/api/axiosInstance.ts`. `customInstance` пробрасывает конфиг в `axiosInstance` и возвращает `response.data`. Для каждого модуля также генерируется `*.faker.ts` — фабрики мок-данных (см. «MSW-моки»).

> ⚠️ Фабрика `getBasic` (health) **не реэкспортируется** из `generated/index.ts` — недостижима из `shared/api`. Reorder-функции (`reorderSections`, `reorderPlaylistsInSection`) в отличие от прежней версии клиента живут **внутри модуля sections** (`getSections`) и через `sectionsApi` достижимы, но в рантайме не вызываются.

## Главы и стихи: диапазоны и списки

С версии спецификации 0.15.1 поля `chapter` и `verse` в `SermonEntity` и `PlaylistSermon` расширены с одиночного числа до «диапазонов» (примеры — в `src/shared/api/generated/api.schemas.ts`):

- `chapter: number | number[] | null` — массив из двух чисел трактуется как **диапазон глав** (например `[3, 4]` = главы 3–4).
- `verse: number | number[] | (number | number[])[] | null` — по комментарию в спецификации: массив из двух целых чисел — **диапазон от–до** (`[9, 18]`); массив, содержащий кортежи или смесь целых и кортежей, — **список разрозненных отрезков** (`[[9, 18], 20]` = отрезок 9–18 и стих 20; `[16, [18, 20], 22]` = стихи 16, 18–20, 22).

**Влияние на фронт (в ходе этой же миграции обновляется):**

- **Доменная модель** `src/shared/model/domain/common.ts` — `sermonSchema` расширяется под новые union-формы `chapter`/`verse`, чтобы валидировать данные и с сервера, и из кэша. Старые значения (одиночное число / `null`) остаются валидными подмножеством новых форм.
- **Форматтеры ссылок на Писание** — `formatSermonReference` (`src/shared/lib/format/formatSermonReference.ts`) и `formatScripture` (`src/features/sermon-search/lib/formatScripture.ts`) расширяются: диапазон `[a, b]` выводится как «a-b», список отрезков — через запятую. Используются в подписях плейлиста, мини/полноэкранного плеера и в строках результатов поиска.
- **Кэши** (per-query кэш поиска `cachedSermonSearch:<query>`, кэш секций `CACHED_SECTIONS`, плейлисты в параметрах маршрута) хранят `SermonData` с этими полями — расширенная схема валидации принимает и старые, и новые формы.
- **DTO на запись** (`CreateSermonDto`/`UpdateSermonDto`) — `chapter`/`verse` стали опциональными.
