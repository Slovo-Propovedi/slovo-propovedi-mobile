# Архитектура: почему так

Этот документ объясняет **мотивацию и историю** архитектурных решений. Машино-проверяемые правила (границы FSD, порядок импортов, отсутствие точек с запятой, лимит 130 строк) уже настроены в ESLint и steiger (`check:fsd`) — здесь они не дублируются, а обосновываются. За деталями правил обращайся к [`AGENTS.md`](../AGENTS.md).

## Почему FSD (Feature-Sliced Design)

Архитектура строится на **слоях** с однонаправленными импортами (сверху вниз):

```
app/           → точка входа, реэкспорт экранов (только expo-router)
pages/         → экраны, композиция UI
widgets/       → составные UI-блоки (плавающий плеер, таб-бар, баннеры)
features/      → пользовательские взаимодействия и бизнес-логика
entities/      → доменные модели и сущности (player, settings)
shared/        → переиспользуемые утилиты, UI-компоненты, типы
```

**Мотивация.** Каждый слой отвечает только за свою зону ответственности. Это даёт:

- предсказуемую навигацию по коду — по имени слоя сразу понятно место файла;
- контроль зависимостей: `shared` не может импортировать `features`, `entities` не зависит от `widgets`. Это проверяется steiger и импорт-правилами ESLint;
- переиспользование: общая логика выносится вниз, ближе к `shared`, и не дублируется в экранах.

Пример следования правилам: логика плеера живёт в `src/entities/player/`, а не в экранах. Экраны (`src/pages/listen/`) лишь читают состояние через hooks из `entities/player`, ничего не зная о внутренней реализации.

**Импорт в коде.** Внутри кода используются абсолютные импорты по слоям (`entities/player`, `shared/ui/theme`), относительные импорты запрещены между слоями. Это разворачивает физическую структуру в логическую и защищает границы слоёв. Порядок импортов (external → internal FSD → типы → относительные) проверяется плагином perfectionist.

**Публичный API слайса.** Каждый слайс экспортирует наружу только публичный контракт через **один** barrel-файл `index.ts` в корне слайса (например, `src/entities/player/index.ts`). Сегментных barrel-файлов (`ui/index.ts`, `lib/index.ts`) нет, а внутренние детали (helper-функции, внутренние атомы) наружу не экспортируются. См. [`AGENTS.md`](../AGENTS.md) → «Barrel Export Rules».

**Импорты внутри слайса — только относительные.** Файлы одного слайса импортируют друг друга через относительные пути (`./lib/usePlayer`, `../model`), а **не** через собственный barrel (`'entities/player'`). Причина: относительный путь сразу показывает, из какой части модуля берётся зависимость и насколько она «глубокая» — это делает контекст явным при чтении кода и защищает от циклических импортов через barrel. Абсолютные импорты по слоям (`'entities/player'`, `'shared/ui/theme'`) используются только при обращении к **чужим** слайсам.

### @x cross-import (кросс-слойные импорты между слоями одного уровня)

Правило FSD: между слоями одного уровня (например, `entities/player` ↔ `entities/listening-history`) прямой импорт через barrel запрещён — это нарушает направленность зависимостей. Для таких случаев используется паттерн **@x**: в корне слайса создаётся папка `@x/` с файлами, названными по имени потребителя.

```
src/entities/listening-history/
├── @x/
│   └── player.ts       # узкий API только для entities/player
├── index.ts            # полный публичный API (для pages, widgets и т.д.)
└── ...
```

Файл `@x/player.ts` реэкспортирует только те символы из слайса-поставщика, которые нужны конкретному потребителю (`entities/player`). Потребитель импортирует по пути `'entities/listening-history/@x/player'`, а не `'entities/listening-history'`.

**Мотивация:**

- **Узость контракта** — потребитель видит только то, что ему нужно, не весь публичный API;
- **Защита от случайного использования** — невозможно импортировать внутренний символ, которого нет в `@x`;
- **Явная зависимость** — путь `@x/player` сразу говорит, для кого создан этот экспорт;
- **Изоляция изменений** — расширение полного barrel (`index.ts`) не ломает кросс-слойных импортов, если `@x` не изменён.

**Не путать с barrel-файлами:** `@x/` — это НЕ сегментные barrel-файлы (которые запрещены). Barrel в корне слайса (`index.ts`) един и служит внешним потребителям. `@x/` — это дополнительные, узкие точки входа, создаваемые по мере необходимости при кросс-слойных связях.

### Babel module-resolver

Абсолютные импорты по слоям разворачивает `babel-plugin-module-resolver` в [`babel.config.js`](../babel.config.js): алиасы `entities`/`features`/`pages`/`shared`/`widgets` → `src/*`. Важно: Metro применяет babel-конфиг проекта **ко всем файлам, включая node_modules**, поэтому в конфиге передан кастомный `resolvePath`, который пропускает переписывание для файлов внутри node_modules. Без этого guard'а bare-импорт npm-пакета с совпадающим именем (например, пакет `entities` из цепочки react-native-svg → css-select → domutils → dom-serializer) переписывался бы в `src/entities` и ломал сборку.

## Почему «один компонент / хук / функция — отдельный файл»

Внутри слайса файлы дробятся по принципу «одна сущность — один файл»: один React-компонент, один хук или одна функция живут в отдельном файле (например, `usePlayer.ts`, `useSeekControls.ts`, `PlayerProgressBar.tsx`). Причины:

- **явный контекст при импорте** — путь к файлу однозначно говорит, что в нём лежит (`./lib/useSeekControls` → хук управления перемоткой);
- **меньше merge-конфликтов** — разные авторы реже правят один и тот же файл;
- **простой поиск** — по имени файла можно найти реализацию, не открывая весь модуль;
- **чёткая ответственность** — файл нельзя «обрасти» побочной логикой, если в нём по правилу лежит только одна сущность.

Допускаются исключения: тесно связанные мелкие хелперы можно группировать в один файл (например, `nativePlayerHelpers.ts`), если они используются только вместе. Главное — чтобы имя файла честно отражало его содержимое.

## Почему Expo Router (файловая навигация)

Навигация объявлена файловой структурой папки `app/`, а не конфигом в коде. Это:

- **один источник истины** для маршрутов — путь роута совпадает с путём файла;
- типизация маршрутов и простое глубокое линкование (`router.push` с `pathname` и `params`).

### Разделение ответственности `app/` ↔ `src/pages/`

- `app/` — **только** реэкспорты и layout'ы expo-router. Файлы в `app/` тонкие, например `app/(tabs)/listen/index.tsx` = `export default ListenScreen` из `pages/listen`.
- `src/pages/` — реальная логика экранов.

Такой разрыв нужен, чтобы код экранов оставался тестируемым и независимым от expo-router. Именно поэтому `export default` разрешён только в `app/`, а в `src/` — только именованные экспорты.

### Фактическая структура `app/`

```
app/
├── _layout.tsx          # корневой провайдер: reatomContext + ThemeProvider + ErrorBoundary
├── _RootLayout.tsx      # корневой Stack, баннеры сети/обновлений, hardware back
├── index.tsx            # Redirect → /listen
├── settings.tsx         # реэкспорт pages/settings
├── about.tsx            # реэкспорт pages/about
└── (tabs)/
    ├── _layout.tsx      # таб-бар + плавающий плеер (ExpandablePlayer)
    ├── listen/          # стек таба «Слушать»: index, playlist, playlist-list
    ├── read.tsx         # реэкспорт pages/read (таб заблокирован)
    ├── study.tsx        # реэкспорт pages/study (заглушка)
    └── more.tsx         # реэкспорт pages/more
```

> ⚠️ В `AGENTS.md` показана вложенная папка `app/read/` с `book-reader.tsx`/`books-list.tsx`. **Фактически** таких маршрутов нет — есть только `read.tsx` (одиночный таб). Экраны `pages/book-reader` и `pages/books-list` существуют, но маршруты для них не зарегистрированы. Это долг — см. [`debt.md`](./debt.md).

## Почему Reatom (а не Zustand/Redux)

Для состояния выбран **Reatom** (`@reatom/core`, `@reatom/framework`, `@reatom/npm-react`). Причины:

- **Атомы** — минимальная единица состояния, легко читаются и переиспользуются. Пример: `src/entities/player/model.ts` (`isPlayingAtom`, `positionAtom`, `durationAtom`).
- **Экшены** — асинхронные операции с явным `ctx` (контекстом транзакции). Эффекты (запись в AsyncStorage, сброс атома через `ctx.schedule`) оформлены прямо в экшене, что делает данные детерминированными.
- Единый контекст `ctx` из `src/shared/lib/reatom-ctx/ctx.ts` прокидывается через `<reatomContext.Provider value={ctx}>` в `app/_layout.tsx`. Это позволяет использовать Reatom вне React-дерева — например, в `PlayerService` (`src/entities/player/lib/PlayerService/index.native.ts`) и в axios-интерцепторах (`src/shared/api/axiosInstance.ts`).
- Zustand и Redux Toolkit отклонены — см. [`decisions.md`](./decisions.md).

### Одно событие — одна точка изменения

Правило: изменение, затрагивающее один смысл, вносится в **одном месте** модели. Например, все атомы и экшены плеера — только в `src/entities/player/model.ts`, скачивание — в `src/entities/player/lib/download-model.ts`, состояние сети — в `src/shared/model/network.ts`. Нельзя раскидывать атомы одного домена по нескольким файлам. Это упрощает поиск и рефакторинг.

## Почему платформенные реализации `.native.ts` / `.web.ts`

Приложение собирается на iOS, Android и Web. Часть возможностей (expo-audio, экран блокировки) есть только на нативных платформах, на Web — только `HTMLAudioElement`. Для таких модулей используется суффиксный паттерн Metro/Webpack:

```
src/entities/player/lib/PlayerService/
├── index.ts        # TS-фолбэк: export { playerService } from './index.native'
├── index.native.ts # реализация на expo-audio (PlayerService)
└── index.web.ts    # реализация на HTMLAudioElement (WebPlayerService)
```

Общий `index.ts` резолвится бандлером в нужную платформенную реализацию автоматически. Наружу слайс экспортирует один и тот же контракт (`playerService`), поэтому потребители (`src/entities/player/lib/usePlayer.ts`) не знают о платформе.
