# Навигация (Expo Router)

**Стек:** `expo-router`, настройка — `app/`
**Статус:** готов (таб «Читать» заблокирован)

## Точка входа

`app/index.tsx` — `<Redirect href='/listen' />`. Первый экран приложения — таб «Слушать».

## Корневой стек

`app/_RootLayout.tsx` (`_RootLayout`) — содержит `Stack`:

- `index` и `(tabs)` — без шапки (`headerShown: false`);
- `settings` — заголовок «Настройки»;
- `about` — заголовок «О приложении»;
- `history` — заголовок «История прослушивания», вход из вкладки «Ещё» (`router.push('/history')`);
- `offline` — заголовок «Офлайн», вход из вкладки «Ещё» (`router.push('/offline')`);
- `share` — заголовок «Поделиться приложением» (см. [`../screens/share.md`](../screens/share.md)).
- цвет фона контента и шапки — из `currentTheme`; `headerTitleAlign: 'center'` в `screenOptions` — заголовок центрирован в шапке, а не прижат к кастомной кнопке «Назад» (см. ниже).

Список пяти под-экранов (`settings`/`history`/`offline`/`about`/`share`) — константа `SUB_SCREENS` в `src/shared/routing/rootStackScreens.ts` (вынесена из `_RootLayout.tsx`, чтобы файл уложился в лимит 130 строк ESLint).

**Кнопка «Назад» в шапке (`headerLeft`)** — кастомный `HeaderBackButton` (`src/widgets/sub-screen-header-back/ui/HeaderBackButton.tsx`) вместо стандартной кнопки react-navigation, используется в двух местах:

- пять под-экранов корневого стека (`settings`/`history`/`offline`/`about`/`share`, `_RootLayout.tsx`) — фолбэк `/more` (экран «Ещё», логический родитель всех пяти);
- стек «Слушать» (`playlist`/`playlist-list`/`my-playlists`, `app/(tabs)/listen/_layout.tsx`) — фолбэк `/listen`.

Только иконка (`Ionicons 'chevron-back'`), без текста «Назад» рядом — раньше в стеке «Слушать» использовалась нативная кнопка с `headerBackTitle: 'Назад'` (текст виден только на iOS), теперь оба стека выглядят одинаково. Контейнер 48×48 (без `hitSlop`) даёт полноразмерную область нажатия и frame для скринридеров без изменения размера иконки (24); `marginLeft: -8` сохраняет визуальное положение шеврона.

- Проп `fallbackRoute` (по умолчанию `'/more'`) задаёт, куда уходить, если истории нет — каждый стек передаёт свой через `headerLeft: props => <HeaderBackButton tintColor={props.tintColor} fallbackRoute='...' />`.
- По нажатию: если `router.canGoBack()` — `router.back()`; иначе — `router.replace(fallbackRoute)`.
- **Почему не стандартная кнопка:** на web после **полной перезагрузки страницы** (например, `F5` на `/settings`) история навигации react-navigation пуста — экран становится «корневым» в стеке, и `router.canGoBack()` возвращает `false`, поэтому системная кнопка «Назад» вообще не рендерится (react-navigation её не показывает, когда идти некуда) — пользователь не может вернуться в приложение. Кастомная кнопка рендерится всегда и в этом случае уводит на `fallbackRoute`.
- **Ограничение:** фолбэк всегда ведёт на корень стека, а не восстанавливает реальный стек навигации (например, `/listen/playlist` после релоада уйдёт на `/listen`, а не на предыдущий экран, если он был глубже). Приемлемо для текущих под-экранов; подробнее — [`debt.md`](../debt.md) → Navigation.

Глобальные элементы поверх стека: `NetworkBanner`, `ServerErrorToast`, `UpdateDialogRoot` (все — внутри `_RootLayout`).

**Аппаратная кнопка «Назад» (Android)** — обработчик `BackHandler.addEventListener('hardwareBackPress', ...)` с каскадом:

1. открыт оверлей «Подробнее» (`showDetailsAtom`) → закрыть;
2. открыто меню плеера (`showMenuAtom`) → закрыть;
3. открыты настройки звука (`showSoundSettingsAtom`) → закрыть;
4. открыта плейлист-шторка (`showPlaylistAtom`) → закрыть;
5. развёрнут плеер (`isPlayerExpandedAtom`) → `closePlayerSheetAction`;
6. есть история (`router.canGoBack()`) → `router.back()`;
7. иначе — ничего (возврат `false`).

Отдельного шага для поиска нет: «Назад» на `/search` уходит по истории на предыдущий таб, а хук `useClearSearchOnLeave` (`src/pages/search/lib/useClearSearchOnLeave.ts`) в момент смены активного маршрута сбрасывает сессию (запрос, фокус, ввод) — см. [`../screens/search.md`](../screens/search.md).

В `_RootLayout.tsx` также: подписка `subscribeToNetwork()` (модульный вызов), `checkForUpdateAction` через `setTimeout(0)` в `useEffect` (вместо `InteractionManager.runAfterInteractions`), персист позиции каждые 5с, `useUpdateNotificationResponse()`.

Провайдеры — `app/_layout.tsx`: `reatomContext.Provider` (единый `ctx`), `ThemeProvider`, `GestureHandlerRootView`, `ErrorBoundary` + `GlobalErrorHandler`. Здесь же модульные `initializePlayer()` и `initServerUrlAction(ctx)`.

### Патч expo-router: guard для `onUnhandledLinking` (удалён в SDK 58)

`patches/expo-router+57.0.28.patch` **удалён** при миграции на SDK 58: в expo-router 58.0.24 символ `onUnhandledLinking` полностью убран из сборки, поэтому и источника DEV-warning'а «Can't perform a React state update on a component that hasn't mounted yet» больше нет. В SDK 57 патч правил `build/fork/useLinking.native.js`, где `.then()` `getInitialState()` до монтирования `NavigationContainer` дёргал `onUnhandledLinking` (= `setLastUnhandledLink`, setState); патч откладывал вызов через `setTimeout(..., 0)` и пропускал его через guard `isMountedRef`. К коду приложения отношения не имел — Reatom-атомы не трогают навигационное состояние. Отдельно от этого живёт workaround cold-start гонки 150 мс — `useColdStartLinkRecovery` остаётся (см. [`../debt.md`](../debt.md) → Navigation).

## Табы

`app/(tabs)/_layout.tsx` — `Tabs` с кастомной панелью:

- 3 таба-раздела: `listen` «Слушать», `read` «Читать», `more` «Ещё» (`title` в `_layout.tsx`). Маршрут `search` зарегистрирован в таб-навигаторе (у него собственный вложенный стек) и рендерится баром как полноценный слот-вкладка: в развёрнутом компактном острове он занимает долю наравне с табами, в широкой раскладке — иконка-лупа в слоте шириной 48 (табы там текстовые), в свёрнутой компактной строке — отдельный круг поиска. Пока `/search` в фокусе, капсула активной вкладки уезжает на поиск, а слот табов отдаёт фолбэк «Слушать» (`useActiveTabRouteKey`) и рендерится неактивным без капсулы; тап по табу возвращает на раздел и закрывает поиск (см. «Кастомный таб-бар»).
- `tabBar` → `CustomTabBar` (`src/widgets/tab-bar/ui/CustomTabBar.tsx`) + `ExpandablePlayer` рендерятся поверх на всех табах. Нижний поисковый виджет — одна движущаяся кнопка поиска (`TabBarSearchButton`; при свёртывании отрывается от острова в закрытый круг, видна только в свёрнутой строке; в развёрнутой поиск живёт слотом внутри острова табов) — рендерится **внутри `CustomTabBar`** в компактной раскладке (`SearchIslandMorph` в баре больше не рендерится: виджет остался поверхностью поля-пилюли, см. [../screens/search.md](../screens/search.md)), а в широкой его заменяет `TabIslandSearchSlot` внутри острова табов. `CustomTabBar` есть на каждом таб-экране, поэтому поиск доступен везде. Слой `SearchGate` удалён: страница выдачи — это маршрут `search`; нижняя пилюля больше не привязана к нему (`isSearchOpenAtom` не пишется), а `useClearSearchOnLeave` сбрасывает сессию при уходе и фокусирует поле страницы при входе. Плеер (`zIndex: 20`) рендерится в том же фрагменте `tabBar` следом за баром и накрывает всё, в фокусе нижнего поля (мёртвый режим) опускаясь до 9 — под бар и пилюлю поиска (web-стекинг: каждый RNW-`View` сам является stacking context, поэтому плеер обязан жить в одном контексте с баром).
- Маршрут `search` — вложенный стек `Stack`: `index` (страница поиска) без шапки, `playlist` и `preacher` — реэкспорты страниц деталей с нативной шапкой стека поиска (кнопка «Назад» с фолбэком `/search`; у `playlist` шапка прозрачная, заголовок и правый хром задаёт страница); навигация из выдачи пушит `/search/playlist`, `/search/preacher` внутри маршрута, поэтому «Назад» возвращает выдачу нетронутой, а уход с активного маршрута `search` (а не blur внутри него) сбрасывает сессию поиска.
- **ВАЖНО:** таб «Читать» гейтится фича-флагом `read` — при выключенном/незагруженном флаге `CustomTabBar` показывает глобальный информационный диалог через `showInfo` («Скоро будет доступно», `useTabPress` → `shared/model/info-dialog`) и не навигирует (`isDisabled={!isTabAvailable(route.name)}`). `ReadScreen` дополнительно проверяет флаг через `useFeatureFlag` и при `false` рендерит `null` (см. [feature-flags.md](./feature-flags.md)).
- **Переключение таба применяется в коммите нажатия.** `CustomTabBar` не навигирует очередным `navigateToTab` навигатора: тот ставит действие в очередь expo-router и применяет его в эффекте («Queues an action to be dispatched after the current React commit»), из-за чего контент менялся лишним навигационным коммитом — на нативе это десятки миллисекунд (новый экран показывался «с задержкой»), на web незаметно. `getInstantTabNavigation` (`src/widgets/tab-bar/lib/getInstantTabNavigation.ts`) шлёт тот же `NAVIGATE` через `dispatchSync` дескриптора сфокусированного маршрута, и экран меняется в одном коммите с тапом; если дескриптора нет — фолбэк на очередной `navigateToTab`. `lazy` в этой версии expo-router на монтирование табов не влияет (все экраны смонтированы, `BottomTabView` рендерит все маршруты), Suspense-фолбэк при переключении не показывается.

## Стек раздела «Слушать»

`app/(tabs)/listen/_layout.tsx` — `Stack` внутри таба:

- `index` — без шапки (`headerShown: false`);
- `my-playlists` — шапка **динамическая**: в обычном режиме прозрачная (`headerTransparent: true`, `title: ''`, большой заголовок «Мои плейлисты» рисует сам список) с `headerRight` (карандаш «Изменить порядок»); в режиме редактирования снова непрозрачная (`headerStyle.backgroundColor = currentTheme.background`), заголовок «Мои плейлисты» и `headerRight` (галочка «Сохранить»). Опции собирает `useMyPlaylistsHeader` (см. [../screens/my-playlists.md](../screens/my-playlists.md));
- `playlist-list` — прозрачная шапка (`headerTransparent: true`, `title: ''`);
- `playlist` — прозрачная шапка;
- `preacher` — нативная шапка, заголовок задаётся именем проповедника из параметров (`useHeaderTitle`); вход — тап по проповеднику в выдаче поиска (в стеке «Слушать»); из выдачи поиска пушится `/search/preacher` внутри маршрута `search`;
- `playlist-edit` — нативная шапка с заголовком «Редактировать плейлист» (экран редактирования локального плейлиста, см. [../screens/playlist-edit.md](../screens/playlist-edit.md)).

Экраны реэкспортируются из `src/pages/` (`app/(tabs)/listen/index.tsx` → `ListenScreen`, `my-playlists.tsx` → `MyPlaylistsScreen`, `playlist.tsx` → `PlaylistScreen`, `playlist-edit.tsx` → `PlaylistEditScreen`, `playlist-list.tsx` → `PlaylistListScreen`, `preacher.tsx` → `PreacherScreen`).

## Передача параметров

Параметры передаются **строками** через `router.push({ pathname, params })` (не JSON — полный объект экран резолвит сам):

- `/listen/playlist?playlist=<UUID>` — `navigateToPlaylist` передаёт только `playlist.id`, полный `PlaylistData` экран достаёт через `usePlaylistById` (секции → кэш → API, см. [../screens/playlist.md](../screens/playlist.md));
- `/listen/playlist-edit?playlist=<UUID>` — карандаш в шапке экрана плейлиста (`PlaylistHeaderActions`) передаёт `playlist.id`; экран редактирования берёт плейлист из `myPlaylistsAtom` (см. [../screens/playlist-edit.md](../screens/playlist-edit.md));
- `/listen/playlist-list?sectionId=<строка>` — `navigateToPlaylistList` (параметр `title` в URL не передаётся, заголовок берётся из резолвнутого раздела);
- `/listen/preacher?artist=<имя>` — `useSearchNavigation` (`src/pages/search/lib/useSearchNavigation.ts`) передаёт только имя проповедника; экран парсит его (trim, непустое, ≤ 200 символов) и сам грузит проповеди (см. [../screens/preacher.md](../screens/preacher.md));
- `/listen/my-playlists` — `navigateToMyPlaylists` (без параметров) — экран редактирования порядка локальных плейлистов.

Хелперы навигации:

- `useListenNavigation.ts` (`src/pages/listen/lib/`) — `navigateToPlaylist`, `navigateToPlaylistList`, `navigateToMyPlaylists`;
- `useSearchNavigation.ts` (`src/pages/search/lib/`) — `navigateToPlaylist`, `navigateToPreacher` (пушат `/search/playlist`, `/search/preacher` внутри маршрута `search`, поверх живой сессии выдачи);
- `useReadNavigation.ts` (`src/pages/read/lib/`) — `navigateToBookReader` (`/read/book-reader`), `navigateToBooksList` (`/read/books-list`);
- `src/shared/routing/` — `useColdStartLinkRecovery.ts` (Android-only safety net холодного старта, см. «Android App Links» ниже), `launchPath.ts` (pure-хелперы разбора launch URL: `extractLaunchPath`, `shouldAttemptRecovery`), `rootStackScreens.ts` (`SUB_SCREENS` корневого стека), `useHeaderTitle.ts`.

## Android App Links

Хост `https://app.slovo-propovedi.ru` заявлен через App Links: точные пути `/listen` и `/listen/playlist` открывают приложение (холодный старт или поверх запущенного — работает «из коробки» через expo-router, без кастомной linking-конфигурации), остальные маршруты остаются в браузере. Подробности (конфиг, assetlinks.json, nginx, adb-тесты, ограничения) — [deep-links.md](./deep-links.md).

Дополнительно приложение подстраховывает **холодный старт на Android**: expo-router может потерять launch-ссылку в гонке 150 мс и оставить приложение на `/listen` — хук `useColdStartLinkRecovery` (`src/shared/routing/`, вызов из `_RootLayout.tsx`) через ~1 с повторно читает launch intent и восстанавливает переход; корректно обработанные ссылки, ручная навигация и iOS не затрагиваются. Подробности — [deep-links.md](./deep-links.md) → «Android: гонка 150 мс при холодном старте».

## Зона администратора `/admin`

Отдельный маршрут вне публичных табов (объявлен в корневом стеке как `admin` с `headerShown: false`):

- `app/admin/_layout.tsx` — `Stack` зоны: при монтировании однократно вызывает `restoreSession` (`entities/auth`) и показывает `ActivityIndicator`, пока сессия не разрешена (`idle`, а на защищённых маршрутах также `loading`); редиректит неаутентифицированных на `/admin/login` (кроме самого login). Аутентифицированного пользователя на `/admin/login` в `/admin` не уводит — после успешного входа возвращаемся на «Ещё». Шапка есть только у `login` (`HeaderBackButton`, фолбэк `/settings`).
- `app/admin/login.tsx` → `AdminLoginScreen` (`pages/admin-login`).
- `app/admin/(tabs)/_layout.tsx` — `Tabs` с `headerShown: false` и тем же `CustomTabBar`, что и публичные табы: `index` (Главная), `sections`, `playlists`, `sermons`. Списочные экраны `media`, `flags` и `users` в таб-группе больше не живут: это стековые экраны `app/admin/{media,flags,users}.tsx`, зарегистрированные в `app/admin/_layout.tsx` так же, как «Источники импорта» (`app/admin/invidious.tsx`) — нативная шапка с заголовком и кнопкой «Назад» (фолбэк `/admin`). Открываются только строками блока «Дополнительно» на «Главной».
- Файлы табов: `index.tsx` (admin-home), `sections.tsx` / `playlists.tsx` / `sermons.tsx` — экраны слайсов `pages/admin-sections` / `admin-playlists` / `admin-sermons`; стековые списки — `pages/admin-media` / `admin-flags` / `admin-users`. Отдельного таба «Загрузить» нет: проповедь создаётся через `/admin/sermons/create` из шапки списка проповедей и быстрых действий главной.

Вход в зону — из шапки «Настроек» (кебаб-меню `SettingsHeaderMenu` через `headerRight` в `app/_RootLayout.tsx`) и с экрана «Ещё» (компактная иконка-кнопка «В админ панель» → `AdminPanelButton`). В `SettingsHeaderMenu` используется хук `useAdminEntry` (`entities/auth`): при `idle` восстанавливает сессию (`restoreSession`), затем пушит `/admin` (есть права) или `/admin/login`; для аутентифицированных единственный пункт меню — «Выйти из аккаунта админа» (`signOut`). На экране «Ещё» `AdminPanelButton` рендерится только для аутентифицированных `admin`/`moderator` (проверка `canAccessAdmin`; `MoreScreen` при монтировании вызывает `restoreSession`, если статус `idle`) и пушит `/admin`. После успешного входа на `/admin/login` показывается тост «Вход выполнен» и выполняется `router.replace('/more')`.

## Кастомный таб-бар

`CustomTabBar` (`src/widgets/tab-bar/ui/CustomTabBar.tsx`) — плавающая нижняя строка в стиле Apple Music: остров табов с `BlurView` и — в компактной раскладке — одна движущаяся кнопка поиска (`TabBarSearchButton`), которая отрывается от острова в отдельный круг справа, когда строка сворачивается, и приклеивается обратно при развороте (прямоугольник интерполируется между слотом в острове и кругом по оси формы острова, см. «Свёртывание» ниже). Морф круга в поле выведен из эксплуатации: поле ввода теперь живёт на странице поиска (`SearchPageField`), а кнопка больше не раскрывается (круг — только в свёрнутой строке; `SearchIslandMorph` в баре не рендерится; см. [../screens/search.md](../screens/search.md)); в широкой раскладке отдельного круга нет — поиск встроен в остров табов (см. «Широкая раскладка» ниже). Остров ограничен `maxWidth: CONTENT_COLUMN_WIDTH` (600 px из `shared/ui/layout`): в компактной раскладке на планшетах и десктоп-web строка остаётся центрированной колонкой, на телефонах колонка шире экрана и ширина не меняется. В широкой раскладке остров не тянется на колонку, а ужимается по контенту (≈332 pt: три текстовых таба по 88 + иконка-поиск 48 + внутренние отступы 10×2), и ряд островов не применяет боковые инсеты — остров просто центрируется. Боковой инсет строки морфит вместе с состоянием «одна линия»: worklet `getBarSideInset(oneLineProgress)` клампит прогресс в 0..1 и интерполирует между `BAR_SIDE_INSET_EXPANDED` (= `SLIDER_REST_INSET + 1` — на пиксель правее линии покоя карточек слайдеров, `SLIDER_PEEK` + `INDENTS.middle` = 24, плюс 1, чтобы край островов не совпадал с краем карточки; развёрнутый бар с отцепленной пилюлей мини-плеера, широкий остров табов, открытое поле поиска) и `BAR_SIDE_INSET_COLLAPSED` (×1.5 = 36; пилюля сложена в однострочный ряд) за те же `BAR_MORPH_DURATION_MS` (200). Прогресс публикует модульный `oneLineBarMorphDriver` (`src/widgets/tab-bar/model/oneLineBarMorphDriver.ts`, фабрика `createAtomMorphDriver`) от `isOneLineBarAtom` (= `isBarCollapsedAtom && !isSearchFieldVisibleAtom`, `src/widgets/tab-bar/model/barMorph.ts`); паддинг строки анимирует `useRowInsetStyle` через longhand-свойства `paddingLeft`/`paddingRight` (shortform `paddingHorizontal` Reanimated на web не анимирует), а рестинг-слой отдаёт settled-инсет, чтобы морф не красил целевую геометрию на кадр раньше. Поэтому контент строки (остров табов, в свёрнутой строке — плюс зазор и круг поиска) начинается от `getColumnSideInset(screenWidth, 0, CONTENT_COLUMN_WIDTH) + getBarSideInset(...)` и занимает `min(экран, CONTENT_COLUMN_WIDTH) − 2 × getBarSideInset(...)`; на эти же края опирается развёрнутая пилюля мини-плеера (см. [player.md](./player.md)), поэтому её левый/правый край совпадают с краями острова и круга поиска на любой ширине.

**Широкая раскладка (≥ 768 pt по длинной стороне и ≥ 600 pt по короткой).** Хук `useIsWideLayout()` включает широкую раскладку только для окна планшетного класса: `min(width, height) >= WIDE_LAYOUT_MIN_SHORTEST_SIDE` (600) И `max(width, height) >= WIDE_LAYOUT_MIN_WIDTH` (768). Поэтому iPad mini в портрете (744×1136) и десктопное окно (1280×800) — широкие, а телефон в альбомной ориентации (844×390) и узкое окно web (900×500) остаются компактными. В широкой раскладке плавающий хром закрепляется сверху: `floatingContainer` получает `top = insets.top + BAR_TOP_ISLAND_MARGIN` (8) вместо `bottom: 0`, подъём над клавиатурой не применяется, а морф принудительно развёрнут — `useTabIslandMorph({ isForceExpanded: isWide })` и `useRowInsetStyle(isWide)` читают прогресс 0 на обеих осях, поэтому скролл-свёртывание не сжимает остров. Высота ряда и `tabBarHeightAtom` не меняются, но геометрия мини-плеера читает их только в компактной раскладке — в обеих позах (откреплённая пилюля и однострочный ряд). В широкой раскладке `getMiniPlayerGeometry` `tabBarHeight` игнорирует: нижняя линия пилюли — это `wideBottomInset` из `useBarBottomPadding()` (та же величина, что у нижнего отступа ряда), а верхний отступ экранов считается от контентной высоты ряда (`WIDE_BAR_ROW_HEIGHT` = ужатый остров 48 + тот же 8-й запас над кромкой, что у компактного ряда = 56), не от измеренной `tabBarHeight`. В этой раскладке `CustomTabBar` рендерит `TabIslandSearchSlot` — трейлинг-слот с одной иконкой-лупой (без подписи, `accessibilityLabel` «Поиск», та же цель онбординга `listen.search-toggle`; при фокусе поиска слот несёт капсулу активной вкладки) фиксированной ширины 48, а табы становятся текстовыми: иконка скрыта, подпись — 16 pt (`WIDE_TAB_SLOT_WIDTH` 88, `WIDE_SEARCH_SLOT_WIDTH` = минимальный тач-таргет 48, `WIDE_TAB_LABEL_SIZE` = `FONT_SIZES.md`). Поэтому остров ужимается по контенту до ≈332 pt и центрируется, а не занимает всю колонку, и верх читается одним стеклянным островом `[табы][поиск]`. `SearchIslandMorph` в широкой раскладке не рендерится. В компактной раскладке тот же слот встроен в остров табов: в развёрнутой строке остров занимает всю колонку и тоже читается одним островом, а отдельный круг (`TabBarSearchButton`) отрывается от острова только при сворачивании бара (в том числе на `/search`). Заголовочные строки экранов в широкой раскладке не рендерятся вовсе (не спейсер): `ListenScreen`, `MoreScreen` и `ReadScreen` просто опускают `ListenTopRow`/`ScreenTitleRow`, а их действия (щит админки, «?», «Обновить») переезжают в фиксированный оверлей `WideTopActions` — правый верхний угол на вертикальной середине острова (`WIDE_ACTIONS_TOP` = 16, высота 48, `right: INDENTS.low`), поверх скролла и с прозрачной для тапов пустой областью. Переход между раскладками анимирован: `useChromeLayoutShift` за `CHROME_LAYOUT_SHIFT_DURATION_MS` (400) поднимает таб-бар из нижнего якоря в верхний и опускает мини-пилюлю вниз; прогресс засевается в покое текущей раскладки, поэтому первый маунт не анимируется, а обратный переход играет ту же анимацию в обратную сторону. В широкой раскладке внизу остаётся один мини-плеер. Вне пары порогов (телефоны — в том числе в альбомной ориентации — и узкие окна web) поведение компактной раскладки остаётся прежним.

Экраны резервируют место под плавающий хром через `useScreenChromePadding()` (`src/shared/ui/layout/lib/useScreenChromePadding.ts`): в компактной раскладке `topChromeHeight = 0`, `topChromeScrollInset = 0`, `bottomChromeHeight = tabBarHeight + PLAYER_SIZES.miniPlayerHeight` (прежняя ручная формула), а в широкой `topChromeHeight = insets.top + BAR_TOP_ISLAND_MARGIN + WIDE_BAR_ROW_HEIGHT + BAR_OUTER_GAP` (остров табов сверху; берётся именно контентная высота ужатого широкого ряда `WIDE_BAR_ROW_HEIGHT` (56: остров 48 + 8-й запас), а не измеренная `tabBarHeight`, потому что измерение включает нижний safe-area-паддинг ряда и завышало бы верхний отступ на его величину), `topChromeScrollInset = BAR_TOP_ISLAND_MARGIN + WIDE_BAR_ROW_HEIGHT + BAR_OUTER_GAP + WIDE_CONTENT_TOP_GAP` (8 + 56 + 8 + 24 = 96; первый элемент стоит с дополнительным зазором 24 под полосой хрома) и `bottomChromeHeight = PLAYER_SIZES.wideMiniPlayerHeight (64) + barBottomPadding + BAR_OUTER_GAP`, где `barBottomPadding` — тот же `useBarBottomPadding()`, что задаёт нижний отступ ряда островов (реальная safe-area-линия на нативе, 21 на iOS web, `max(inset, 25)` на остальном web, пол 12 до первого инсета); отдельного `isWeb`-переключателя для широкой пилюли больше нет. **Верхний остров плавает над контентом, как нижние:** системная safe-area остаётся layout-паддингом корня экрана (`paddingTop: insets.top`), а клиренс острова (`topChromeScrollInset`) уходит в `contentContainerStyle` скролла. Тогда первый элемент стоит ниже острова в покое, но при прокрутке уезжает под стекло, а не обрезается непрозрачной полосой на всю ширину; полоса при этом не перехватывает тапы и драг — верхняя область принадлежит скроллу. Так сделано в `ListenScreen`, `MoreScreen`, `AdminHomeScreen`, `AdminSectionsScreen`, `AdminSermonsScreen`, `AdminPlaylistsScreen`, а также в `PlaylistTrackList` и `MyPlaylistsDragList` (там `topChromeHeight` уже лежит в `contentContainerStyle`, а корень без верхнего паддинга). Экраны с **фиксированной** верхней шапкой (`SearchTabScreen`/`SearchScreen`: заголовок, табы области и поле поиска не скроллятся) держат `topChromeHeight` в layout-паддинге корня — иначе остров накрыл бы шапку. Хук читают `ListenScreen`, `SearchTabScreen`, `SearchResultsList`, `RecentSearchesSection`, `MoreScreen`, экраны админки и списки `OfflineScreen`, `HistoryScreen`, `PlaylistTrackList`, `MyPlaylistsDragList`, `PreacherSermonsList`, `PlaylistList`. Экраны с **прозрачной** нативной шапкой (`PlaylistTrackList` — `/listen/playlist`, `/search/playlist`; `MyPlaylistsDragList` — режим редактирования «Мои плейлисты») дополнительно кладут `topChromeHeight` в верхний контентный отступ, иначе плавающий остров накрыл бы шапку; в компактной раскладке это 0. У `PlaylistList` верхний отступ (`headerHeight + TITLE_TOP_GAP`) уже больше острова, поэтому он ничего не меняет. Экраны с **непрозрачной** нативной шапкой (`preacher` в обоих стеках, `playlist-edit`) пока остаются перекрытыми — это записано в [debt.md](../debt.md) → «Navigation».

Фон острова и круга поиска — общий стеклянный рецепт `src/shared/ui/glass/` (`GlassSurface` + `createGlassStyles`), тот же, что у пилюли мини-плеера и пилюли поиска: полупрозрачная заливка, блюр и 1px светлая рамка; значения и платформенные оговорки — в [theme.md](./theme.md#стеклянные-нижние-острова-frosted-glass). Теней у нижних островов нет вовсе: глубину читает сама полупрозрачная заливка стекла и 1px рамка (см. [theme.md](./theme.md#стеклянные-нижние-острова-frosted-glass)). Градиентная подложка `BarBackdropShade` под нижним хромом удалена. На Android `elevation: 12` у поднятого слоя, а не у контейнера табов: в компактной раскладке — у ряда островов (остров табов + отдельный круг поиска), в широкой — у самого острова, поэтому ряд остаётся плоским и стекло рисуется только в границах пилюли (фидбек 2026-11-27: верхний таб-бар читался как непрозрачная подложка на всю ширину). На Android 12+ острова размывают реальный контент страницы: `BlurTargetProvider` над навигатором (`app/(tabs)/_layout.tsx` и `app/admin/(tabs)/_layout.tsx`) публикует target активного маршрута, а корень каждого экрана с видимой нижней строкой обёрнут в `BlurBackdrop` — табы (включая `/search`), вложенные маршруты стеков «Слушать» и `search` и табы админки; таб-бар при этом остаётся сиблингом target — потомком одной из страниц он не становится, поэтому blur не захватывает сам себя. Все поверхности нижнего хрома — остров, пилюля поиска и мини-пилюля — берут backdrop через `usePageBlurTarget`: это target страницы текущего маршрута (страница поиска публикует свой target с непрозрачным фоном темы), один и тот же в любом состоянии. Отдельного target'а у подложки больше нет — `ShadeBlurTarget`, ключ `BOTTOM_CHROME_SHADE_KEY` и `getChromeBlurTarget` удалены: хром, размывавший собственный градиент, получал плоский серый тон и на странице поиска выглядел иначе (светлее в тёмной теме, темнее в светлой), чем на остальных экранах. Во время морфов (остров табов, пилюля поиска и мини-плеер) живой блюр продолжается на всех платформах, включая Android 12+ с реальным target: статичного фолбэка больше нет, эталон — web, где стекло всегда живое (сплошная заливка фоном на морфе читалась как белая/чёрная плита; подробности и условие возможного возврата полупрозрачного фолбэка — [theme.md](./theme.md#стеклянные-нижние-острова-frosted-glass) и [debt.md](../debt.md)).

Высота острова живёт на оси D — `oneLineBarMorphDriver` от `isOneLineBarAtom`: 60 (`TAB_BAR_ISLAND_HEIGHT_EXPANDED`) в развёрнутом баре, 48 (`TAB_BAR_ISLAND_HEIGHT`) в однострочном ряду (видимое нижнее поле — мёртвый режим и в приложении не встречается) (свёрнутая высота — не самостоятельная константа, а производная от `PLAYER_SIZES.miniPlayerHeight`: свёрнутый ряд однострочный и единой высоты). Форму и ширину двигает только ось A — `tabIslandMorphDriver` от `isTabIslandCollapsedAtom` (= `isBarCollapsedAtom || isSearchFieldVisibleAtom`, 0 = развёрнут, 1 = свёрнут): ширина интерполируется от ширины развёрнутого острова к **текущей** высоте (`interpolateSize` в `getIslandStyle`), а диаметр свёрнутого круга — это и есть текущая высота: 60×60 рядом с открытым полем, 48×48 в компактном ряду. Оси независимы (A не трогает высоту, D не трогает форму), но идут одной длительностью `BAR_MORPH_DURATION_MS`; `useTabIslandMorph` подписан на обе, слоты (`TabSlot`) берут из оси D и диаметр (ширину), и высоту — слот всегда высотой с остров; resting-двойник острова тоже двойной — высота от settled-оси D (`settledOneLine`), форма от settled-оси A (`settledCollapsed`). Круг поиска всегда остаётся идеально круглым (ширина = высота = `radius * 2`). Правило сетки: компактные 48 существуют только в однострочном ряду со скрытым полем — любое состояние с видимым полем ведёт всю строку на 60. Строка островов при этом сохраняет фиксированную высоту `BAR_ROW_MIN_HEIGHT` (68 — острову 60 остаётся 8 над кромкой, компактному 48 — 20 запаса над рядом), поэтому измеряемая высота таб-бара не скачет между состояниями. В широкой раскладке остров по форме принудительно развёрнут, но высоту читает из собственной константы `WIDE_TAB_ISLAND_HEIGHT` (48): верхний таб-бар ужатее компактного развёрнутого (60) и ниже мини-пилюли (64), слоты и таб-элементы получают ту же высоту через флаг `isWideLayout` (`getTabSlotStyle`/`getTabItemStyle`), а ряд островов — константную `WIDE_BAR_ROW_HEIGHT` (56), которая не участвует в морфе, поэтому измеряемая высота широкого таб-бара стабильна.

Активный таб подсвечен **одной переезжающей капсулой**: `TabIslandContent` рендерит единственный `TravelingCapsule` (фон `withAlpha(currentTheme.primary, 0.18)`, скругление `RADIUSES.round`, `pointerEvents: none`), а не по капсуле в каждом слоте — per-slot капсулы удалены. Геометрию и полёт ведёт `capsuleTravelDriver` (`widgets/tab-bar/model/capsuleTravelDriver.ts`): перелёт стартует **синхронно на тапе**, ещё до ре-рендера навигатора (`useTabPress` → `onTabTravel` → `requestTravel` из `useCapsuleTravelRequest`), а эффект маршрута лишь сверяет ту же цель и не откатывает уже идущий полёт (`isRunningFlag` + совпавший `targetCenter`). Капсула скользит от старого центра к новому (база 100 мс + 50 мс за каждый пересечённый слот, потолок 220 мс) с быстрым стартом: `easeOutQuad` срывает подсветку с нажатого таба сразу и замедляет её к цели. «Жидко» раздувая контент каждого промежуточного слота: подпись **и иконка** перекрашиваются из `currentTheme.text` в `currentTheme.primary` по перекрытию капсулы со слотом из одного `colorStyle` (`useSlotHighlightStyles` + `interpolateColor`; иконка рисуется глиф-текстом через `AnimatedText`, чтобы читать ту же анимированную стиль-функцию, а не флипаться на коммите маршрута), а контент слота и сама капсула подрастают на 4 % при пересечении; заблокированные слоты (`isDisabled`, напр. «Читать») остаются `currentTheme.textMuted` с затемнением `styles.disabledTabButton` (`opacity: 0.5`). На прилёте капсула перелетает цель на 10 % собственной ширины (овершут 60 мс) и возвращается (70 мс), добавляя слоту ещё 8 % масштаба (`getTravelScale`). Хаптики расписаны по дистанции, а не по финалу: битов ровно `slotDistance` (один — соседний слот), они делят время перелёта поровну, граница t=0 (точка тапа) молчит, промежуточные биты дают мягчайший тик (`hapticHighlightPass`: iOS `selectionAsync`, Android `Context_Click`, на web молча), последний — Light-хаптик как у обычного тапа (`hapticLanding`: iOS `impactAsync(Light)`, Android одиночный `Virtual_Key`, без `AndroidHaptics.Confirm`; на web молча; гейт — `hapticsEnabledAtom`). Овершут и возврат — только хореография, а финальный `settle` хаптика не даёт: он лишь фиксирует settled-состояние React. Смена таба идёт без press-хаптика (`hapticDisabled`), единственный отклик — биты перелёта. В свёрнутом круге капсула гаснет вместе с островом (`opacity: 1 − progress`), а активный таб сохраняет статическую подсветку — primary-иконку; круг поиска при фокусе `/search` несёт собственную статическую капсулу (`ActiveTabCapsule` в `TabBarSearchButton`); в развёрнутом широком острове капсула так же переезжает на слот поиска при фокусе `/search`. Внутренние отступы повторяют эталонные кадры (`getIslandContentPadding`, `ISLAND_CONTENT_PADDING_HORIZONTAL = 10`, `TAB_ITEM_GAP = 8`): контент острова отступает от скруглённых краёв, между табами есть зазор 8, а капсула шире своего слота на `CAPSULE_SLOT_BLEED = 12` (по 6 с каждой стороны) — так подпись не прилипает к её краям. Те же 6dp задают капсуле горизонтальный инсет, но по вертикали он тоньше — 4dp (`CAPSULE_VERTICAL_INSET`, `top`/`bottom`), поэтому подсветка не заполняет остров по высоте и чуть отступает от его верхней и нижней кромок. В компактном развёрнутом острове ширина слота — `(ширина острова − 2 × padding) / число табов` (в широком — постоянные 88 у табов и 48 у поиска). Горизонтальный padding острова анимируется тем же `progress` и в свёрнутом круге становится 0, иначе активный слот шириной с текущий диаметр круга не поместился бы в него и иконка уехала бы из центра; `getTabSlotStyle` держит `minWidth = MIN_TOUCH_TARGET` (48) с затуханием к 0 вместе со скрытыми слотами (в свёрнутом круге слот и есть тач-таргет размером с текущий диаметр — 60×60 рядом с открытым полем, 48×48 в компактном ряду, — а контент таб-элемента — `getTabItemHeight` от оси D: 52 (60 − 2 × 4) в развёрнутом баре и в круге при открытом поле, 40 (48 − 2 × 4) в компактном ряду при иконке 28). Вертикальная геометрия острова (высота слота и таб-элемента) следует оси D, поэтому в круге при открытом поле (ось A схлопнута, ось D развёрнута) иконка центрирована, а горизонтальные отступы элемента по-прежнему читают ось формы A. Свёрнутый остров делает неактивные слоты неинтерактивными (`pointerEvents='none'` на `TabSlot`, `isCollapsed` из `useTabIslandMorph`): нулевая ширина слота не мешает его дочерним pressable-элементам вылезать за край острова, и без этого гейта невидимая кнопка «Ещё» перехватывала тапы по правой половине круга активного таба. Тап по кругу целиком принадлежит активному слоту. Отступы самого таб-элемента тоже анимируются: `getTabItemHorizontalMargin` гасит горизонтальный полу-зазор до 0 в свёрнутом круге (иначе остаточные 4dp сдвигали иконку вправо), а `getTabItemVerticalMargin` держит одинаковые компактные 4dp в обоих состояниях, поэтому таб-элемент заполняет ужатый остров (Issue #153). Сами анимированные стили собирают `getIslandContentStyle`/`getTabItemStyle` (`src/widgets/tab-bar/lib/getBarMorphStyles.ts`) и используют только longhand-свойства (`paddingLeft`/`marginTop`, а не `paddingHorizontal`/`marginVertical`): Reanimated обновляет web-стили через `createReactDOMStyle` из react-native-web, минуя `preprocess`, поэтому shortform в анимированном стиле залипает на значении первого рендера (8dp padding и 4dp margin оставались в свёрнутом круге — иконка прилипала к правому краю), тогда как `width`/`height`/`opacity` продолжали анимироваться.

Свёртывание (см. `isBarCollapsedAtom`, драйвер `useBarCollapseOnScroll`): остров плавно (200 мс, `BAR_MORPH_DURATION_MS`) сжимается из полной ширины строки в круг, диаметр которого равен текущей высоте острова, оставляя только активный таб — иконку без подписи. **Кнопка поиска в том же кадре отрывается от острова** (`TabBarSearchButton` + `useSearchSeparation`/`getSearchButtonGeometry`): один и тот же элемент интерполирует свой прямоугольник между слотом внутри острова (`left` — внутренний край колонки + боковой инсет + паддинг контента + доли табов) и закрытым кругом у правого внутреннего края ряда; `left`/`width`/`height` ведёт одна ось — форма острова (`progress`), поэтому второго клока нет и кнопка видна всю дорогу, а не проявляется из ниоткуда. Своё стекло кнопки (`glassStyle`) проявляется ровно на величину separation и так же гаснет при развороте: кнопка **приклеивается обратно** в слот, а слот в острове (`TabIslandSearchSlot` с `isDetached`) держит только ширину как распорку. Капсула активного поиска едет на том же элементе (`capsuleStyle`). **Высоту острова и таб-элемента задаёт только анимированный стиль** (`getIslandStyle`, `getTabItemHeight`): статический `height` в том же массиве стилей перекрывает анимированный на устройстве (остров залипал на компактных 48 и не дорастал до 60 — ниже круга поиска), а `flex: 1` на таб-элементе обнуляет flex-basis и сжимает иконку с подписью до контентной высоты. Поэтому в `styles.ts` у `floatingIsland`/`tabItem` нет ни статической высоты, ни `flex`. Клип контента острова живёт на внутренней обёртке `islandContent` (`overflow: hidden` + `borderRadius: round`), а не на host `floatingIsland` (у него `overflow` нет вовсе — стекло клипает себя само в `GlassSurface`, та же структура, что у поискового круга): на iPad Safari host-клип с `border-radius` не обрезает композитных детей (иконки с `translateY`, подписи с `opacity`), и залипший mid-morph контент рисовался вне пилюли (Issue #152). Подпись таба позиционирована абсолютно и не участвует в раскладке слота: иконка остаётся единственным flex-центрированным содержимым и не «уезжает» вверх в свёрнутом круге. В развёрнутом баре иконка поднята на фиксированный offset (`getTabIconOffset`) и уступает место подписи снизу, а при морфе плавно возвращается в центр; высота самого таб-элемента (`getTabItemHeight`) растёт вместе с островом, поэтому между иконкой и подписью остаётся чистый вертикальный зазор. Неактивные табы не размонтируются, а плавно уходят по ширине и прозрачности (`getTabSlotStyle`), чтобы не было мигания при морфе. У каждого слота, как и у самого острова, есть committed resting-слой: `TabSlot` кладёт `getTabSlotStyle` от settled-флагов (`settledCollapsed` — форма, `settledOneLine` — диаметр, оба из `useTabIslandMorph`) последним элементом массива стилей — на iPad Safari animated-стиль слота мог залипнуть на развёрнутой геометрии в середине морфа (Issue #152), и React-коммит на settle возвращает финальную геометрию, даже если animated-слой так и не ожил. Мёртвый режим нижней пилюли (поле в строке) дополнительно принудительно сворачивал остров по `isSearchFieldVisibleAtom` и убирал его по `isSearchFieldFocusedAtom`; в приложении этот режим больше не включается (`isSearchOpenAtom` не пишется маршрутом), поэтому остров живёт по скроллу, а строка показывает поиск слотом в развёрнутом острове (отдельным кругом — в свёрнутой) и мини-плеер. Фокус поля страницы разворачивает бар, но не трогает остров. Геометрия морфа вынесена в чистые хелперы `src/widgets/tab-bar/lib/getIslandStyle.ts` и хук `useTabIslandMorph`. При каждом монтировании корневого лейаута бар стартует развёрнутым: `useLaunchBarState` (`widgets/expandable-player`, вызов из `app/_RootLayout.tsx`) сбрасывает `isBarCollapsedAtom` и снапит общий драйвер «одной линии» (`oneLineBarMorphDriver.snap`) в render-фазе корня — до того, как дочерний хром заполнит `settled` из атома, — поэтому render-phase seed'ы (`useAtomMorphDriver`) читают уже развёрнутый атом: мини-пилюля не показывает свёрнутую геометрию и не проигрывает слайд запуска. Коррекция нужна на каждом монтировании, а не один раз за процесс: на Android JS-процесс переживает свайп из «недавних» (медиа-сервис), и новое открытие монтирует корень со старым флагом (см. [updates.md](./updates.md)).

**Морф стартует из подписки на атом, а не из render-эффекта.** Цель острова — вычисляемый `isTabIslandCollapsedAtom` (`isBarCollapsedAtom || isSearchFieldVisibleAtom`, `src/widgets/tab-bar/model/barMorph.ts`); модульный `tabIslandMorphDriver` (`widgets/tab-bar/model/tabIslandMorphDriver.ts`, фабрика `createAtomMorphDriver` из `shared/lib/hooks/atomMorphDriver.ts`) подписывается на него и запускает `withTiming` в том же тике, что и изменение атома. Раньше `withTiming` стоял в `useEffect` по булеву из рендера: на Android dev-сборка тратила ~130 мс на React-коммит до эффекта, и строка заметно замирала перед началом движения (на web коммит дешёвый, поэтому там задержки не было). Мини-пилюля (та же ось «одной линии»: `isOneLineBarAtom` = `isBarCollapsedAtom && !isSearchFieldVisibleAtom`, читается кросс-слайсом через `widgets/tab-bar/@x/morph`) стартует так же, а у кнопки поиска своего клока нет вовсе — её отрыв читает ось формы острова, поэтому все поверхности движения начинаются синхронно в одном кадре. React-состояние (`isCollapsed`) по-прежнему приходит позже и обслуживает **только** гейтинг ввода, а не геометрию: скрытые слоты перестают ловить тапы на самом флипе, а тактильный отклик активного таба включается только в свёрнутом круге — `TabButton` гейтит гаптику по живому флагу (`hapticDisabled={isActive && !isBarVisuallyCollapsed}`), поэтому тап по кружку, который разворачивает бар, отзывается в пальце. Resting-геометрию кормит settled-флаг из `useAtomMorphDriver`, запаздывающий до завершения морфа: на флипе он коммитит СТАРТОВОЕ состояние новой анимации, а цель — только по completion (см. [theme.md](./theme.md)). Все оси морфа идут через модульные драйверы (фабрика `createAtomMorphDriver`, `shared/lib/hooks/atomMorphDriver.ts`; React-обёртка `useAtomMorphDriver.ts`): **A** — форма и ширина острова табов (его высота — на оси D; `widgets/tab-bar/model/tabIslandMorphDriver.ts`, атом `isTabIslandCollapsedAtom`), **B** — открытие поиска (`widgets/search-island/model/searchOpenDriver.ts`, `isSearchOpenAtom`), **C** — фокус поля (`.../searchFocusDriver.ts`, `isSearchFieldFocusedAtom`), **✕** — внешний крестик (`.../searchCloseDriver.ts`, `isSearchCloseVisibleAtom`), **D** — «одна линия» (`widgets/tab-bar/model/oneLineBarMorphDriver.ts`, `isOneLineBarAtom`) — одна ось двигает паддинг ряда островов, высоту таб-острова и его слотов, поле поиска и геометрию мини-пилюли. Оси B/C/✕ отдаются наружу кросс-импортом `widgets/search-island/@x/morphDrivers.ts`, оси A и D — `widgets/tab-bar/@x/morph.ts`. Каждая поверхность читает один и тот же инстанс своей оси, поэтому дрейфа между поверхностями нет.

**Часы морфа хранят JS-зеркала.** `createAtomMorphClock` (`shared/lib/hooks/atomMorphClock.ts`) держит `isAnimatingFlag` и `generationCounter` в обычном JS рядом с Reanimated shared values, потому что на нативе запись shared value из JS применяется на UI-потоке асинхронно (Reanimated 4.7 shareables), и чтение в том же тике возвращает устаревшее кэшированное значение. Пока активация кадровых хостов и защита от устаревшего settle читали `isAnimating.value`/`generation.value` сразу после записи, они видели старое состояние: хосты деактивировались в том же тике, `frameStep` не запускался, и все морфы нижней панели (остров, пилюля поиска, мини-плеер) залипали в стартовой позе. Правило: **никогда не принимать решения по `sv.value` сразу после записи из JS** — писать shared value для worklet и читать JS-зеркало; `frameStep` по-прежнему читает shared values на UI-потоке, где они свежие.

Скролл-драйвер подключён к основным скроллам «Слушать» (`ListenScreen`, `Animated.ScrollView` секций) и списку выдачи страницы поиска (`SearchResultsList`, через `useBarCollapseOnScroll`), а также к истории (`HistoryScreen`), офлайну (`OfflineScreen`) и сворачивающимся шапкам плейлистов (`pages/playlist/lib/useCollapsingHeader.ts`, `widgets/playlist-list/lib/useCollapsingHeader.ts`). Драйвер приостанавливается (`isSuspended`) в двух случаях: пока развёрнут плеер (`isPlayerExpandedAtom`) **или** нет активной проповеди (`currentAudioAtom === null` — без мини-плеера свёрнутая строка оставила бы мёртвый зазор на его месте). Маршрут поиска драйвер не приостанавливает — приостановка по поиску удалена: поле переехало на страницу, и прокрутка выдачи сворачивает бар как остальные списки. Эти условия собирает хук `useIsBarCollapseSuspended` (`src/features/sermon-search/lib/useIsBarCollapseSuspended.ts`, наружу отдаётся кросс-импортом `features/sermon-search/@x/suspension`); его читают все перечисленные драйверы (`SearchResultsList` — тоже). `currentAudioAtom` и `isPlayerExpandedAtom` реэкспортированы через `entities/player/@x/sheet`, чтобы экраны и виджеты не тянули barrel `entities/player` с expo-audio в модульный граф списков (падали тесты экранов); Хелпер `useIsSearchBarCollapseSuspended` удалён вместе с приостановкой по поиску. Оба списка при этом ставят `keyboardDismissMode='on-drag'`: драг по строке, оказавшейся под нижним хромом, опускает клавиатуру и одновременно прокручивает список, а позы страницы от фокуса не зависят, поэтому blur на драге ничего не перестраивает. Касаниям пройти сквозь полосу помогает гейтинг слоёв: `floatingContainer` и `islandsRow` — `box-none`, host таб-острова — `box-none` в покое и `none` в фокусе поля, хост движущейся кнопки поиска занимает ровно её прямоугольник (слот острова ⇄ круг) и лишней полосы не добавляет, слой мини-плеера — `box-none`. Поэтому скролл начинается на любой точке полосы, кроме самих контролов (тап/драг ровно по пилюле, «✕» или кнопкам табов по-прежнему принадлежит им). Драйвер подписан на `isBarCollapsedAtom` и зеркалит внешние изменения в свой UI-thread snapshot: тап по свёрнутому кружку разворачивает бар без события скролла, и без синхронизации следующий скролл вниз считал бы бар уже свёрнутым и не сворачивал бы его до пересечения верхнего порога. При этом драйвер запоминает последний обработанный offset: повторный `onScroll` с тем же offset (перестройка layout/клавиатуры, вызванная самим тапом) не считается скроллом и не сворачивает только что развёрнутый бар — иначе первый тап по кругу поиска или активного таба в свёрнутой строке визуально «не срабатывал». Реальный скролл (offset изменился) сворачивает бар как раньше. Работает одинаково на нативе и web: `onScroll` читает `event.contentOffset.y`, который react-native-web поставляет так же.

Изменение offset бывает и не жестом: когда над вьюпортом монтируется/размонтируется контент (на «Слушать» при активации поискового запроса секции заменяются списком результатов, при очистке — возвращаются), scroll anchoring браузера сдвигает `scrollTop` на высоту этого блока и присылает обычный `onScroll` — например, 600 → 552. Раньше драйвер принимал такой сдвиг за скролл и сворачивал только что развёрнутый бар: первый тап по кругу поиска из свёрнутой строки открывал поле и тут же прятал его обратно (визуально «тап не сработал»), а закрытие ✕ или тап по кругу активного таба из закрытой поисковой сессии снова сворачивали бар. Поэтому смена высоты контента помечает следующий изменённый offset как layout-сдвиг: он только перебазирует драйвер (`lastOffset`) без пересечения порогов, а следующее настоящее событие скролла снова сворачивает/разворачивает бар. Сигналов два, и они не зависят от порядка доставки: `onContentSizeChange` от скролла (на «Слушать» подключён к `Animated.ScrollView`) и `contentSize` самого события `onScroll`. Второй обязателен на web: react-native-web присылает anchoring-`onScroll` в шаге рендера, а `onContentSizeChange` — это `onLayout` контент-контейнера, который доезжает только следующим React-коммитом. Без сравнения `contentSize` из самого события с сохранённой высотой драйвер видел сдвинутый offset раньше смены высоты и сворачивал бар — тот же «первый тап не сработал». Замер высоты при монтировании (до первого скролла) перебазированием не считается, иначе первый скролл пользователя после запуска экрана терялся бы. Дельта меньше пикселя считается округлением layout, а не сменой контента.

**Ретракт острова по фокусу поля (`searchFocusMorphDriver`) — мёртвый режим нижней пилюли.** В приложении поле страницы живёт вне нижней строки, поэтому остров не ретрактится и мини-плеер не тюкается; ниже описано прежнее поведение нижнего поля. Пока поле в фокусе, остров табов уходит из строки целиком: `getIslandStyle` гасит его ширину и прозрачность до нуля по `focusProgress` (`searchFocusMorphDriver` от `isSearchFieldFocusedAtom`), а пилюля поиска растягивается до левого внутреннего края. При открытом маршруте без фокуса строка читается как `[круг активного таба][поле]`: остров остаётся кругом, пилюля занимает слот справа от него. Обе поверхности идут одной длительностью `BAR_MORPH_DURATION_MS`, поэтому не рассинхронизируются. Мини-плеер при этом остаётся **отделённым** от строки: `isOneLineBarAtom` требует «бар свёрнут **и** поле не видимо», а тюк пилюли под фокусом — отдельная анимация по `searchFocusMorphDriver` (`translateY` + fade в `CollapsedMiniPlayer`), поэтому в фокусе пилюля плеера уезжает под строку поиска, а не сворачивается в неё. Когда тюк полностью осел (слайд 200 мс + задержанный фейд 120 мс; teardown выводится автоматически — `BAR_MORPH_DURATION_MS + MINI_TUCK_FADE_MS` = 320 мс), пилюля **полностью убирается из дерева** (`useMiniPlayerMount`), чтобы её кнопка play/pause не ловила клики под полем. На возврате пилюля монтируется сразу, но остаётся pointer-inert (`pointerEvents='none'` по `settled` морфа) до приземления обратного морфа.

Виджет поиска `SearchIslandMorph` (`src/widgets/search-island/`, компактная раскладка) — стеклянный кадр поля-пилюли (`GlassSurface`, `zIndex: 20` поверх острова). **В баре он больше не рендерится**: отрыв кнопки к кругу ведёт `TabBarSearchButton` (см. «Свёртывание» выше), а `SearchIslandMorph` остался поверхностью мёртвого режима поля в нижней строке и в приложении не монтируется. Режим поля (морф круга в пилюлю по `openProgress` от `isSearchOpenAtom`, фокус-слой, внешний «✕») больше нигде не включается: маршрут не пишет `isSearchOpenAtom`, поле ввода рисует страница (`SearchPageField`). Ниже — описание прежнего режима, сохранённого как мёртвый код до чистки. Геометрию даёт `getSearchIslandGeometry`: `left`/`width` от `openProgress` (ось B, `searchOpenDriver` от `isSearchOpenAtom`; 0 — круг, 1 — слот справа от круга активного таба), высота/радиус — от однострочной оси D и `openProgress` (закрытый чип 60/48, открытое поле всегда 60), низ — от `tabBarHeight` (минус `BAR_ROW_MIN_HEIGHT`), кап — `CONTENT_COLUMN_WIDTH`; `focusProgress` (ось C от `isSearchFieldFocusedAtom`) растягивает пилюлю до левого внутреннего края и освобождает слот внешнего «✕»; `closeProgress` (ось ✕ от `isSearchCloseVisibleAtom`) резервирует под него круг диаметром с поле. Лупа 32 смонтирована всегда, размер постоянный (глиф не масштабируется — уменьшенный глиф Android обрезал по границам пилюли). Своей тени у кадра нет (теней у нижних островов нет вовсе). Внутрь кадра — `SearchBar` с полем, микрофоном при пустом запросе и ⊗ очистки при непустом; тап по любой точке раскрытой пилюли (свободные места строки и её паддинги) фокусирует поле ввода: под контентом (первый ребёнок фрагмента) лежит прозрачный focus-слой, обёртка контента и строка поля помечены `box-none`, а микрофон и ⊗ как прямые дети выигрывают hit-test. Закрытый круг — прозрачный тап-слой с целью онбординга `listen.search-toggle`: его обработчик `openSearch` (`useOpenSearch`) разворачивает бар (`setBarCollapsed(false)`) и навигирует на `/search`; на самом маршруте `/search` он вместо повторной навигации фокусирует поле страницы (`focusSearchInput`). Авто-фокус при входе на маршрут делает `useClearSearchOnLeave`. Внешний «✕» (`SearchIslandCloseSlot`) остался только в мёртвом режиме нижней пилюли; на странице поиск закрывают `Escape` (web), смена таба и «Назад». `useCloseSearch` (`resetSearchSession` + `Keyboard.dismiss` + `router.back()`, fallback `router.navigate('/listen')`) обслуживает `Escape`. Перехода видимости нет — кадр не фейдится и не размонтируется, геометрия морфится; кроссфейдится только контент по `openProgress`. Строка таб-бара и её контейнер помечены `pointerEvents='box-none'`, чтобы пустая область строки не перехватывала тапы; живая сессия голосового ввода абортится на blur поля, очистке ⊗ и сбросе сессии. При скрытом поле (другой таб) поле блюрится, чтобы клавиатура не висела над невидимым полем (`useSearchInputFocus`).

Строка табов имеет фиксированную высоту `BAR_ROW_MIN_HEIGHT` (68; в широкой раскладке — `WIDE_BAR_ROW_HEIGHT`, 56) плюс нижний отступ `getBarBottomPadding(insets.bottom, isWeb)` (`src/shared/ui/layout/bottomBarLayout.ts`) — этого хватает развёрнутому острову (60; в широкой — 48) с запасом, а свёрнутый остров (48 в компактном ряду, 60 при видимом поле) умещается в той же строке. Высота самой строки не зависит от морфа острова (меняется только остров внутри), поэтому измеренная высота таб-бара не скачет между состояниями. На админских табах (`app/admin/(tabs)/_layout.tsx`) кнопка поиска скрыта пропом `hideSearch`.

**Клавиатура.** В edge-to-edge (RN 0.88) `windowSoftInputMode="adjustResize"` больше не уменьшает окно, поэтому нижняя строка сама не поднимается над системной клавиатурой — ни на Android, ни на iOS. `useKeyboardBottomInsetSync()` (`src/shared/ui/layout/lib/keyboardInset.ts`) смонтирован один раз в `app/_layout.tsx`, слушает `keyboardDidShow`/`keyboardDidHide` и пишет высоту клавиатуры в общий Reanimated shared value `keyboardBottomInsetSv`; на web подписки нет (визуальным вьюпортом занимается браузер, поведение прежнее). Каждый контейнер нижней строки применяет `translateY = −keyboardBottomInsetSv` к своему внешнему pass-through слою: `CustomTabBar` (`floatingContainer`, а внутри него и движущаяся кнопка поиска) и мини-плеер (`CollapsedMiniPlayer` для пилюли, `ContainerView` для контейнера-подложки). Полноэкранный плеер не сдвигается: в `ContainerView` lift включается только при `expanded === false`, а `progress`-анимация разворота остаётся прежней. Высота строки измеряется через `onLayout` и от `transform` не зависит, поэтому `tabBarHeightAtom` и геометрия островов не пересчитываются при появлении клавиатуры. Поле поиска, результаты и мини-пилюля остаются видимыми над клавиатурой.

Подписи табов не переносятся и почти не масштабируются шрифтом: в `TabButton.tsx` у текста заданы `numberOfLines={1}` и `maxFontSizeMultiplier={1.2}` (фикс «сломанного» таб-бара на узких экранах / крупном системном шрифте, Issue #53).

Переключение табов нажатием «молчаливо»: `TabButton` передаёт `hapticDisabled={!(isActive && isBarVisuallyCollapsed)}` в `TouchableButton`, поэтому смена таба идёт без раннего press-пульса, а единственный отклик дают биты перелёта капсулы — мягчайший тик на промежуточных и Light на последнем (`hapticHighlightPass`/`hapticLanding`, см. выше); по активному табу в развёрнутом баре ещё и нет нажимного затемнения (`activeOpacity={1}`), а навигация для него пропускается в `useTabPress` (кроме режима активного `/search`, см. ниже). В свёрнутом баре виден только круг активного таба, и тап по нему **разворачивает бар** (`setBarCollapsed(false)`, тот же морф 200 мс), не навигируя: мини-плеер поднимается автоматически, потому что его геометрия читает тот же `isBarCollapsedAtom`. Исключение — фокус `/search`: круг показывает неактивный фолбэк «Слушать», и тап навигирует (см. ниже). Этот тап получает обычный хаптик нажатия (ранний пульс и `hapticLight` на отпускании), как любое «возвратное» нажатие: свёрнутость (`isBarVisuallyCollapsed` из `useTabIslandMorph`) снимает `hapticDisabled` с активного таба. Бар не открывает и не закрывает поиск: тап по кругу обрабатывает тап-слой пилюли (`useOpenSearch`: разворот бара, затем `router.navigate('/search')`; на самом `/search` — фокус поля страницы), закрытие — внешний «✕», «Назад» или смена таба, а сброс сессии — `useClearSearchOnLeave`.

**Пока активен маршрут `/search`, поиск — активная вкладка.** В развёрнутом компактном острове слот поиска стоит наравне с табами: та же доля ширины, иконка-лупа и подпись «Поиск» (`TabIslandSearchSlot`); в широком острове это иконка без подписи в слоте шириной 48. При фокусе `/search` капсула переезжает на слот поиска. В свёрнутой компактной строке слот гаснет, а капсулу несёт отдельный круг поиска (`TabBarSearchButton`); круг табов при этом показывает «Слушать» **неактивным**. Ключ этого круга `CustomTabBar` берёт не из `state.index` (там стоит `search`, которому слот не соответствует), а из чистого `useActiveTabRouteKey` (`src/widgets/tab-bar/lib/useActiveTabRouteKey.ts`): при фокусе `/search` он отдаёт фолбэк — «Слушать», а если такого маршрута в наборе нет, первый видимый таб. Подсветка гейтится отдельно (`isHighlighted = isActiveSlot && !isSearchFocused`), поэтому слот-фолбэк остаётся без капсулы: активная цель — поиск. Тап по любому табу в таком состоянии **навигирует**, а не молчит: `useTabPress` при `isSearchFocused` не применяет no-op активного таба (иначе пользователь заперт в поиске), эмитит `tabPress` и вызывает `navigateToTab`, а смена пути запускает `useClearSearchOnLeave` — запрос, фокус и ввод сбрасываются одной транзакцией, поиск закрывается.

На web кнопки табов (`TabButton`) и вложенный таб-бар (`shared/lib/tab-bar/renderTabBar.tsx`) рендерятся как настоящие `<button>` — у них задан `accessibilityRole='button'` (иначе RNW отдаёт `<div tabindex="0">`, который не получает Vimium-хинты). Подробнее — [web.md](./web.md#настоящие-button-для-vimium-хинтов).

Нижний внутренний отступ таб-бара задаётся динамически через `useBarBottomPadding()` (`src/shared/ui/layout/lib/useBarBottomPadding.ts`; приложение рендерится edge-to-edge): на нативе при реальном системном инсете (3-кнопочная или жестовая навигация, home indicator на iOS) острова стоят **вровень с линией safe-area** — без дополнительного зазора над ней, а в первые кадры, пока insets ещё нулевые, держится пол `BAR_BOTTOM_INSET_MIN = 12`. На iOS web (iPhone/iPod или iPadOS, маскирующийся под Mac) нижний отступ постоянный — 21 (`IOS_WEB_ISLANDS_GAP`): зазор центрирует полосу home indicator (по 8 px снизу и сверху; полоса занимает [8, 13] px от нижней кромки), оболочка — `100lvh` на iOS web (полная физическая высота экрана через класс `ios-web`) и `100dvh` на Android/десктопе, полоса home indicator рисуется ОС поверх страницы внутри этого зазора, поэтому env()-проба намеренно игнорируется — иначе она удваивает системную полосу, когда сообщает значение. На остальном web (браузеры Android и десктоп) зазор равен `max(bottomInset, 25)` (`BAR_BOTTOM_INSET_WEB = BAR_SIDE_INSET_EXPANDED`) — снизу он зеркально повторяет боковые инсеты развёрнутого хрома и образует с ними ровную рамку; больший реальный инсет (линия safe-area в установленном PWA) выигрывает через `max`. Разделения на браузер и PWA больше нет: детектор `useIsBrowserWeb` и аргумент `browserClearance` удалены, хук на iOS web возвращает `IOS_WEB_ISLANDS_GAP` до вызова `getBarBottomPadding(bottomInset, isWeb)` (`src/shared/ui/layout/bottomBarLayout.ts`). Причина — на iOS Safari env()-проба в момент монтирования отдаёт 0, а когда сообщает значение, совпадает с системной полосой, которую ОС уже рисует под оболочкой: пол 12 прилипал к нижней кромке, 34 давал слишком широкую полосу, поэтому оставлен только зазор 21 (Issue #154, скриншоты пользователя). Поверх статичного пола на web действует живой подъём через общий `keyboardBottomInsetSv` (полоса `visualViewport`, тот же пайплайн, что и подъём над клавиатурой): он компенсирует скрывающуюся панель инструментов iOS и застывший layout viewport; детали — [web.md](./web.md#safe-area-на-web). Сами острова при этом привязаны к нижней кромке content-бокса строки (не центрируются), поэтому их силуэт касается линии паддинга в обоих состояниях бара. Так как высота строки таб-бара измеряется через `onLayout` (см. ниже) и фиксирована между развёрнутым/свёрнутым состояниями, при росте таб-бара мини-плеер и экраны адаптируются автоматически — через `tabBarHeightAtom`.

Тот же принцип применён к нижнему отступу контролов полноэкранного плеера: `useBarBottomPadding()` — формула повторяет таб-бар, поэтому контролы встают на одном уровне с кнопками таб-бара и на жестовой навигации, и на 3-кнопочной (Issue #105).

Высота строки таб-бара (`BAR_ROW_MIN_HEIGHT` + `getBarBottomPadding(insets.bottom, isWeb)`) измеряется через `onLayout` на строке островов и записывается в `tabBarHeightAtom` (`src/shared/ui/layout`, экшен `setTabBarHeight`) — это единственный источник правды о высоте таб-бара. Ширина через `onLayout` не измеряется: строка — это `width: '100%'` в контейнере во всю ширину с `maxWidth`, равным базе раскладки — короткой стороне окна, урезанной `CONTENT_COLUMN_WIDTH` (`useLayoutBaseWidth`, `src/shared/ui/layout/lib/useLayoutBaseWidth.ts`). Поэтому `useTabIslandMorph` выводит ширину острова из базы на рендере, а анимированный слой читает её из shared value, записанного в layout-эффекте до отрисовки. Короткая сторона инвариантна к повороту телефона: остров, слоты, кнопка поиска и пилюля сохраняют портретную ширину, двигается только положение — строку центрирует нативный flex, а абсолютные кнопку поиска и пилюлю центрирует инсет, вычисленный из живой ширины окна (размеры при этом остаются из базы). Реальные resize (разделитель split-screen, изменение окна) базу меняют, и она приходит в worklet'ы тем же pre-paint каналом. Неположительная высота — не измерение: `onLayout` игнорирует `height <= 0` и не публикует её (неактивный экран табов на web рендерится с `display: none` и измеряется как 0×0), поэтому в атом попадает только реальный замер. Высота строки не зависит от морфа острова (остров внутри меняет высоту 60 ⇄ 48 (48 — только в однострочном ряду со скрытым полем), но строка остаётся 68; в широкой раскладке — 56), поэтому повторного измерения на каждом кадре морфа нет и высота не скачет между свёрнутым и развёрнутым состояниями. Начальное значение атома — приближение `PLAYER_SIZES.tabBarHeight` из темы, только до первого измерения. Потребители высоты (мини-плеер, нижние отступы экранов) читают атом, константу напрямую больше не используют — см. [player.md](./player.md) и [state.md](./state.md); экранные отступы идут через `useScreenChromePadding()` (см. «Широкая раскладка» выше).

## Анимации и Reduce Motion

Все морфы нижней строки — остров табов, пилюля/поле поиска и мини-плеер — идут через Reanimated, чьи анимации по умолчанию используют `ReduceMotion.System`. Если ОС или браузер сообщают об уменьшении движения (Android → «Удалить анимации» в специальных возможностях / `animator duration scale = 0`; `prefers-reduced-motion: reduce` в браузере), `withTiming` завершается мгновенно, без кадров: морф не проигрывается, а сразу оказывается в целевом состоянии. Это **осознанное доступное поведение** — приложение намеренно не переопределяет его глобальным `ReducedMotionConfig` (рассматривали и отклонили).

**Диагностика для агентов:** «анимации прыгают мгновенно» / «морф бара не проигрывается» → первым делом проверьте системную настройку анимаций устройства или браузера, а не ищите регресс в коде. В этом режиме приложение работает корректно, просто без промежуточных кадров.
