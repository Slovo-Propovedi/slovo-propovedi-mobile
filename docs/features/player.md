# Аудиоплеер

**Слой:** `entities/player` + виджет `widgets/expandable-player`
**Статус:** готов

## Обзор

Аудиоплеер построен на `expo-audio` и отвечает за воспроизведение проповедей, очередь, режимы повтора, lock-screen-управление и фоновое воспроизведение.

- **Очередь (native):** на native воспроизведение ведёт единственная нативная очередь `AudioPlaylist`, которой владеет `native/PlaylistEngine.ts`. Переход между треками выполняет движок (ExoPlayer на Android, AVQueuePlayer на iOS) **без участия JS** — это цель миграции: воспроизведение продолжается при заблокированном экране и замороженном JS-процессе. JS — наблюдатель: `trackChanged` → `TrackAutoAdvanceService.handleTrackChanged` (история, resume-seek, метаданные, кэш). Web-сервис не менялся и по-прежнему управляет треками в JS.
- **Платформы:** Android — релизная платформа миграции (проверено на устройстве); iOS компилируется, но на устройстве не тестировался; web — прежняя реализация (`HTMLAudioElement`).
- **Проверка миграции:** typecheck, lint, knip, jest, gradle-сборка и `yarn test:native` — зелёные.
- **iOS:** фоновое воспроизведение включено через `infoPlist.UIBackgroundModes: ["audio"]` и плагин `expo-audio` с `enableBackgroundPlayback: true` (`app.config.ts`).
- **Android:** foreground-service через permission `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (`app.config.ts`).
- Управление аудио-режимом — `src/entities/player/lib/PlayerService/native/AudioModeManager.ts` (`interruptionMode: 'doNotMixPersistent'`, `playsInSilentMode: true`, `shouldPlayInBackground: true`).

### Android audio-focus (expo-audio из SDK 58, без патча)

До SDK 58 Android-фокус приходилось чинить патчем `patches/expo-audio+57.0.5.patch` — в `57.0.x` было два бага: запрос фокуса для `doNotMix` шёл как `AUDIOFOCUS_GAIN_TRANSIENT`/`USAGE_UNKNOWN` (чужое приложение могло вернуться поверх проповеди), а фокус освобождался при входе ExoPlayer в `Player.STATE_BUFFERING` (на время буферизации `isPlaying` = `false`) и больше не запрашивался.

В 58.0.9 поведение нативное, патч **удалён**:

- `Playable.hasActivePlaybackIntent()` удерживает фокус во время `Player.STATE_BUFFERING` — перебуферизация больше не делает воспроизведение невидимым для focus-стека;
- добавлен режим `interruptionMode: 'doNotMixPersistent'` — постоянный `AUDIOFOCUS_GAIN` вместо transient (expo-audio CHANGELOG 58.0.9, PR #49101). Приложение мигрировало на него в `AudioModeManager.ts` (`'doNotMix'` → `'doNotMixPersistent'`).

Апстрим по-прежнему **не** ставит `USAGE_MEDIA` в `AudioAttributes` — принято: постоянный gain закрывает проблему авто-возврата чужого звука, ради которой старый патч добавлял `USAGE_MEDIA`. Верификация при апгрейде пакета — `yarn check:patches` (generic-гвард сверяет версии в именах патчей с установленными).

## Архитектура PlayerService

Паттерн **Service**: единый singleton-объект оборачивает платформенные API. Платформенное разрешение — через расширения `.native.ts` / `.web.ts` (резолвится Metro/Webpack).

- `src/entities/player/lib/PlayerService/index.native.ts` — класс `PlayerService` (нативный, expo-audio). Экспортирует singleton `playerService`.
- `src/entities/player/lib/PlayerService/index.web.ts` — класс `WebPlayerService` (HTMLAudioElement).
- `src/entities/player/lib/PlayerService/index.ts` — TypeScript-fallback: `export { playerService } from './index.native'`.

### Стриминг и кэш

Очередь собирается из **уже разрешённых источников** — `resolveQueueSource` (`src/entities/player/lib/PlayerService/native/resolveQueueSource.ts`), вызывается из `queueContext` при каждой сборке очереди:

- если файл **полностью в кэше** → `file://` (мгновенный старт);
- иначе — **оригинальный сетевой URL**: стриминг с сервера (`downloadFirst: false`, прогрессивная буферизация через нативные движки: ExoPlayer на Android, AVQueuePlayer на iOS), воспроизведение начинается после загрузки метаданных/начала буфера, не дожидаясь полного файла. Параллельно `queueLoader` (на старте) и координатор (на смене трека) ставят **текущий** трек в офлайн-кэш через `startBackgroundCaching`.
- **Web** — `WebPlayerService` использует `HTMLAudioElement` (`new Audio()`), который всегда выполнял прогрессивное стриминг-воспроизведение независимо от `downloadFirst` (опция не влияет на веб-путь). Офлайн-воспроизведение закешированных треков на web делает прозрачно Service Worker (`<audio src>` остаётся сетевым URL) — см. [web.md](./web.md).

**Partial-файлы в очередь не попадают никогда.** Усечённая длительность `.cache.mp3` испортила бы таймлайн всей очереди, поэтому очередь — это только полные кэш-файлы или сеть. Фоновая закачка остаётся **per-current-track**: её взводит координатор на `trackChanged` (и `queueLoader` на старте), а не сборка очереди — очередь из сотни треков никто не кэширует.

**Где partial всё ещё используется:** только в seek/resume swap-путях (`seekViaPartialSource` / `swapPartialForNetworkSeek` / `resumeWithSourceSwap`) — источником текущего элемента очереди он становится через `swapCurrentSource`, а не через её сборку. Пока играет партиал, таймлайн показывает **полную длительность** записи — она берётся из истории прослушивания (`applyPartialDuration` в `src/entities/player/lib/PlayerService/native/partialDuration.ts`: запись с `durationMs > 0` для текущей проповеди), а если записи нет — остаётся последняя известная полная длительность. Таймлайн **никогда не показывает** усечённую длительность скачанной части и не прыгает при подмене источника на партиал и обратно. Позиция и буферизованная доля читаются относительно полной длины; объём буферизации показывают существующие полосы скачивания (`MiniDownloadProgress`/`FullscreenDownloadProgressBar`).

**Край частичного файла больше не управляет авто-переходом.** Прежний инвариант «дошли до края партиала → пауза вместо перехода» **отменён**: в очереди партиалов нет, а нативный переход не спрашивает JS. Офлайн + следующий трек не закэширован → нативная ошибка/столл → `reportPlaybackError` (`reportError` + `isStalledOfflineAtom`) и пауза; после возврата сети reconnect-heal перепривязывает источник. Trade-off осознанный: непрерывность воспроизведения при замороженном JS важнее предупреждения о нескачанном следующем треке. Если офлайн стартуется трек, у которого на диске есть только партиал, офлайн-guard его по-прежнему разрешает, но очередь не может использовать партиал источником — воспроизведение упрётся в сетевой URL и нативный столл (партиал применим только через seek/resume swap).

### Очередь и нативный авто-переход (AudioPlaylist)

На native очередь — единственный владелец порядка воспроизведения. `PlaylistEngine` создаёт `AudioPlaylist` из текущего плейлиста, начальный индекс — текущая проповедь; если текущего плейлиста нет или он не содержит трек, собирается очередь из одного трека. `queueContext` читает `CURRENT_AUDIO`/`CURRENT_PLAYLIST`/`CURRENT_REPEAT_MODE` из AsyncStorage **раньше** атомов: после замороженного JS сторедж — единственная честная запись того, где остановилось воспроизведение. Прежняя JS-машинерия авто-перехода (`handleTrackEnd`, `advanceToNextTrack`, офлайн pre-guard) удалена: нативный переход нельзя пре-блокировать из JS.

**Переход между треками выполняет нативный движок** — без JS. JS получает `trackChanged(previousIndex, currentIndex)` и **сверяет** переход постфактум (`TrackAutoAdvanceService.handleTrackChanged`):

1. если сторедж уже указывает на новый трек (ручное переключение успело закоммитить состояние) — событие игнорируется;
2. старый трек флашится из per-index снапшота движка (последние `currentTime`/`duration` этого индекса) → `recordSermonSwitchAction({ markOldCompleted: true })`;
3. `setCurrentAudioAction` (artwork — из плейлиста), resume-позиция нового трека из истории → `seekToResume` (**только при живом JS**);
4. `savePlaybackProgress` для нового трека;
5. метаданные lock screen (playlist-level, см. ниже) и `startBackgroundCaching` для нового трека.

**Resume-семантика:** при живом JS новый трек перематывается на сохранённую позицию истории; при замороженном процессе — стартует с 0:00. Это осознанный компромисс миграции: непрерывность важнее точности resume, который «догоняется» при пробуждении JS (см. «Возврат в foreground (native reconcile)»). Позиция в пределах 10с от конца (`COMPLETION_REMAINING_MS`) не применяется — трек считается дослушанным.

**Повтор** — нативный loop (`mapRepeatMode`): Off → `'none'`, Queue → `'all'`, Track → `'single'`. Повтор трека больше не JS-перезапуск (`repeatCurrentTrack` удалён): нативный single-item loop не порождает `trackChanged`, поэтому **per-loop событий истории нет** — прежняя семантика «каждый повтор отмечал завершение» отменена. Смена режима применяется на живую очередь (`applyRepeatMode` → `playerService.setRepeatMode`).

**Режим повтора не читается с нативного объекта.** `PlaylistEngine` зеркалит loop в собственном состоянии (значение выставляется при сборке очереди и в `setLoopMode`), а JS-геттер `loop` у `AudioPlaylist` не читается. Апстрим-баг expo-audio 58.0.9 — JS-геттер `loop` был единственным членом `AudioPlaylist` без main-thread hop и ронял плеер при чтении из JS-потока (`IllegalStateException: Player is accessed on the wrong thread`, `AudioModule.kt:1016` → `AudioPlaylist.kt:78`, `ref.repeatMode`) — **исправлен локально** патчем `patches/expo-audio+58.0.10.patch`: геттер обёрнут в `runOnMain`. Патч эффективен, потому что expo-audio собирается из исходников (`expo.autolinking.buildFromSource`, см. [decisions.md](../decisions.md)): при prebuilt AAR правка Kotlin в `node_modules` не компилировалась бы. Зеркало в состоянии движка при этом сохранено — чтение loop из JS не требует блокирующего перехода на main thread. Сеттер был безопасен и без патча (`runOnMain`). Кнопки next/prev на lock screen по-прежнему не выставляются (продуктовый выбор), но их включение теперь безопасно — см. «Метаданные lock screen».

**Ручные Next/Prev** (`usePlayerToggleTrack` → `executeTrackSwitch`) сохраняют JS-funnel: офлайн-guard по целевому треку, flush истории старого, resume из истории, метаданные. `replaceAudio` теперь не пересоздаёт плеер, а делает `skipTo(index)` + `seekTo(position)` в существующей очереди (`replaceQueueTrack`); если трека в очереди нет — one-track rebuild. Событие `trackChanged` от `skipTo` координатор игнорирует (сторедж уже указывает на новый трек).

**Конец очереди** — один `didJustFinish` на последнем элементе при loop `'none'`: `handleQueueEnd` помечает запись завершённой один раз (`markHistoryCompletedAction`, длительность из снапшота) и защитно ставит паузу; повторный вызов дедуплицируется по индексу.

**Известное ограничение:** context-only переключение плейлиста (та же проповедь играет, но текущим стал другой плейлист без вызова player-service) не пересобирает нативную очередь — следующий авто-переход пойдёт по прежнему порядку. Записано в [debt.md](../debt.md).


### Авто-кэш на web при воспроизведении (Issue #81)

Начиная с Issue #81, `WebPlayerService` автоматически кэширует трек при старте воспроизведения — зеркало нативного поведения `resolveQueueSource`. В `loadAudio` (и через него в `replaceAudio`) вызывается `autoCacheOnPlay(audioUrl)` (`webAutoCache.ts`):

- проверяет `audioCacheService.isCached(audioUrl)`; если трек уже в кэше — ничего не делает;
- если не в кэше **и** пользователь онлайн (`isOnlineAtom` из `shared/model/network` через `ctx.get`) — запускает `startBackgroundCaching(audioUrl)`;
- **не блокирует воспроизведение**: проверка и запуск кэширования fire-and-forget (промис с молчаливым `catch` — сбой проверки кэша некритичен, стриминг продолжается из сети), паритет с Issue #73;
- покрывает и начальный `loadAudio` (восстановление приложения), и `replaceAudio` (смена трека).

### Resume со сменой источника на кэш (Issue #107)

Если фоновая закачка завершилась посреди стриминга, а затем интернет пропал, resume (пауза → play) раньше молча не работал: текущий элемент очереди оставался привязан к мёртвому серверному URI, потому что источник резолвился только при сборке очереди (`resolveQueueSource` в `queueContext` — старт/смена контекста).

Фикс — `PlayerService.resumeAfterPause(audioUrl)` (`src/entities/player/lib/PlayerService/native/resumeWithSourceSwap.ts`), вызывается из кнопки play (`useGuardedTogglePlay`) и из same-track ветки `playNewSermonAsync` (повторный тап на тот же трек). Метод сравнивает два факта — «трек закэширован» (`audioCacheService.getCachedUri`) и «очередь привязана к полному cache-файлу» (`playlistEngine.getCurrentSourceUri`): совпали — достаточно `play()`; расхождение (трек докачался, а очередь всё ещё на сетевом URL; или cache-файл удалён) — `swapCurrentSource(cachedUri ?? audioUrl, positionAtom)` и затем `play()`. Подмена источника идёт через `swapCurrentSource` (insert/remove на текущем индексе) и сохраняет тот же экземпляр `AudioPlaylist`/MediaSession/foreground-service. На native через `resumeAfterPause` идут все JS-достижимые пути resume — кнопка play, same-track ветка `playNewSermonAsync` и авто-resume после системного прерывания; на web — UI-resume и reconnect, а web interruption auto-resume сознательно остаётся прямым `audio.play()` (см. комментарий в `interruptionAutoResume.ts`). На web `resumeAfterPause(audioUrl)` сравнивает `src` живого `<audio>` с запрошенным URL (`shouldRebindForResume` в `web/reconnectHeal.ts`): совпадение → `play()` (Service Worker отдаёт закэшированные байты по тому же URL), расхождение → `replaceAudio(audioUrl, position)` и затем `play()`. Same-track ветка `playNewSermonAsync` больше **не** вызывает дополнительный `deps.play()` после `resumeAfterPause` (тот сам стартует воспроизведение) — устранён двойной старт.

**Диагностика `status.error` и границы восстановления.** `playlistStatusHandler` + `reportPlaybackError` читают `status.error` из expo-audio: ошибка уходит в `reportError` (`[player] playback error: …`), а при офлайне (`isOnlineAtom === false`) выставляется `isStalledOfflineAtom`, чтобы reconnect-heal подхватил стрим. Перепривязку источник ошибка не делает — восстановление остаётся за следующим resume-ребром (тап play или авто-resume после прерывания), которое проходит через cached-source swap; мёртвая очередь без последующего play-намерения остаётся молчащей (авто-replay — отдельное UX-решение). Кнопка play на lock-screen/в уведомлении действует на очередь нативно (expo-audio MediaSession/MPRemoteCommandCenter) и из JS не перехватывается; кнопки next/prev там не выставляются — на экране блокировки только seek ±10с, а переключение треков идёт из UI приложения (см. «Метаданные lock screen»).

**Смена плейлиста для уже играющей проповеди.** Если тап по playing-проповеди приходит с другим плейлистом (`currentPlaylistAtom` известен и его `id` отличается), `playNewSermonAsync` не делает no-op (Issue #99), а переключает контекст: `setCurrentAudio` с artwork по правилу `sermon.artwork ?? playlist.artwork`, `setCurrentPlaylist` (next-prev строятся из него), lock-screen metadata — при этом воспроизведение **не** перезапускается и `play()`/`resumeAfterPause` не дергаются, позиция сохраняется. Чтобы арт в уведомлении/lock-screen гарантированно обновился (in-place `updateLockScreenMetadata` может не перерисовать картинку), контекстный switch зовёт `reassertLockScreenMetadata` — полную активацию сессии (`setActiveForLockScreen(true)`), а не `setLockScreenMetadata`. Нативную очередь такой switch **не** пересобирает (player-service не вызывается) — см. известное ограничение в «Очередь и нативный авто-переход» и [debt.md](../debt.md).

### Reconnect-heal (Issue #109)

`reconnectRecovery` (`src/entities/player/lib/reconnectRecovery.ts`) расширяет восстановление устаревшего источника на случай незакэшированного/мёртвого стрима: при возврате сети (false→true по `isOnlineAtom`) `recoverStreamAfterReconnect` на нативе перепривязывает текущий элемент очереди через `replaceAudio` на сохранённой позиции (или собирает очередь заново через `loadAudio`, если она никогда не загружалась), на web — создаёт новый `HTMLAudioElement` на сохранённой позиции. Подробнее — [audio-cache.md](./audio-cache.md) → «Возобновление после восстановления сети (Issue #109)».

Нативное лечение подменяет источник в существующей очереди (или пересобирает её в ветке `loadAudio`), поэтому после успешного `replaceAudio`/`loadAudio` повторно выставляет метаданные lock screen (`reassertLockScreenMetadata`) — зеркало foreground-реассерции (`useAppStatePlayback`). Без этого медиа-уведомление показывает иконку приложения вместо обложки плейлиста.

**Авто-resume после офлайн-зависания (Issue #109 follow-up):** лечение резюмирует не только когда трек «завис» во время воспроизведения (`isPlaying && isBuffering`), но и когда выставлен `isStalledOfflineAtom` (`shouldResume = isPlaying || stalledOffline`) — в ветке, где очередь уже загружена (путь через `replaceAudio`); в ветке «никогда не загружалась» (зависание сразу после офлайн-старта) авто-resume по флагу stall не работает, возобновление следует только за `isPlaying`. Флаг выставляется на нативе в `createAudioInterruptionHandler` при прерывании с `isBuffering` (буферизационный столл сам по себе — признак голодания стрима; NetInfo-флип может отставать от underrun'а), на web — в `onError`, когда `isBuffering` (событие `waiting` приходит до сетевой ошибки; онлайн-сигнал так же может отставать от underrun'а, как и на нативе); сбрасывается при сборке/пересборке очереди (`loadAudio`/`replaceAudio` — нативный chokepoint) и на web-событии `playing`. Нативный heal флаг **не** сбрасывает сам — `loadQueue`/`replaceQueueTrack` делают это на входе; web-heal сбрасывает сразу после чтения (chokepoint'а нет). Принятый trade-off: пауза **во время** офлайн-зависания тоже приведёт к авто-resume; пауза до зависания — нет. Подробнее — [audio-cache.md](./audio-cache.md) → «Авто-resume после восстановления сети».

**Офлайн-seek на частичный файл:** тап по прогрессбару при офлайне, когда источник ещё сетевой и есть частично скачанный файл, подменяет источник на партиал и продолжает воспроизведение с выбранной позиции. Возобновление — по `isPlaying || isStalledOfflineAtom`: продолжает играть, если трек играл или был поставлен на паузу столлом; после ручной паузы остаётся на паузе в выбранной позиции. Принятый trade-off (как у reconnect auto-resume): пауза **во время** офлайн-зависания тоже считается столлом и приводит к авто-resume.

**Seek при загруженном партиале (Issue #109 follow-up):** если источником уже служит сохранённый частичный файл (`.cache.mp3`), а полный файл тем временем докачался в кэш, любой seek подменяет загруженный партиал на полный файл в выбранной позиции — иначе перемотка за пределы скачанной части клампится на усечённой длительности партиала (позиция «прыгает»). Работает и офлайн (локальный файл не зависит от сети); воспроизведение продолжается, если трек играл, пауза остаётся паузой. Решение принимается в `seekViaPartialSource.ts` (`shouldSwapPartialForCachedSeek` + `swapPartialForCachedSeek`), вызывается из `PlaybackController.seekTo` через `seekWithSourceSwap`. Если полный файл ещё не докачан, но пользователь онлайн, seek подменяет партиал на сетевой стрим с выбранной позиции: воспроизведение начинается по мере буферизации, не дожидаясь конца закачки; фоновая закачка продолжается (очередь дедуплицирует), частичный файл при перезапросе **не удаляется** (чистка — на успешном скачивании и в свипах; удаление убивало temp активной закачки → `rename` падал с `NoSuchFileException`). Решение — `shouldSwapPartialForNetworkSeek`/`swapPartialForNetworkSeek` в `swapPartialForNetworkSeek.ts`, вызывается из `seekWithSourceSwap` в `seekViaPartialSource.ts`.

**Seek-swap без мигания прогресса:** при подмене источника (партиал → кэш/сеть) seek-guard взводится в `swapSourceForSeek` (`armSeekSwap`) и остаётся взведённым через весь `swapCurrentSource`: та же очередь продолжает слать статусы уже привязанных слушателей, и сброшенный guard пропустил бы `currentTime≈0` нового источника в `positionAtom` (видимый сброс прогрессбара в 0). Позиция держит цель, пока новый источник не загрузится; после успешного swap состояние seek явно очищается (тот же тройной сброс, что и на ошибке). Длительность при same-track swap (позиция > 0) **не сбрасывается** — известная корректная длительность сохраняется; при настоящей смене трека (позиция 0) сброс остаётся.

**Известные ограничения:** на native через cached-source swap идут все JS-достижимые пути resume (UI-resume и авто-resume после прерывания); на web — UI-resume и reconnect через swap, а web interruption auto-resume сознательно остаётся прямым `audio.play()` (см. комментарий в `interruptionAutoResume.ts`). Единственный «незалеченный» вход — кнопка play в lock-screen/уведомлении: она действует на нативную очередь (expo-audio MediaSession/MPRemoteCommandCenter) и не доходит до `resumeAfterPause`, поэтому мёртвый источник в текущем элементе очереди там всё ещё не лечится (см. [debt.md](../debt.md), `src/entities/player/lib/PlayerService/native/LockScreenControls.ts`).

### Офлайн-guard при воспроизведении (Issue #81)

Общий guard `guardOfflinePlayback(audioUrl, isOnline)` (`src/entities/player/lib/playOfflineGuard.ts`) проверяет офлайн-ситуацию перед стартом воспроизведения:

- если `isOnline` — поток воспроизведения идёт как раньше;
- если **офлайн** и трек **не закэширован** (`audioCacheService.isCached` = false) — показывается информационная модалка `showInfo(OFFLINE_PLAYBACK_MESSAGE)` (в стиле `ConfirmDialog`, без иконки, заголовок «Информация» по умолчанию) с текстом «Невозможно воспроизвести незакешированную проповедь без интернета», и функция возвращается раньше (guard вернул `true` — воспроизведение заблокировано);
- если **офлайн**, но трек **закэширован** — воспроизведение из кэша идёт нормально (пропуск guard'а);
- если **офлайн**, трек не закэширован, но на диске есть **сохранённый частичный файл** (`.cache.mp3`) — guard разрешает воспроизведение без диалога (легаси-правило). Очередь партиал источником не использует: старт такого трека упрётся в сетевой URL и нативный столл; партиал применим только через seek/resume swap (см. «Стриминг и кэш»); web резолвит `null` и сохраняет прежнее поведение.

Для пауза → play (toggle-play и web media-session) частично пробуферизированная (не сохранённая целиком) проповедь разрешена офлайн — слушатель дослушивает буферизованную часть; когда буфер исчерпывается, срабатывает штатная обработка столла.

Guard покрывает все пути старта воспроизведения:

1. **Тап на трек** — `usePlayNewSermon` (`usePlaySermon.ts`) вызывает guard перед любыми мутациями состояния (до `setCurrentAudio`/`setCurrentPlaylist`/`replaceAudio`/`play`/открытия полноэкранного плеера): при блокировке `currentAudio`/`currentPlaylist` не задаются, `replaceAudio`/`play` не вызываются, полноэкранный плеер не открывается.
2. **Toggle-play (пауза → play)** — единый хук `useGuardedTogglePlay` (`src/entities/player/lib/useGuardedTogglePlay.ts`) вызывает guard при переходе пауза → play (когда `currentAudio.audioUrl` существует): при блокировке `play()` не вызывается, плеер остаётся на паузе, диалог уже показан guard'ом. Пауза (play → pause) guard'ом **не** блокируется — пауза работает всегда. Хук используется всеми play/pause-кнопками: полноэкранный плеер (`useFullscreenHandlers`), мини-плеер (`ExpandablePlayer`) и кнопка play в `PlayerControls`.
3. **Next/Prev переключение трека** — `usePlayerToggleTrack` вызывает guard перед `executeTrackSwitch` (когда у целевого трека есть `audioUrl`): при блокировке переключение не происходит, wrap-уведомление не показывается.
4. **Web media-session play** — play-хендлер `webMediaSession.ts` вызывает guard при паузе (когда `currentAudio.audioUrl` существует): при блокировке `play()` не вызывается.
5. **Нативный авто-переход** — JS pre-guard невозможен: очередь переключает движок без участия JS, и «заблокировать» переход до его начала нечем. Офлайн + следующий трек не закэширован → нативная ошибка/столл → `reportPlaybackError` (`reportError` + `isStalledOfflineAtom` при офлайне) и пауза; после возврата сети reconnect-heal перепривязывает источник. Поэтому guard остаётся только на JS-путях старта (пп. 1–4): ручные Next/Prev по-прежнему гейтятся до `replaceAudio`. Generic-ошибка «Ошибка при автоматическом переходе к следующей проповеди» относится теперь к сбоям reconciliation в `handleTrackChanged` (нативные переключения уже состоялись).

Стриминг работает благодаря HTTP range requests (MinIO отдаёт `206 Partial Content`, `Accept-Ranges: bytes`). Раньше `downloadFirst: true` блокировал воспроизведение до полного скачивания файла в tmp-каталог.

## Инициализация

`initializePlayer` (`src/entities/player/lib/initializePlayer.ts`) вызывается модульно в `app/_layout.tsx` (`void initializePlayer()`). Восстанавливает из AsyncStorage (`multiGet` + Zod-парсинг через `getParseJsonWithSchema`): последний аудио/плейлист, позицию, громкость, скорость воспроизведения, режим повтора. Затем собирает нативную очередь (`playerService.loadAudio(audioUrl, position)`) и ставит метаданные lock screen. Скорость и громкость восстанавливаются до `loadAudio` — `playbackPreferences` сохраняет значения, а `applyPreferences` внутри `loadQueue` применяет их к свежей очереди (новый нативный экземпляр всегда стартует с rate 1.0 / volume 1). Режим повтора `queueContext` читает из `CURRENT_REPEAT_MODE` при сборке — повтор восстанавливается вместе с очередью, не отдельным вызовом. Настройки звука (баланс, эквалайзер, pitch) восстанавливает `restoreAudioSettings` (`lib/restoreAudioSettings.ts`, zod-схемы ключей из [storage.md](../contracts/storage.md)): значения пишутся только в preferences-синглтон и атомы, нативные эффекты при старте не трогаются — их к живой очереди пере-присоединит первый `loadQueue` (см. «Настройки звука»).

**Симметрия save/restore.** Запись `CURRENT_AUDIO` идёт только через `setCurrentAudioAction`, который нормализует форму перед `JSON.stringify` (`lib/persistedAudio.ts`): отсутствующий `artwork` превращается в `null` (ключ обязан присутствовать — схема объявляет `artwork: z.string().nullable()`, иначе `undefined` выпал бы из JSON и уронил весь парс), а вложенный `playlists` проецируется в лёгкие рефы `{ artwork, id, title, sermons: [] }` — членства проповеди нужны UI (например, выбор «Где продолжить» после удаления играющей проповеди), но очередь проповедей и вложенные структуры в записи не хранятся, поэтому размер не растёт, а zod-парс не падает на тяжёлой форме. Запись плейлиста идёт только через `setCurrentPlaylistAction`, который нормализует форму через `lib/persistedPlaylist.ts`: `artwork` плейлиста и `artwork` каждой вложенной проповеди превращаются в `null`, если отсутствуют/`null` (обе формы требуют присутствия ключа — `artwork: z.string().nullable()` у плейлиста и `isSermonShape` у проповеди), так что сохранённая форма всегда валидна без опоры на конвенцию мапперов. API→домен мапперы (`mapSermonEntityToSermonData`, `mapPlaylistEntityToPlaylistData`, `mapSectionPlaylistToPlaylistData`, `mapPlaylistSermonToSermonShape`) по-прежнему нормализуют `artwork ?? null` и `description ?? undefined` на границе. При невалидном сохранённом JSON парсер логирует `console.warn` с zod-issues (`lib/playerStorageParsers.ts`); парс-мисматч не считается крашем.

**Изоляция стартовой цепочки.** В `app/_layout.tsx` шаги инициализации изолированы `catch`: падение гидратации офлайн-реестра или загрузки настройки кэша логируется, но не прерывает восстановление плеера (раньше отказ любого `.then` молча пропускал `initializePlayer`); терминальный `.catch` репортит оставшуюся ошибку через `reportError`.

## Восстановление после сбоя

Полный teardown остался только в двух точках — `unload` и пересборка очереди:

- **`unload`** (`playerService.unload()`): снимает флаг `statusMuted` (статус-события после stop/unload не должны срабатывать как ребро прерывания), `audioEffectsAttach.detach()` → `playlistEngine.destroy()` (снятие подписок `playlistStatusUpdate`/`trackChanged` + `destroy()` нативной очереди). Lock screen **не** деактивируется перед teardown: `destroy()` при ещё активной сессии удаляет уведомление нативно и надёжно, а предварительный `setActiveForLockScreen(false)` может молча не сработать, пока сервис binder в состоянии BINDING, и оставить осиротевшее уведомление (дубли — см. «Смена трека: нативная очередь и подмена источника»).
- **Пересборка очереди** (`buildQueue` в `loadAudio`/one-track fallback): старая очередь освобождается, её lock-screen состояние очищается (`lockScreenControls.clear(previous)`), затем создаётся новая. Это единственный путь, где сессия действительно пересоздаётся; смена трека внутри очереди teardown'а не делает.

**`resetPlaybackAction`** (`src/entities/player/resetPlayback.ts`, экспорт из `entities/player`) — полное закрытие плеера из UI: вызывает `playerService.unload()` (нотификейшн-бар убирается нативно; ошибка `unload` логируется, но UI всё равно закрывается), удаляет `CURRENT_AUDIO`/`CURRENT_PLAYLIST`/`CURRENT_SOUND_POSITION` (после этого холодный старт их не восстановит) и сбрасывает состояния — `currentAudioAtom`/`currentPlaylistAtom` в `null`, `isPlayingAtom`/`isBufferingAtom` в `false`, `positionAtom`/`durationAtom` в `0`. Сброс забывает текущую проповедь полностью: если она была загружена, удаляется и её запись в истории прослушивания (через `@x/player`-точку вызывается `removeHistoryEntryAction`) — удалённая проповедь больше не предлагается для продолжения. Флеш-воссоздание невозможно: снятие `currentAudioAtom` останавливает 10с-флаш прогресса, а удалённая запись защищена «тамбстоуном» (`entities/listening-history/model/forgottenSermons.ts`) — возможный in-flight flush её не воскресит. Сброс также сворачивает полноэкранный плеер (`isPlayerExpandedAtom` → `false`), поэтому развёрнутое состояние не переживает закрытие и следующий запуск не открывает плеер сразу на полный экран. Миниплеер и полноэкранный плеер скрываются, очередь пустеет. Используется при очистке плейлиста и при удалении играющей проповеди из её плейлиста — во втором случае сброс живёт в `togglePlaylistSermon` (`entities/playlist`), единственной точке мутации принадлежности, поэтому срабатывает на **любой** поверхности удаления (меню строки, меню плеера, снятие галочки в модалке «Добавить в плейлист»), а не только в UI-подтверждениях.

**Удаление играющей проповеди — выбор плейлиста для продолжения.** Если удаляется проповедь, которая сейчас играет из этого плейлиста, поверхности удаления (меню строки экрана плейлиста и меню полноэкранного плеера) не закрывают плеер сразу: `togglePlaylistSermon` вызывается с опцией `{ suppressPlayerReset: true }` (встроенный сброс подавлен), после чего фича `features/continue-playback` предлагает выбрать, где продолжить. Кандидаты — серверные плейлисты, где проповедь есть (`sermon.playlists`; сохраняются при персистенции/в снапшотах лёгкими рефами `{ artwork, id, title, sermons: [] }`, поэтому доступны и после холодного старта), и локальные из `myPlaylistsAtom`, у которых её id в `sermonIds`, кроме исходного плейлиста (дедуп по id). Если локальных членств у проповеди нет (старые снапшоты/хранилище) и её id — UUID, членства уточняются сервером (`fetchSermonPlaylists`: `GET /sermons/{id}` → `PlaylistEntity.playlists` мапятся в `PlaylistData`; ошибка — пустой список). Если кандидатов нет — плеер закрывается сразу (`resetPlaybackAction`). Выбор плейлиста (`useContinuePlayback.pick`) продолжает воспроизведение (`usePlayNewSermon`) без остановки, а запись истории синхронизируется по текущей позиции/длительности (`flushHistoryProgressAction` с выбранным плейлистом). Кандидат может быть лёгким рефом (`sermons: []`): при выборе он разворачивается до полного плейлиста (`resolveFullPlaylist`: загруженные секции → кеш секций → API для UUID → сам лёгкий реф как фолбэк), чтобы очередь и автопереход работали. «Закрыть плеер» и тап по фону закрывают плеер (`resetPlaybackAction`). Опция `suppressPlayerReset` по умолчанию выключена — без неё `togglePlaylistSermon` закрывает плеер, как раньше.

Upstream-причины:

- `expo/expo#46137` — сервис не вызывал `startForeground` после рестарта ОС, foreground-service падал; полный release в `unload` пересоздаёт нативный контекст при следующем `loadAudio`, восстанавливая работоспособность.
- `expo/expo#46957` — на Android 15+ нельзя запросить audio focus из фона (`Activity` недоступна); смена трека внутри нативной очереди не бросает и не перезапрашивает фокус из фона вовсе (митигация сильнее прежнего release-before-recreate).
- `androidx/media#1928` — застрявший audio focus чистится только ребутом; наш release в `unload` — митигация, полная очистка может требовать перезагрузки ОС.

### Crash-guard при старте (Issue #45)

Нативный краш ExoPlayer/MediaSession при восстановлении плеера JS try-catch не ловит — процесс умирает целиком. Чтобы разорвать crash loop после обновления, `initializePlayer` ведёт счётчик попыток запуска в AsyncStorage (`PLAYER_STARTUP_ATTEMPTS`, `src/entities/player/lib/startupGuard.ts`):

- счётчик читается **первым делом**, до любых нативных вызовов;
- при значении **>= 3** восстановление пропускается целиком: `loadAudio`/`setLockScreenMetadata` не вызываются, атомы остаются пустыми, счётчик сбрасывается в 0, приложение стартует нормально (пользователь может запустить проповедь вручную — `loadAudio`/`replaceAudio` сами сконфигурируют аудио-режим);
- иначе счётчик инкрементируется, и запись **await-ится до** нативных вызовов — если процесс упадёт, следующий запуск увидит увеличенный счётчик;
- **успешное восстановление сбрасывает счётчик в 0** (даже частичное: нет сохранённого трека или трек не прошёл валидацию — процесс жив, значит это не краш). Счётчик остаётся инкрементированным только если восстановление бросило исключение (его ловит `initializePlayer`), поэтому порог == 3 означает три **подряд неудачных** старта, а не три обычных открытия приложения;
- **ручной старт воспроизведения** (`playNewSermonAsync`) тоже сбрасывает счётчик — застрявший guard (пропуск восстановления) разлипается после первого ручного запуска проповеди, и следующий cold start снова восстанавливает состояние;
- парс-мисматч (zod-отказ) крашем **не** считается и счётчик не накапливает;
- при здоровом аптайме 30с `scheduleStartupGuardReset` (вызывается один раз в `app/_layout.tsx`, защита от повторного планирования) сбрасывает счётчик в 0.

Пропуск восстановления **не удаляет** данные: `listeningHistory`, `listeningProgressSnapshot`, аудио-кэш и содержимое `CURRENT_AUDIO`/`CURRENT_PLAYLIST` остаются нетронутыми.

  **Снапы:** `['70%', windowHeight − topInset]` (геометрия — общий хук `lib/useSheetSnapMetrics.ts`: детенты и `FINAL_SNAP_INDEX = 0` заданы в одном месте; шторка плейлиста оборачивает его в `ui/PlaylistBottomSheet/useQueueSheetSnapMetrics.ts`, шторка настроек звука использует `useSheetSnapMetrics` напрямую). `FINAL_SNAP_INDEX = 0` — шторка открывается на 70% (первый снап); свайп вверх по handle разворачивает на полную высоту минус статус-бар. `useQueueSheetSnapMetrics` отдаёт **реактивную метрику `sheetTop`** (позиция верха шторки в screen-координатах per-snap: `0.3·windowHeight` на 70%-снапе, `topInset` на полном) — она прокидывается вниз по цепочке пропов (`PlaylistBottomSheet → PlaylistSheetContent → PlaylistSheetList → useScrollGuarantee`) и пересчитывает геометрию футера/маски при смене снапа. Это заменило прежний `hiddenBelowSheetEdge` (см. ниже).

  **Гарантия скролла (Issue #69, follow-up):** хук `useScrollGuarantee` (`ui/PlaylistBottomSheet/useScrollGuarantee.ts`) — динамический `ListFooterComponent` (spacer, `pointerEvents: none`) + **frame-bounding** через `maxHeight` на обёртке списка. Чистая математика вынесена в `scrollGuaranteeMath.ts` (`computeFooterHeight`, `computeBelowScreenOffset`, `computeMaxListHeight`, `MIN_GUARANTEE = 84`).

  **Frame-bounding (главный механизм follow-up):** `maxListHeight = max(0, windowHeight − sheetTop − chromeOffset)` ограничивает высоту `listWrapper` (View-обёртки списка). `chromeOffset` — измеренное через `measureInWindow` расстояние от верха экрана до верха обёртки (= gorhom handle + заголовок + паддинги контейнера); измеряется **только при settle** (`settleTick`-плюмбинг: `useSheetLifecycle.onSheetSettled → state → List`), потому что позиция шторки финальна лишь после завершения snap-анимации — замер mid-animation дал бы транзиентный `y`. Инвариант: `wrapper_bottom = sheetTop + chromeOffset + maxHeight = windowHeight` — низ обёртки совпадает с низом экрана **на любом снапе, на любом устройстве**. Никаких жёстких размеров — всё либо измеряется (`measureInWindow`, `onLayout`), либо берётся из системных API (`useWindowDimensions`, `useSafeAreaInsets`).

  **Итоговая формула футера (three-term max):** `footer = max(84, ceil(frame − raw + 84 + belowScreen), ceil(belowScreen) + 84)`, где `belowScreen = chromeOffset === null ? 0 : max(0, sheetTop + chromeOffset + frameHeight − windowHeight)` — safety-net: если `maxHeight`-стиль по какой-то причине не применился (например, в первом цикле измерений до резолва `chromeOffset`), футер всё равно компенсирует и гарантирует очистку края. Минимальная гарантия `84px` (одна строка) — короткие списки всегда могут начать drag. `raw` (высота контента без футера) инвариантна к изменению футера, поэтому вычисление сходится к неподвижной точке без осцилляции.

  **Прокрутка к текущей проповеди:** при открытии шторка **автоматически прокручивается к текущей проповеди** (она встаёт в верх списка, `viewPosition: 0`). Механизм — хук `useScrollToCurrentTrack` (`ui/PlaylistBottomSheet/useScrollToCurrentTrack.ts`). Скролл выполняется один раз за монт при оседании на первом снапе.

  **Settle-путь (follow-up):** `useSheetLifecycle` вызывает `scrollToCurrent() + noteScrollScheduled()` для `FINAL_SNAP_INDEX` **и в `handleAnimate`, и в `handleSheetChanges`** (идемпотентно). **ВАЖНЫЙ урок:** gorhom **НЕ вызывает `onAnimate` для mount-open анимации** (guard `BottomSheet.tsx:484` — mount оценивается на UI-thread без колбэка, подтверждено на устройстве) — поэтому `onChange` — единственный надёжный settle-сигнал для автоскролла и активации reveal-потолка. `onSheetSettled` (для `index ≥ 0`) — источник `settleTick` для замера `chromeOffset`.

  **Ревел-гейт:** хук `useListReveal` (`ui/PlaylistBottomSheet/useListReveal.ts`). **Ближний верх (~≤240px, `isOffsetNegligible`)** — цель уже видна при открытии: ни скролла, ни скелетона, список сразу. **Дальние цели** — список скрыт (`hiddenContent`, `opacity: 0`), поверх — пульсирующий скелетон (`TracksListSkeleton` из `entities/track-list`, 8 строк, геометрия совпадает с реальными строками `TRACK_LIST_ITEM_SIZES`; пульс opacity 0.5↔1, ~700ms, per-row). Reveal происходит **только после сходимости автоскролла**: реальный offset должен попасть в ±160px (`REVEAL_CONVERGENCE_TOLERANCE_PX`) от целевого (`intendedOffsetRef`) **и** в планировщике не должно быть отложенных ретраев (`scrollScheduler.hasPending()`). Любой фолбэк-прыжок и каждый backoff-ретрай (страховочная цепочка) остаются скрытыми за скелетоном до стабильной посадки (фикс видимых 3–4 прыжков при открытии). Потолок 1500ms (`REVEAL_CEILING_MS`) форс-ревелит даже без scroll-эха; тач пользователя (drag/momentum start) ревелит мгновенно (`revealNow`).

  **Скролл:** двойной rAF-надж после оседания шторки → `scrollToIndex({ index, viewPosition: 0 })`. Список задаёт `getItemLayout` с точными метриками строки (74px + разделитель 17px = шаг 91; у последней строки разделителя нет — `FlatList` его не рендерит), поэтому первый же вызов попадает в цель — без оценки `avg × index` и без цепочки повторных `scrollToIndex`, которые раньше давали видимые прыжки. Фолбэк `onScrollToIndexFailed` (оценка `scrollToOffset` + до 6 повторных `scrollToIndex` с линейным бэкоффом 100×n) сохранён как **спящая страховка**: на точных метриках он не срабатывает. Скелетон по-прежнему закрывает маску до прихода точного скролла. Таймеры автоскролла гейтятся на текущий снап и momentum-флинг пользователя в момент срабатывания. **Перф:** шторка мемоизирована (`memo`) со стабильным `onClose` (`useCallback` в `FullscreenContent`) — нет шторма ре-рендеров на тики позиции; `INITIAL_NUM_TO_RENDER = 10` (плоский, без раздувания до цели — сходимость спрятана за скелетоном); `onScroll` отключается после reveal (`isRevealed ? undefined : onScroll`). **Перф строк (follow-up):** `useSheetMenuActions` кэширует actions по id (`actionsCache`, пересоздаётся при смене зависимостей) — unrelated-ре-рендеры (cacheTrigger, чужие прогрессы) не пересоздают `menuActions`; прогресс строки читается узкой подпиской `useHistoryProgress(id)` (`entities/listening-history`, Object.is-bailout) вместо пропа `progressMap` — строка ре-рендерится только когда меняется её собственный прогресс.

  **Render-storm урок (follow-up):** DEV-диагностика с `setState` на каждое scroll-событие (throttle 16ms) замораживала JS на секунды при открытии больших плейлистов (VirtualizedList warning dt 2712ms). Диагностика полностью удалена (badge/hook/`enableLogging` — grep zero). **Урок: никогда не `setState` в `onScroll` без троттлинга** — даже с throttle 16ms на больших списках это убивает JS-поток.

  **История Issue #48 (gorhom patch-package):** gorhom 5.2.14 определяет состояние EXTENDED точным равенством `animatedPosition.value === containerHeight - animatedSheetHeight.value` (`BottomSheet.tsx` ~L308); при дробном PixelRatio позиция пружины и измеренная высота расходятся на доли пикселя → `===` никогда не истинно → вложенный список остаётся LOCKED и откатывает программные скроллы в 0 (`useScrollable.ts:41-76`, линия issues #2737). **Фикс — патч через `patch-package`** (см. [decisions.md](../decisions.md) → patch-package): точное равенство заменено на epsilon `Math.abs(...) < 0.5` в трёх местах (EXTENDED, EXTENDED-with-keyboard, FILL_PARENT). **Патч УДАЛЁН (в ветке фикса #69):** с `enableContentPanningGesture={false}` unlock вложенного списка безусловен, поэтому epsilon-патч потерял поведенческого потребителя (PlaylistBottomSheet — единственный потребитель `@gorhom/bottom-sheet` в `src/`, проверено grep'ом). Версия распинена `5.2.14` → `^5.2.14`, node_modules возвращён к upstream (`===`-сравнения восстановлены).   ### Мёртвый скролл на коротких плейлистах (Issue #69)

  **Симптом (оригинальный репорт):** «Не работает разворачивание боттомшита если проповедей не сильно много». Уточнено: мёртвый скролл + закрытие шторки по флику на коротких плейлистах. На длинных плейлистах не воспроизводилось.

  **Корневая причина (подтверждена на устройстве):** gorhom размеряет frame вложенного FlatList по **максимальному** снапу (`windowHeight − topInset`), константно независимо от текущего снапа. При коротких плейлистах высота контента ≤ frame → Android ScrollView физически не может начать drag (нет избытка контента) → ноль scroll-событий → ничего не перехватывает касание → row Pressable'ы забирают тап → быстрые флики срабатывают как `onPress` при подъёме пальца → `handlePressItem` императивно закрывает шторку (Metro: `ANIMATION_SOURCE.USER`). Трек часто не менялся: `scrollToCurrent` (viewPosition 0) ставит текущий трек вверх списка, где начинаются флики → `playNewSermon` перезапускает тот же трек. Длинные плейлисты не воспроизводили (frame < content → ScrollView забирает касания).

  **Ключевая механика gorhom:** gorhom определяет Scrollable-статус (LOCKED/unlocked) через `useScrollable`. При `enableContentPanningGesture={false}` gorhom **безусловно** разблокирует скроллящийся компонент — но это не решало проблему на Android: ScrollView с content ≤ frame не может начать drag независимо от lock-статуса gorhom (нативное ограничение Android `ScrollView`).

  **Дополнительно (Reveal-гейт):** старый порог `y > 100px` был недостижим для коротких плейлистов, чей максимальный скролл < 100px (≈1 строка ~73px) — скелетон не исчезал до потолка 1500ms (`REVEAL_CEILING_MS`). Исправлено: порог `y > 0`.

### Архитектура рендера ExpandablePlayer (Issue #100)

До Issue #100 `ContainerView` рендерил `<FullscreenContent />` **безусловно**: при свёрнутом плеере невидимое полноэкранное поддерево оставалось смонтированным и ре-рендерилось на каждый тик `positionAtom` (~1–2 раза/сек) и на каждый тик `downloadProgressAtom` — корневая причина статтера при скролле Home во время фоновой закачки. Фикс — три уровня:

1. **Mount-гейт полноэкранного контента** (`model/useFullscreenContentMount.ts`): `ContainerView` монтирует `FullscreenContent` только при развороте; при сворачивании поддерево остаётся смонтированным на время collapse-анимации и размонтируется через `COLLAPSE_DURATION_MS = 250`. Повторный разворот в этом окне отменяет отложенный размонт; возврат из фона (AppState `active`) снапит флаг к развёрнутому состоянию (паритет с `useAppStateSnap`). Тайминги анимаций вынесены в единый источник `model/expandDurations.ts` (`EXPAND_DURATION_MS = 300`, `COLLAPSE_DURATION_MS = 250`) — раньше были захардкожены в `useExpandAnimation.ts`; эффект анимации прогресса вынесен в `model/useProgressAnimation.ts`.

2. **Прогресс скачивания — в листовых компонентах** (`model/useDownloadProgressForUrl.ts`): гейт-хук `useDownloadProgressForUrl(audioUrl)` возвращает `downloadProgress` только если `isDownloading && downloadingAudioUrl === audioUrl`, иначе `0`. Мини-плеер рендерит `MiniDownloadProgress`, полноэкранный — `FullscreenDownloadProgressBar` (обёртка над чистым `PlayerProgressBar` из entities). Контейнер `ExpandablePlayer` **не подписан** ни на один downloader-атом; `useFullscreenHandlers` держит только `isDownloadingAtom`/`downloadingAudioUrlAtom` (визуальное состояние кэш-меню) и не читает `downloadProgressAtom` — на тики закачки ре-рендерятся только листья.

3. **Намеренное изменение поведения:** оверлей «Подробнее» вынесен в атом `showDetailsAtom` и **явно сбрасывается** при сворачивании плеера: `handleCollapsePress` (`FullscreenContent.tsx`) сначала закрывает оверлей, если он открыт, и всегда сбрасывает флаг при сворачивании (инвариант — после сворачивания `showDetailsAtom === false`); на Android аппаратный back закрывает его отдельным шагом каскада (`app/_RootLayout.tsx`) первым — до шторки плейлиста и меню, а на web — `Escape` через тот же `handleCollapsePress`. Атом-бэкенд состояние (например, `showPlaylist` через `showPlaylistAtom`) персистит между сворачиваниями/разворачиваниями. Ранее `showDetails` было компонент-локальным состоянием, которое сбрасывалось только при ремоунте `FullscreenContent` (после полного истечения 250мс collapse-окна) — это давало регрессию: при повторном разворачивании оверлей «Подробнее» появлялся снова.

- **Marquee-компоненты мемоизированы (follow-up):** `MarqueeText` (`shared/ui/marquee-text`) и обёртка `MovingText` обёрнуты в `memo`; pan-жест строится через `useMemo` по стабильным shared values и `useCallback`-стабильному `startIdleMarquee`, а колбэк `useFrameCallback` — `useCallback([])`. Тики позиции аудио (~2/с) больше не пересоздают жест/RNGH-конфигурацию и не пере-регистрируют нативный frame-clock — корневая причина микро-статтера бегущей строки в полноэкранном плеере. Сглаживанию плавности также помогает Android fast-path флаг Reanimated (`ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS`) — см. [`../decisions.md`](../decisions.md) → «Reanimated / Worklets static feature flags».

### Восстановление после фона (Issue #61)

**Симптом:** на Android, если пользователь слушает проповедь, ставит паузу и уходит из приложения на длительное время (минуты/часы), при возврате мини-плеер показывает пустой серый прямоугольник (цвет `surface` в тёмной теме) вместо обложки и контролов; касания на этом прямоугольнике ничего не делают. Остальная часть приложения работает. Перезапуск приложения исправляет.

**Корневая причина:** виджет `widgets/expandable-player` всегда рендерит полноэкранный `Animated.View`-контейнер (zIndex 200) с оверлеем `miniOverlay` цвета `surface` — при свёрнутом плеере этот контейнер позиционируется точно под мини-плеером и закрывает его, когда мини-плеер пропадает. Видимость мини-плеера управляется анимацией `miniStyle` через shared value `progress` Reanimated: `opacity = interpolate(progress, [0, 0.3], [1, 0])`. После долгого фона UI-thread Reanimated может рассинхронизироваться — shared value `progress` оказывается застрявшим выше 0.3, miniPlayer получает `opacity: 0`, а оверлей surface-цвета показывается вместо него. Обработки AppState в виджете не было — ничего не восстанавливало значение `progress` и не пересоздавало нативные view (жесты, изображения, текстовые бегунки могли также оказаться в stale-состоянии, объясняя «мёртвые» касания).

**Фикс (два уровня защиты, виджет selbstständig):**

1. **Снап `progress` при каждом возврате в active** (`model/useAppStateSnap.ts`, вызывается из `useExpandAnimation.ts`): подписка на AppState, при `nextAppState === 'active'` — прямое присваивание `progress.value = expanded ? 1 : 0` (без `withTiming`). Прямое присваивание отменяет любую in-flight анимацию и фиксирует значение на UI-thread.

2. **Remount поддерева по ключу** (`ui/ExpandablePlayer/ExpandablePlayer.tsx`): хук `useBackgroundRecovery` (`model/useBackgroundRecovery.ts`) отслеживает AppState и возвращает счётчик; при возврате из фона дольше 5 минут счётчик инкрементируется. Обёртка `View` с `key={recoveryKey}` и стилем `styles.recoveryOverlay` (`{ ...StyleSheet.absoluteFill, pointerEvents: 'box-none' }` из `commonStyles.ts`) оборачивает всё содержимое виджета — смена ключа полностью перемонтирует поддерево (свежие нативные view для жестов, изображений, анимаций, бегущего текста; shared values перепривязываются). `pointerEvents: 'box-none'` гарантирует, что обёртка не перехватывает касания, предназначенные экранам табов. **`box-none` обязан жить внутри `StyleSheet.create`, а не в инлайн-стиле:** на web RNW полифилит не-CSS-значения `box-none`/`box-only` только при компиляции стиля в классы; инлайн `style.pointerEvents:'box-none'` даёт невалидный CSS `pointer-events: box-none`, браузер его отбрасывает → обёртка становится `pointer-events: auto` и глотает все касания страницы под плеером (см. `docs/features/web.md` → «pointerEvents на web»).

### Расползание мини-плеера при обновлении (Issue #63) — ИСПРАВЛЕНО, ПОДТВЕРЖДЕНО НА УСТРОЙСТВЕ

**Симптом:** после обновления приложения (новый build) на Android верх мини-плеера (60px статичный бар, `MiniPlayer`, zIndex 300) стоит **правильно**, но нижняя часть surface-цветного контейнера-подложки (zIndex 200, `ExpandablePlayer.tsx`) растягивается вниз поверх иконок таб-бара — должна перекрывать только на 4px (`MINI_PLAYER_TAB_OVERLAP`). Любое взаимодействие (тап/пан на плеере) исправляет.

**Статус:** фикс подтверждён на реальном устройстве (Android). TEMP(#63) телеметрия (логгеры `issue63Log`, `logContainerApply`, `useIssue63Diagnostics`, `issue63Debug`) удалена после подтверждения стабильности.

**Корневая причина (рассинхронизация Reanimated UI-thread + ненадёжный канал обновления worklet-замыканий):**

1. `tabBarHeightAtom` стартует с приближения 78; реальное измерение `CustomTabBar` через `onLayout` приходит через 1–2 кадра. На Android измерение может быть **двухфазным**: `useSafeAreaInsets()` на первых кадрах может вернуть `bottom: 0` → BlurView с `paddingBottom: Math.max(bottom, 30)` растёт, когда реальные insets приходят → второй `onLayout` с **большей** высотой.

2. Когда атом обновляется после монта, Reanimated должен обновить замыкание worklet'а и повторно применить стиль на UI-thread. В загруженном окне старта повторное применение может быть **сброшено** — JS-сторона корректна (статичный мини-бар на правильной позиции), но нативный контейнер сохраняет устаревшую геометрию: `bottom` вычислен из **меньшего** устаревшего `tabBarHeight` → коробка свисает поверх табов на дельту высот.

3. Доказательство асимметрии каналов: запись `progress.value` (что делает пан-жест / любой тап) **всегда** перезапускает worklet'ы с актуальными замыканиями и восстанавливает layout. Shared-value writes — надёжный межпоточный канал; обновления через замыкание worklet'а — ненадёжный.

**Постоянная архитектура защиты (6 уровней):**

1. **Гейтинг по измеренной высоте таб-бара** (`ui/ExpandablePlayer/ExpandablePlayer.tsx`): атом `isTabBarMeasuredAtom` (начальное значение `false`) переключается в `true` при первом `setTabBarHeight` из `CustomTabBar`. Виджет рендерится (`return null`) до измерения реальной высоты, поэтому первый кадр использует точную геометрию вместо приближения 78.

2. **Прямое присваивание `progress` при первом монте** (`model/useExpandAnimation.ts`): на первом запуске эффекта `expanded` прямое присваивание `progress.value = expanded ? 1 : 0` (без `withTiming`) — форсирует shared value на UI-thread и перезапускает зависимые worklets. Последующие изменения `expanded` анимируются через `withTiming`.

3. **AppState snap** (`model/useAppStateSnap.ts`): при каждом возврате в active — прямое присваивание `progress.value = expanded ? 1 : 0` (отменяет застрявшие mid-animation значения).

4. **Геометрия через shared values вместо замыканий worklet'ов** (`model/useExpandAnimation.ts` + `model/useGeometrySharedValues.ts`): значения `miniBottom`, `screenWidth`, `fullScreenHeight` зеркалируются в `useSharedValue`-обёртки; `containerStyle` worklet читает `*.value` вместо значений из JS-замыкания. Синхронизация через `useEffect` → `.value = ...` — надёжный межпоточный канал.

5. **Статичная resting-геометрия через React shadow tree** (`lib/getRestingContainerStyle.ts`): контейнер получает **plain-стиль** (не анимированный) с корректной resting-геометрией. React shadow tree commits **никогда не сбрасываются** — в отличие от JS-триггерных Reanimated commits. Стилевой массив: `[styles.container, containerStyle, restingContainerStyle, style, {backgroundColor}]` — animated `containerStyle` переопределяет значения во время анимации; в покое оба слоя согласованы.

6. **Закрытый контур детекции и лечения** (`model/useContainerGeometryGuard.ts` + `model/useExpandAnimation.ts`): `useContainerGeometryGuard` — хук детекции (onLayout → сигнатура `y > expectedTop + 1dp` → окно 15с → кап 5) + `onMismatch` callback → `forceGeometryReapply` (запись в `geometryReapplyTick` shared value, alternating ±0.01dp — sub-pixel diff defeating no-diff skip, drift permanently bounded). Ожидание **всегда закреплено за СВЁРНУТОЙ геометрией** (`collapsedRestingContainerStyle.top`) — сигнатура бага (#63) существует только в мини-состоянии; при анимациях разворота/сворачивания y ≤ collapsedTop → ложных срабатываний нет по построению. Окно 15с отсчитывается от **аттача контейнера** (первый guarded onLayout), а не от маунта хука — покрывает поздний аттач (свежая установка: пользователь нажал play через 40с). `console.warn('playerGeometryHeal', …)` — fail-loud телеметрия последней линии; если warn появится в проде — сигнал рецидива, нужен лог. Тип `style`-пропа контейнера запрещает геометрические ключи (`NonGeometricStyle`) на уровне компилятора — last-wins в shadow tree не может быть нарушен внешним стилем.

**Кламп высоты и floor размеров на web** (`model/useExpandAnimation.ts`, `ui/ExpandablePlayer/ExpandablePlayer.tsx`): `fullScreenHeight = Math.min(Dimensions.get('screen').height, height из useWindowDimensions)`. На web `Dimensions.get('screen')` — это физический `window.screen.height`, выше вьюпорта; без клампа абсолютная геометрия плеера вылезала бы за документ и рождала вертикальный скроллбар. Backdrop получает `Math.floor(screenHeight)` / `Math.floor(screenWidth)` — дробные размеры окна давали 1px overflow документа и паразитные скроллбары. На нативе `window == screen`, поэтому кламп — no-op, но сглаживает транзиентное сжатие окна системной клавиатурой.

**Флип порядка стилей** (`ui/ExpandablePlayer/ContainerView.tsx`): `restingContainerStyle` после `containerStyle` — на уровне теневого дерева «последний побеждает», shadow всегда несёт корректную resting-геометрию, и любой релэйаут перезаписывает кадр правильными значениями.

## Управление

- **Play/Pause** — `PlayerControls` → `usePlayer().play/pause` (с защитой от AppState-ошибок `activity is no longer available`).
- **Next/Prev** — `usePlayerToggleTrack` по текущему плейлисту. Кнопки всегда активны при наличии аудио и не скрываются/не отключаются на границах плейлиста (Issue #67); long-press перемотка работает на любом треке. Семантика тапа зависит от режима повтора (`resolveTrackToggle`): **Off** — на границе показывается подсказка «Это первая/последняя проповедь» (`trackToggleNoticeAtom` → `BoundaryHint`), переключения нет; **Track** — тап в любом месте перезапускает текущую проповедь с начала (`seekTo(0)` + `play`) и показывает подсказку «Проповедь запущена заново»; **Queue** — next на последнем треке переходит к первому (подсказка «Это начало плейлиста»), prev на первом — к последнему (подсказка «Это конец плейлиста»), внутри плейлиста переключение без подсказки. Переключение через кнопки восстанавливает позицию из истории (`getResumePosition`), flush'ит позицию старого трека (`recordSermonSwitchAction`) и выполняется как `skipTo` в существующей нативной очереди (`replaceAudio` = skipTo + seekTo).
- **Перемотка** — `useSeekControls` + `PlayerProgressBar`; long-press кнопок ±10с. `useSeekControls` также отдаёт `tapSeek` — одиночный скачок ±10с (`TAP_SEEK_STEP_MS`, клампится к границам трека); к экранным кнопкам **не подключён** — используется краями экрана полноэкранного плеера (см. ниже) и клавиатурой web (см. ниже). Во время seek (`isSeekingAtom`) нативные `onPositionChange` не перезаписывают `positionAtom` (оптимистичная позиция); флаг снимается, когда нативная позиция подтвердила цель (`seekTargetPositionAtom`, допуск `SEEK_TARGET_CONFIRM_TOLERANCE_MS` = 500мс), иначе — safety-timeout `SEEK_SAFETY_TIMEOUT_MS` = 2с. База интервала long-press обновляется синхронно в `doSeek` (`useSeekControls`), а не только React-эффектом от пропа. При смене трека (`replaceAudio` → `replaceQueueTrack`) guard сбрасывается (`resetSeekGuard`): `isSeekingAtom` → false, `seekTargetPositionAtom` → null — иначе позиции нового трека игнорировались бы до подтверждения цели. Исключение — seek-swap (`swapSourceForSeek` → `swapCurrentSource`): guard взводится на время подмены источника, чтобы `currentTime≈0` нового источника не мигнул в `positionAtom` (см. «Seek при загруженном партиале»). При драге прогрессбара полноэкранного плеера (`PlayerProgressBar`) на каждую смену целой секунды preview-позиции срабатывает тактильный тик (`hapticTick`, `useSeekHandling.ts`) — тактильно чувствуется каждый шаг перемотки; на iOS это selection-тик (`selectionAsync`), на Android — `Context_Click` (`performAndroidHapticsAsync`, т.к. CLOCK_TICK неощутим на MIUI), на web — короткий импульс ~10 мс через Vibration API (`navigator.vibrate`) при наличии API, иначе тихий no-op. Тик подчиняется глобальной настройке «Виброотклик» в Настройках (`hapticsEnabledAtom` из `shared/model/settings`): выключение гасит и тик перемотки, и haptic-отклик кнопок. Метка прошедшего времени в `PlayerControlsSection` во время драга следует за preview-позицией (колбэк `onPreviewChange`, пробрасывается через `FullscreenDownloadProgressBar` из `PlayerProgressBar`/`useSeekHandling`) и по завершении драга возвращается к реальной позиции.
- **Repeat** — `PlayerRepeatToggle` (off/track/queue), меняет нативный loop очереди (`applyRepeatMode` → `mapRepeatMode`: Track → `'single'`, Queue → `'all'`, Off → `'none'`). В режиме `queue` ручное переключение кнопками Next/Prev заворачивает по циклу на границах плейлиста; в режиме `track` тап Next/Prev перезапускает текущую проповедь с начала (см. Next/Prev). Авто-повтор трека — нативный single-item loop без `trackChanged` (per-loop событий истории нет).
- **Скорость** — `PlayerSpeedMenu` в `ui/PlayerMenu/` (YouTube-style submenu: 0.75/1/1.25/1.5/2), атом `playbackRateAtom` через `usePlaybackRate` hook, ре-применение после сборки очереди (новый нативный экземпляр стартует с 1.0). Pitch-коррекция `'high'` (на iOS — spectral-алгоритм; чуть дороже по CPU, но сохраняет тембр речи). Ручная высота тона (pitch 0.5..2) — отдельный слайдер в шторке «Настройки звука» (см. ниже): смена скорости сбрасывает pitch нативно, и сохранённое значение ре-применяется автоматически.
- **Громкость** — `volumeAtom`/`setVolumeAction` + live-вариант `applyVolumeAction` (`useVolume`, `playbackPreferences.applyVolume`/`setVolume`); UI-слайдер живёт в шторке «Настройки звука» (`VolumeSection`; `PlayerVolumeBar` удалён 2026-09-10 — мёртвый, не рендерился).
- **Long-press ±10с** — через `onLongPressSeek`/`onPressOutSeek` в `PlayerControls`. Работает независимо от позиции в плейлисте (кнопки не отключаются на границах, Issue #67).
- **Края экрана (полноэкранный плеер, Issue #123)** — невидимые зоны вдоль левого/правого края средней области плеера (`PlayerEdgeSeekZones` → `EdgeSeekZone`, ширина 64dp; монтируются в `PlayerMiddleArea` вокруг spacer-Pressable, при открытом оверлее «Подробнее» исчезают вместе с ним). **Зажатие края** — непрерывная перемотка с ускорением (`startSeek`/`stopSeek`, тот же механизм, что у long-press кнопок next/prev). Зажатие обоих краёв одновременно безопасно: повторный `startSeek` сбрасывает предыдущий интервал (guard в `useSeekControls`), и первое отпускание останавливает перемотку. **Двойной тап по краю** — шаг ±10с (`tapSeek`): первый тап серии только взводит жест, каждый следующий быстрый тап в окно 300мс (`useEdgeTapSeek`, `EDGE_TAP_WINDOW_MS`; счётчики независимы по сторонам) добавляет ещё один шаг ±10с с тактильным тиком (`hapticLight`, подчиняется настройке «Виброотклик») — аккумуляция как в видеоплеере YouTube. Жесты — RNGH `Gesture.Exclusive(LongPress, Tap)` + `scheduleOnRN` (LongPress `.onStart` → `startSeek`, `.onFinalize` → `stopSeek`; Tap `.onEnd` → `handleEdgeTap`). Зоны — бонусная жестовая поверхность без визуала и a11y-семантики: вся функциональность доступна через прогрессбар и кнопки; на web работают мышью (удержание/клики) в дополнение к клавиатуре. **Онбординг:** полосы краёв — цели `player-fullscreen.edge-back`/`player-fullscreen.edge-forward` (обёртка `OnboardingTarget` лежит корнем `EdgeSeekZone` и сама несёт абсолютное позиционирование, чтобы не сломать раскладку); шаг «Края экрана» сценария `player-intro` подсвечивает обе (`areaTargetIds`) полупрозрачными заливками поверх живого интерфейса (см. [onboarding.md](./onboarding.md) → «Области подсветки»).
- **Клавиатура (web)** — `usePlayerKeyboardSeek` в полноэкранном плеере: `ArrowLeft`/`ArrowRight` — тап ±10с (`tapSeek`), удержание ≥ 500мс — long-press-перемотка с ускорением 5с→30с (как у экранных кнопок); OS auto-repeat (`event.repeat`) игнорируется — непрерывную перемотку ведёт hold-таймер; `Space` — play/pause (пропускается, если фокус на интерактивном элементе — кнопка активируется нативным Space, иначе было бы двойное срабатывание); `Escape` — сворачивание (при открытом оверлее «Подробнее» — сначала закрывает его, при открытой шторке плейлиста — сначала закрывает её). Только web + развёрнутый плеер. Подробнее — [web.md](./web.md) → «Плеер на web».

### Тапаемые таймкоды в описании

В оверлее «Подробнее» полноэкранного плеера таймкоды в тексте описания — интерактивные ссылки: тап перематывает текущий трек на указанную позицию (`usePlayer().seekTo`).

- Поддерживаемые форматы: `M:SS` и `H:MM:SS`. В форме `M:SS` минуты могут превышать 59 (до двух цифр, трактуются как суммарные минуты, например `75:30` валиден); ограничению 00–59 подчиняются только секунды, а в форме `H:MM:SS` — минуты и секунды в среднем и последнем сегментах. Поэтому `1:75` и похожие числа остаются обычным текстом.
- Парсер — `src/shared/lib/player/parseTimecode.ts`: `parseTimecodeSegments` делит описание на текстовые и таймкод-сегменты, `timecodeToMs` конвертирует валидный таймкод в миллисекунды; из barrel `shared/lib/player` экспортируется только `parseTimecodeSegments` (остальное — внутренние детали модуля).
- Рендер — `DescriptionWithTimecodes` (`src/widgets/expandable-player/ui/FullscreenContent/DescriptionWithTimecodes.tsx`): вложенные `<Text>` с `onPress`, `accessibilityRole='link'`, акцентный цвет `COLORS.primary` и подчёркивание; для скринридера ссылка имеет `accessibilityLabel` «Перейти к ${таймкод}» (например, «Перейти к 5:00»).
- Ошибка `seekTo` (например, трек не загружен) перехватывается, логируется в `console.error` и показывается пользователю через `reportError` — косметическая фича не роняет плеер.

### Виброотклик

Чекбокс «Виброотклик» в Настройках (`hapticsEnabledAtom` из `shared/model/settings`) гейтит **только** app-level виброотклик — вибрацию кнопок и интерактивных поверхностей и тик перемотки (`hapticTick` — тик на смене секунды при драге прогресс-бара), оба через `src/shared/lib/haptics.ts`. Кнопки вибрируют рано — через ~120 мс после касания (`usePressHaptic`); таймер отменяется на `pressOut`, если жест стал скроллом/свайпом, поэтому скролл остаётся без вибрации. Элементы с `onLongPress` ранний отклик пропускают и вибрируют на завершённом жесте: тап по `onPress`, меню по `onLongPress`. Тап по средней области полноэкранного плеера тоже даёт `hapticLight`, свайп-вниз сворачивает плеер без вибрации. Системную настройку виброотклика ОС учитывает сама: на Android `performAndroidHapticsAsync` → `View.performHapticFeedback` сверяется с системным флагом `HAPTIC_FEEDBACK_ENABLED`; на iOS UIKit-генераторы молча дропаются при выключенных System Haptics. Прочитать системное состояние из JS нельзя (в `expo-haptics` нет API; на iOS — невозможно by design), поэтому чекбокс в приложении **никогда не дизейблится** по этому признаку — решение зафиксировано 2026-09: нативный модуль детекции не добавляем.

## Настройки звука

Шторка «Настройки звука» (`src/widgets/expandable-player/ui/SoundSettingsBottomSheet/`) — управление эффектами воспроизведения поверх играющего трека: громкость, баланс Л/П, эквалайзер, высота тона и выбор устройства вывода. Открывается из контекстного меню полноэкранного плеера — активный пункт «Настройки звука» (`PlayerMenuItems`) на месте прежней заблокированной заглушки.

### Секции шторки

Секции рендерятся по флагам возможностей из `eqInfo` (`AudioEffectsInfo` — возвращается при attach: на Android нативным модулем, на web — статический снапшот веб-реализации; пишется в `audioEffectsInfoAtom`); громкость доступна всегда.

| Секция         | Управление                                                                                                              | Условие рендера                     |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| Громкость      | слайдер 0–100% (шаг 0.05) + кнопка «Сбросить» (100%)                                                                    | всегда                              |
| Баланс         | слайдер -1..1 (шаг 0.05, подписи «Левый»/«Правый») + сброс в центр                                                       | `eqInfo.balanceSupported` (API 28+) |
| Эквалайзер     | чекбокс вкл/выкл, пресеты-чипы «Ровно»/«Голос»/«Бас»/«Высокие», полосные слайдеры (дБ) по `eqInfo.bandCount` с подписями центральных частот | `eqInfo.eqSupported`                |
| Высота тона    | слайдер 0.5..2 (шаг 0.05) + сброс в 1                                                                                   | `eqInfo.pitchSupported`             |
| Источник звука | кнопка «Выбрать устройство вывода» (системная панель вывода)                                                             | `eqInfo.outputSwitcherSupported`    |

- Полосы эквалайзера: диапазон дБ берётся из `eqInfo.bandRange` (`bandLevelRange` устройства, значения клампятся на нативе), частоты — из `eqInfo.bandFrequencies` (центры полос в Гц). Количество полос — из `eqInfo.bandCount` (fallback 5): если на устройстве счётчик отличается от канонических 5, массив gains ресайзится (добивается нулями/обрезается) на границе apply в `audioEffectsPreferences`, а рендер нормализует длину (`EqualizerSection.normalizeGains`). Чип пресета подсвечен, только когда все полосы точно равны пресету (`findActivePreset`); ручной сдвиг любой полосы снимает подсветку. Выбор пресета применяет 5 значений по-полосно.
- Слайдеры работают в режиме **live-apply + persist-on-release** (паттерн live-preview): на каждый тик драга (`onChange` → `applyBalance`/`applyPitch`/`applyEqBandGain`/`applyVolume`) значение сразу уходит в аудиодвижок (на Android — main-queue вызов в нативный модуль, на web — узлы Web Audio графа; слышно мгновенно) и в атом (sync-экшены `applyBalanceAction`/`applyPitchAction`/`applyEqGainsAction`/`applyVolumeAction` — без AsyncStorage), так что звук меняется прямо во время драга, а UI (бегунок и заголовок секции) следует за атомом — локальные draft-хуки (`useDraftValue`/`useDraftGains`) удалены как избыточные. На отпускании (`onSlidingComplete` → `setBalance`/`setPitch`/`setEqBandGain`/`setVolume`) значение персистится в AsyncStorage (пользователь «фиксирует» понравившееся значение). Применение на каждый тик драга — дешёвое (запись в свойство аудио-узла), троттлинг не нужен.
- Кнопки «Сбросить» и чипы пресетов, чекбокс эквалайзера, accessibility-шаги слайдеров (increment/decrement) — мгновенный коммит (persist + apply) без фазы драга; значение в заголовке секции обновляется на лету из атома.

### Интеграция с виджетом

- **Атом открытия** — `showSoundSettingsAtom` (`widgets/expandable-player/model/showSoundSettingsAtom.ts`, экспорт из barrel виджета): ставится из пункта меню (`useFullscreenHandlers` → `FullscreenContent` → `PlayerControlsSection`), шторка рендерится условно в `FullscreenSheets` — одна entrance-анимация без двойного перехода (как у шторки плейлиста). ### Модуль `modules/audio-effects`

Локальный Expo-модуль: нативная часть — android-only (обоснование решения — [decisions.md](../decisions.md) → «Почему локальный модуль `modules/audio-effects`»). JS-обёртка разветвлена по платформам через расширения Metro (`index.ts` → `export * from './platform'`, Metro берёт `platform.native.ts` на Android/iOS и `platform.web.ts` на web; `platform.ts` — TypeScript-fallback в `index.native`):

- **`platform.native.ts` (Android/iOS):** `requireNativeModule('AudioEffects')` (резолвится один раз за запуск; на не-Android и при отсутствии модуля все функции деградируют в no-op); `attachAudioEffects(player, settings)` возвращает `AudioEffectsInfo`; `registerWebAudioElement` — no-op (нативной цепочке элемент не нужен).
- **`platform.web.ts` + `webEffectsGraph.ts` + `webCapabilities.ts` (web):** реализация эффектов через Web Audio API — граф на каждый `<audio>`-элемент `MediaElementAudioSourceNode → 5 × BiquadFilterNode ('peaking', 60/230/910/3600/14000 Гц) → StereoPannerNode → destination`. Граф строится **лениво** при первом вызове эффекта (это всегда user gesture — слайдер/чекбокс/пресет, так что `AudioContext` может стартануть не suspended) и кэшируется per-element в `WeakMap`: `createMediaElementSource` можно вызвать для элемента только один раз, и он навсегда перенаправляет звук элемента в граф. Хранимые настройки (баланс, вкл/выкл EQ, gains) применяются к графу при создании; выключенный EQ = все gains в 0 (цепочка всегда подключена, bypass без переподключения). Без `StereoPannerNode` (старый Safari) EQ-цепочка подключается прямо к destination — звук остаётся, деградирует только баланс. Без `AudioContext` (старые браузеры, jsdom) все эффекты — no-op. Pitch на web **не поддерживается** принципиально (Web Audio не меняет высоту `HTMLMediaElement`-потока независимо от скорости), `pitchSupported: false` — секция скрыта. `openAudioOutputSwitcher` — no-op, `outputSwitcherSupported: false`. Хук `registerWebAudioElement(element)` экспортируется на всех платформах (на нативе — no-op): `WebPlayerService.loadAudio`/`unload` зовут его при создании/сбросе элемента.

Kotlin-модуль `AudioEffectsModule` (`modules/audio-effects/android/src/main/java/ru/slovopropovedi/audioeffects/AudioEffectsModule.kt`):

- `attach(player, settings)` — suspend-`AsyncFunction` (перегрузка `AsyncFunction(name) Coroutine { ... }`, как в expo-audio `AudioModule`; явный параметр `Promise` в лямбде недопустим — в expo-modules-core 57 промис-перегрузки существуют только с `Promise` последним/единственным аргументом, иначе `Promise` трактуется как обычный аргумент и экспорт модуля падает с `MissingTypeConverter`): expo конвертирует аргументы (`AudioPlayer` — SharedRef, `AttachSettings` — Record), тело через `withContext(appContext.mainQueue.coroutineContext)` выполняет всю работу на main queue, потому что ExoPlayer живёт на main looper, а возвращённый capability-снапшот expo резолвит в JS-промис; остальные функции — fire-and-forget запуски, ошибки гасятся внутри queued-тел и никогда не бросаются в JS. Принимает expo-audio `AudioPlayer` (приходит как SharedRef; `player.ref` — нижележащий ExoPlayer) и `settings` (balance, eqEnabled, eqGains, pitch, **rate** — текущая скорость с JS-стороны). Пока `audioSessionId` не присвоен, эффекты не создаются — их пересоздаст `onAudioSessionIdChanged`. Эффекты: `android.media.audiofx.Equalizer` (полосы с устройства, практически 5; priority 0) и `DynamicsProcessing` — баланс через per-channel input gain (коэффициенты левого/правого каналов `1∓balance`, перевод в дБ; API 28+). Pitch — не аудио-эффект, а `PlaybackParameters(rate, pitch)` на самом ExoPlayer: скорость берётся из закэшированного `rate` (из `settings` и аргумента `setPitch`), **не** читается с плеера в момент применения — запись скорости expo-audio стоит в той же очереди, и чтение могло бы воскресить устаревшее значение. Сохранённые gains добиваются нулями/обрезаются до фактического `numberOfBands`.
- `Player.Listener.onAudioSessionIdChanged` — эффекты пересоздаются на новой аудио-сессии, пока жив тот же плеер (обновить capabilities в JS можно через `getInfo` — его вызывает `audioEffectsPreferences.applyToCurrentPlayer`).
- Каждый нативный вызов обёрнут в try-catch: недоступный эффект деградирует capability-флаг (`eqSupported`/`balanceSupported`/`pitchSupported`), но не роняет воспроизведение.
- `openOutputSwitcher` — системная панель вывода: `MediaRouter2.showSystemOutputSwitcher` на Android 14 (API 34)+, intent `android.settings.panel.action.MEDIA_OUTPUT` на Android 11 (API 30)+; на более старых версиях — no-op. Возможность отражена флагом `outputSwitcherSupported` (API 30+) в capability-info.
- **Жизненный цикл:** нативная очередь создаётся заново при пересборке (`loadQueue`), поэтому attach повторяется при каждой сборке: `PlaybackController.applyPreferences` (вызывается из `queueLoader.loadQueue`) последним шагом зовёт `audioEffectsPreferences.apply(player)` — attach с сохранёнными настройками и запись capabilities в `audioEffectsInfoAtom`. Полный detach — при пересборке очереди и в `unload` (`playlistQueueLifecycle`).
- **Порядок в `applyPreferences`:** скорость → громкость → attach последним. Применение скорости сбрасывает pitch нативно (expo-audio ставит `PlaybackParameters(rate, 1f)` в main queue), attach восстанавливает сохранённый pitch; тот же ре-примен выполняет `audioEffectsPreferences.applyPitch()` после каждой смены скорости (`PlaybackController.setPlaybackRate`) — native-вызовы становятся в main queue в порядке dispatch (FIFO), поэтому pitch-запись всегда выполняется после сброса скорости и побеждает.

### Сборка модуля: подводные камни

- **Stale-копия в `node_modules` (yarn 1 `file:`):** yarn 1 копирует локальную зависимость в `node_modules/audio-effects`, и обычный `yarn install` **не** перекопирует её, пока запись в `yarn.lock` не содержит integrity-хеша. После правок JS-обёртки модуля (`modules/audio-effects/index.ts` и др.) JS-потребители могут получить устаревший код — обновлять копию: `rm -rf node_modules/audio-effects && yarn install --check-files`. Для Android-сборки это сейчас безвредно: expo autolinking (SDK 58) резолвит gradle-проект `:audio-effects` обратно на `modules/audio-effects/android` (проверено `./gradlew :audio-effects:properties` → `projectDir`).
- **Нативный rebuild:** успешный `:audio-effects:compileDebugKotlin` **не означает**, что фикс попал в APK — APK пакует bundled runtime-jar модуля из `build/intermediates/runtime_library_classes_dir/`, и этот интермедиат может остаться stale при свежем kotlinc-выводе. Если на устройстве видно старое поведение после фикса — форс-регенерация интермедиата (`./gradlew :audio-effects:bundleLibRuntimeToJarDebug --rerun-tasks`) или полная чистка (`cd android && ./gradlew clean`), затем полный `yarn run:android`. Заодно убедиться, что в `node_modules/audio-effects` не осталась stale JS-копия (см. пункт выше).
- **Юнит-тесты чистой логики:** математика эффектов (`AudioEffectsMath` — баланс, линейный→дБ, millibels, resize gains, milliHz→Hz) вынесена из модуля и покрыта JVM-юнит-тестами (`modules/audio-effects/android/src/test/...`) — `yarn test:native` (см. [`../contracts/native-modules.md`](../contracts/native-modules.md) → «Unit-тесты нативного кода»).

### Возможности и ограничения

- **Web — поддерживаются** громкость (`HTMLMediaElement.volume`, сохранённая в `web/volumeControl.ts` и ре-применяемая к каждому свежему элементу), баланс и эквалайзер — через Web Audio API (лениво создаваемый граф `source → peaking×5 → StereoPanner → destination`, см. «Модуль `modules/audio-effects`» выше). Поскольку снапшот `eqInfo` на web приходит из статических флагов веб-реализации, все секции, кроме pitch и источника звука, на web рендерятся. Граф строится при первом действии пользователя с эффектами; **хранимые с прошлого сеанса** баланс/EQ применятся к графу только после первого действия с эффектами (до этого элемент играет необработанный звук — строить граф eagerly нельзя: `AudioContext` вне user gesture стартует suspended и заглушил бы перенаправленный в него звук элемента).
- **Web — не поддерживаются:** pitch (Web Audio не умеет менять высоту `HTMLMediaElement`-потока независимо от скорости — секция скрыта) и источник звука (нет браузерного API системной панели вывода — секция скрыта). Если аудио отдаётся с **кросс-доменного** источника без CORS-заголовков, перенаправление `<audio>` в Web Audio граф глушит звук — граф поэтому и строится только по явному действию пользователя с эффектами.
- **Баланс** — Android 9+ (API 28+, `DynamicsProcessing`); на более старых секция скрыта флагом.
- **Панель вывода** — системная панель только на Android 11+ (API 30+ intent, API 34+ MediaRouter2); секция рендерится только при `eqInfo.outputSwitcherSupported` (API 30+), на Android 10 и ниже строки нет.
- **Pitch и скорость независимы:** pitch меняет высоту без темпа, скорость — темп; смена скорости сбрасывает pitch, и он ре-применяется автоматически (см. выше).
- **Ошибки нативных вызовов гасятся** (`applyNative` try-catch в `audioEffectsPreferences`, `reportError` вокруг кнопки вывода): эффекты косметические и не должны ронять плеер.

### Общий UI-компонент слайдера

`src/shared/ui/value-slider/ValueSlider.tsx` — тематический слайдер для всех секций шторки: доступность через role `adjustable` + `accessibilityValue` + `accessibilityActions` (increment/decrement с шагом `step`) + hitSlop (без `testID`); tap-to-set и горизонтальный драг через PanResponder. ## Метаданные lock screen

`playerService.setLockScreenMetadata({ albumTitle, artist, artworkUrl, title })` → `LockScreenControls.setMetadata` → два пути:

- **Новая очередь** (первое воспроизведение / после `unload` / пересборка очереди): полный `player.setActiveForLockScreen(true, metadata, { isLiveStream: false, showSeekBackward, showSeekForward })` — активация MediaSession и foreground service; `showNextTrack`/`showPreviousTrack` не передаются (нативный дефолт `false`), поэтому на экране блокировки и в уведомлении остаются только seek ±10с (см. ниже). Если приложение не в foreground, активация **откладывается** (см. ниже).
- **Та же очередь** (смена трека): лёгкий `player.updateLockScreenMetadata(metadata)` — обновляет заголовок/артиста/обложку в существующем уведомлении без teardown-гонок.

**Метаданные — playlist-level.** У `AudioPlaylist` нет per-track API метаданных, поэтому при нативном переходе их обновляет координатор: `TrackAutoAdvanceService.handleTrackChanged` вызывает `lockScreenControls.setMetadata(...)` на каждый `trackChanged`, ручные Next/Prev делают то же в `executeTrackSwitch`.

**Кнопки next/prev на lock screen не выставляются — продуктовый выбор.** `activateMetadata` передаёт только `showSeekBackward`/`showSeekForward`, а `showNextTrack`/`showPreviousTrack` опущены (нативный дефолт — `false`), поэтому на экране блокировки и в уведомлении снова только seek backward/forward — как было до миграции на `AudioPlaylist`. Техническое препятствие снято: апстрим-баг expo-audio 58.0.9 (JS-геттер `loop` без main-thread hop) исправлен локальным патчем `patches/expo-audio+58.0.10.patch` (см. «Повтор»), поэтому включение кнопок безопасно — достаточно передать `showNextTrack: true`/`showPreviousTrack: true` в `LockScreenControls.activateMetadata`. Нативная очередь при этом продолжает поддерживать транспорт: авто-переход между треками выполняет движок, JS получает `trackChanged` и сверяет его как авто-переход (предыдущая проповедь отмечается завершённой). Если JS заморожен, авто-переход всё равно происходит, а метаданные обновятся при пробуждении. Кнопки next/prev вернутся, если продукт подтвердит необходимость; до этого ручное переключение — только из UI приложения (`usePlayerToggleTrack`/`executeTrackSwitch`).

**Отложенная активация (Android 12+).** С API 31 старт foreground service из фона запрещён (`ForegroundServiceStartNotAllowedException`); expo-audio ловит исключение и логирует «Failed to start the expo-audio foreground service...». Холодный восстановительный путь может дойти до `setMetadata` на новой очереди, пока приложение ещё не foreground-permitted, поэтому полная активация гейтится по `AppState.currentState === 'active'` (in-place `updateLockScreenMetadata` сервис не стартует и гейт не проходит): в фоне `{ player, metadata }` складывается в `pendingActivation` (последний выигрывает) и лениво регистрируется `AppState`-листенер; на переходе в `active` активация выполняется, только если `pending.player === activePlayer` (иначе `clear()` её аннулировал). Пока активация отложена, элементы управления lock screen всё равно доступны через notification-фолбэк, а сама активация успешно проходит при следующем foreground. `clear()` сбрасывает `pendingActivation` и снимает листенер.

Скипается в Expo Go (`isExpoGo`). Retry до загрузки плеера и version-counter вынесены в `native/LoadedRetryScheduler.ts` (`loadedRetryScheduler.schedule` / `invalidate`).

**Веб** (вместо нативного `setActiveForLockScreen`): `WebPlayerService.setLockScreenMetadata` → `webMediaSession.ts` (Media Session API). `MediaMetadata` получает `title`/`artist`/`albumTitle` и `artwork` (передаётся как есть: `artworkUrl` из метаданных или без обложки; фолбэк-иконка приложения и фильтрация `hasUriProtocol` — только нативная логика в `LockScreenControls`); `updatePlaybackState`/`updatePositionState` держат системный прогресс-бар и медиа-кнопки (play/pause/±10s) актуальными. Все вызовы — в try-catch (не все браузеры поддерживают; косметика не должна ронять воспроизведение). Подробности — [web.md](./web.md) → «Плеер на web».

Artwork резолвится с фолбэком: `artworkUrl = [metadata.artworkUrl, getLocalAppIconUri()].find(hasUriProtocol)` — приоритет artwork трека, затем локальная иконка приложения (`getLocalAppIconUri` из `src/shared/lib/app-icon.ts`: ассет `assets/fallback-artwork.png` через `Asset.fromModule(...)` + `downloadAsync()` → `file://` uri), иначе — без артворка. `hasUriProtocol` отбрасывает значения без протокола (`assets_fallbackartwork` из release-сборки, `''`, `null`) — в натив уходит только валидный URL (`https://`, `http://`, `file://`, `asset:///`, `content://`). Если валидного значения нет, ключ `artworkUrl` полностью опускается (не отправляется даже как `undefined`). `setActiveForLockScreen` обёрнут в try-catch (см. Баг 3). Фолбэк-иконка догоняет первый показ: `IconFollowUp` ждёт `whenAppIconReady()` и после загрузки метаданные переустанавливаются один раз (in-place для той же очереди).

## Персистенция позиции

Позиция воспроизведения сохраняется в `CURRENT_SOUND_POSITION` как JSON `{ sermonId, positionMs, savedAtMs, durationMs? }` — привязана к конкретной проповеди. Поле `durationMs` опционально: пишется при наличии длительности (10с-тик, пауза), опускается при flush нативного перехода. Точки flush:

- **10с-тик** (`usePlaybackProgressSaver`): при воспроизведении — bound-запись (`savePlaybackProgress`) + flush каталога истории (`flushHistoryProgressAction`); мини-снапшот `listeningProgressSnapshot` **больше не пишется** (писатель удалён); пауза останавливает авто-сохранение (гейт на `isPlaying`); skip-first-tick после переключения трека.
- **Пауза** — позиция персистится на каждом пути: кнопки UI, нативный/веб-контроллер (`PlaybackController.pause`, `WebPlayerService.pause`), lock-screen и OS-прерывание (auto-pause), уход в фон; внешняя пауза веб-элемента `<audio>` тоже flush'ит позицию (слушатель `pause`-события в `index.web.ts`). Flush паузы при OS/lock-screen-прерывании **безусловен на ребре playing→false**: `playlistStatusHandler` вызывает `onAudioInterruption(true)` без чтения атомов, `createAudioInterruptionHandler` безусловно вызывает `pause('auto')` (идемпотентно: no-op guard флаша истории, пауза на уже паузе — no-op) — user-pause и natural-end тоже проходят через этот путь (прослежено как безвредное). `stop()`/`unload()` сначала глушат статус-поток (`statusMuted`), чтобы асинхронный тик после `seekTo(0)` не сработал как ребро прерывания и не затёр позицию нулём.
- **Stop/Unload** — `PlaybackController.stop` (нативный) и `WebPlayerService.stop`/`unload` (веб) flush'ят позицию **до** паузы/сброса (`flushProgress`/`flushProgressAtCurrentTime`) — персистится живая pre-stop позиция, как при паузе.
- **Seek** (`PlaybackController.seekTo` нативный, `WebPlayerService.seekTo` веб): `flushHistoryProgressAction` с trailing-дебаунсом 400мс (`SEEK_HISTORY_FLUSH_DEBOUNCE_MS`) — позиция истории обновляется после seek (в т.ч. на паузе); частые seek long-press (тик 200мс) коалесятся в один финальный write. Веб-`seekTo` использует тот же общий `scheduleHistoryFlush` (паритет с нативным путём).
- **Нативный переход** (`TrackAutoAdvanceService.handleTrackChanged`): `savePlaybackProgress(positionMs: resumeMs)` для нового трека после resume-seek — позиция resume персистится при нативном переходе, чтобы краш сразу после смены трека восстановился на позиции resume.
- **Уход в фон** (`usePlaybackProgressSaver`): AppState `background` → немедленный flush теми же guard'ами.

При cold start `initializePlayer` парсит JSON через `playbackProgressSchema`; легаси-голое-число → parse вернёт `undefined` → позиция 0. Если `sermonId` не совпадает с текущим аудио → позиция 0. Позиция clamp'ится к `durationMs` из записи (если поле отсутствует или ≤ 0, clamp не применяется).

**Нормализация позиции у конца трека.** `savePlaybackProgress` — единственная точка записи `CURRENT_SOUND_POSITION` — при `durationMs > 0` и остатке меньше `COMPLETION_REMAINING_MS` (10с, общий порог завершённости из `entities/listening-history/lib/constants.ts`) сохраняет `positionMs: 0`. Пауза в пределах 10с от конца считается дослушиванием (история при этом получает реальную позицию и помечает запись завершённой), поэтому cold start перезапускает проповедь с начала, а не seek'ает к концу и не даёт мгновенный `STATE_ENDED`. При `durationMs` 0/неизвестной позиция сохраняется как есть.

## История прослушивания и resume

История пишется **по событиям** (старт, пауза/flush, переключение трека, завершение), **каждые 10с при воспроизведении** (тик `usePlaybackProgressSaver` пишет каталог; мини-снапшот больше не пишется) и **при возврате в foreground** (native reconcile, см. «Возврат в foreground (native reconcile)»). Это отдельный механизм от персиста позиции плеера (`CURRENT_SOUND_POSITION`).

### Завершение трека

Завершение **внутри** очереди (не последний трек) не требует JS: движок переходит к следующему элементу, а `handleTrackChanged` фиксирует завершённость старого трека через `recordSermonSwitchAction({ markOldCompleted: true })` (длительность — из per-index снапшота). Завершение **очереди** — отдельный путь: `handleQueueEnd` вызывается по одному `didJustFinish` на последнем элементе при loop `'none'`, один раз помечает запись завершённой (`markHistoryCompletedAction(ctx, sermonId, durationMs)` → `positionMs = durationMs`) и защитно ставит паузу. Повторные события дедуплицируются по индексу.

Ручное переключение кнопками Next/Prev (`usePlayerToggleTrack`) в Queue-режиме тоже заворачивает по циклу на границах плейлиста (Issue #67): next на последнем → первый, prev на первом → последний; в Track-режиме тап перезапускает текущую проповедь с начала. Авто-повтор трека — нативный loop и в JS не наблюдается.

### Возврат в foreground (native reconcile)

Пока JS заморожен, движок продолжает играть, а `trackChanged`, `didJustFinish` и прогресс до JS не доходят. При переходе `background|inactive → active` `useAppStatePlayback` (`src/entities/player/ui/PlayerControls/useAppStatePlayback.ts`) вызывает `playerService.reconcileOnForeground`, если JS считал плеер играющим или движок всё ещё играет; в остальных случаях reconcile не запускается.

Решение считает чистая функция `decideForegroundReconcile` (`src/entities/player/lib/PlayerService/native/reconcileDecision.ts`), применяет `reconcileOnForeground` (`src/entities/player/lib/PlayerService/native/reconcileOnForeground.ts`):

- `flush-current` — движок на той же проповеди: позиция и длительность из движка флашатся в историю и `CURRENT_SOUND_POSITION`;
- `advance` — движок ушёл вперёд по той же очереди: полностью проигранные треки отмечаются завершёнными (`markHistoryCompletedAction`, отсутствующие записи создаются из снапшота трека), затем `TrackAutoAdvanceService.handleTrackChanged` синхронизирует атомы, сторедж, метаданные lock screen и стартовую запись нового трека;
- `idle-complete` — очередь (`loop: 'none'`) закончилась на последнем треке: завершаются все треки от JS-индекса до последнего, `isPlaying`/позиция берутся из статуса движка;
- `fallback` — индексы не сопоставились (повтор-обёртка, другая очередь, обратный скачок): только flush текущей позиции.

После обработки, если движок играет, метаданные lock screen активируются заново (`reassertLockScreenMetadata` — полный путь `setActiveForLockScreen(true)`); это заменяет прежний reassert из `useAppStatePlayback`. Семантика истории — [listening-history.md](./listening-history.md) → «Возврат в foreground (native reconcile)»; ограничение `fallback`-ветки — [debt.md](../debt.md) → «Listening history».

### Resume-позиция (все пути)

Восстановление позиции из истории (`getResumePosition`) работает во всех путях начала воспроизведения:

#### Ручной тап (`usePlayNewSermon`)

`usePlayNewSermon` (`src/entities/player/lib/usePlaySermon.ts`) — основной хук «тапнул на трек». Контекст (`playlist`) ему передаёт вызывающий экран; на экранах «Офлайн» и «История» его выбирает `features/playback-choice` — см. [playback-choice.md](./playback-choice.md). Флоу:

1. `getResumePosition(history, sermonId)` вычисляет позицию resume (0 если нет записи / завершена / position ≤ 0, иначе `positionMs`).
2. Текущий трек другой → `replaceAudio(url, resumeMs)`.
3. Текущий трек тот же (same-id tolerance 1с):
   - `resumeMs === 0` → `seekTo(0)` (с начала).
   - `resumeMs > 0` и позиция далеко → `seekTo(resumeMs)`.
4. При смене трека (`oldAudio.id !== sermonId`) — `recordSermonSwitchAction({ markOldCompleted: false, ... })` **до** `replaceAudio`: flush позиции старого трека в историю.
5. `recordPlaybackStartAction(newAudio, playlist)` — записывает/обновляет запись в истории (только если трек новый или тот же).

Повторный тап по той же проповеди подавляется гардом (Issue #74): хук держит `inFlightSermonIdsRef` (Set id запусков «в полёте») и `lastTapRef` (id + время последнего тапа, запустившего воспроизведение). Если та же проповедь уже «в полёте» (запуск не завершён) или с последнего тапа, запустившего воспроизведение, прошло < 1000мс — тап игнорируется (leading-edge: первый тап срабатывает сразу, повторные в окне/в полёте гасятся; подавленные тапы окно не обновляют). Параллельные запуски одной проповеди невозможны (Set), разные проповеди идут параллельно свободно (пользователь передумал); после окна тап по той же проповеди снова работает (осознанный рестарт). При ошибке запуска окно подавления сбрасывается — повторный тап срабатывает сразу. Гард живёт в refs хука и действует на каждый экземпляр хука отдельно: у `PlaylistScreen`, `DynamicSectionsSlider`, `SearchGroupedResults`, `usePlaybackChoice` и `useSheetLifecycle` своё состояние гарда, тапы через разные компоненты взаимно не подавляются (на практике открытие полноэкранного плеера перекрывает UI). Тап по проповеди, которая уже играет (`currentAudio.id` совпадает и `isPlayingAtom === true`), — полный no-op (Issue #99), **если запрошен тот же плейлист-контекст**; если `currentPlaylistAtom` известен и запрошен другой плейлист, `playNewSermonAsync` переключает контекст (artwork, `currentPlaylist`, lock-screen) без перезапуска и повторного `play()` — позиция сохраняется (см. выше). Тап по той же проповеди на паузе по-прежнему возобновляет воспроизведение.

#### Кнопки Next/Prev (`usePlayerToggleTrack`)

`usePlayerToggleTrack` (`src/entities/player/ui/PlayerControls/usePlayerToggleTrack.ts`) — чтение истории через `ctx.get(historyAtom)` + `getResumePosition(history, sermonId)`. При смене трека `recordSermonSwitchAction({ markOldCompleted: false, ... })` flush'ит позицию старого трека; переход выполняется `skipTo` внутри нативной очереди (`replaceQueueTrack`), без пересоздания плеера.

#### Очередь

Отдельного JS-пути «очереди» больше нет: Next/Prev реализованы в `usePlayerToggleTrack`, авто-переход — нативный движок + `TrackAutoAdvanceService.handleTrackChanged`. (`useQueueManagement` удалён 2026-09-10 — мёртвый хук без потребителей.)

#### Нативный переход (`TrackAutoAdvanceService.handleTrackChanged`)

Resume считается в координаторе: `getResumePosition(ctx.get(historyAtom), newTrack.id)` → `seekToResume` (пропуск при `resumeMs <= 0` и в пределах 10с от конца трека). При замороженном JS шаг не выполняется — трек стартует с 0:00.

### Чтение состояния через ctx.get (без useAtom)

`usePlayNewSermon` **не подписывается** на `currentAudioAtom`/`positionAtom`/`durationAtom`/`historyAtom` через `useAtom` — состояние читается императивно снапшотом `ctx.get(...)` в момент вызова (`src/shared/lib/reatom-ctx`). Это было корневой причиной перф-проблемы: реактивная подписка хука в каждом `TracksListItem` держала все экраны списков подписанными на атомы плеера, и те ре-рендерились ~2 раза в секунду (каждый position-тик) во время воспроизведения. При императивном чтении хук не ре-рендерится от плеера вовсе — списки обновляются только когда меняется `historyAtom` (по событиям истории).

### Порядок reconciliation нативного перехода

`handleTrackChanged` — единственный JS-funnel нативного перехода. Он намеренно **не** вызывает `replaceAudio`/`play()`: переключение уже произошло в движке. Порядок шагов: storage-first чтение контекста (`CURRENT_AUDIO`/`CURRENT_PLAYLIST`) → ранний выход, если сторедж уже указывает на новый трек (ручной путь) → snapshot старого индекса → `setCurrentAudioAction` + `recordSermonSwitchAction({ markOldCompleted: true })` → resume-seek → `savePlaybackProgress` → метаданные lock screen → `startBackgroundCaching`. Ошибки шага репортятся (`reportError`) и не отменяют уже состоявшийся нативный переход.

### Смена трека: нативная очередь и подмена источника (Issue #50 и дубли уведомлений)

Смена трека больше **не** teardown'ит плеер и не пересоздаёт нативный экземпляр. Порядок треков живёт в нативной очереди `AudioPlaylist`: авто-переход выполняет движок, ручной — `skipTo` в той же очереди. Тот же ExoPlayer, та же MediaSession, тот же foreground service и тот же ID уведомления переживают переключение.

История (Issue #50, Android, заблокированный экран): прежний `replaceAudio` вызывал `lockScreenControls.clear()` → `setActiveForLockScreen(false)` (останавливал FGS) и release'ил плеер до старта нового источника. Без FGS и аудио Android замораживал кэшированный процесс, и JS-цепочка авто-перехода (включая polling `waitForLoaded`) стояла до разблокировки экрана. Миграция убирает не только release, но и саму зависимость перехода от JS: движок играет следующий элемент сам.

Teardown теперь только в двух точках (см. «Восстановление после сбоя»): `unload` (`playlistEngine.destroy()`) и пересборка очереди (`buildQueue` — освобождает старую очередь и очищает её lock-screen состояние).

**Дубли media-уведомлений** (исторический контекст): в expo-audio 57.0.x `setActiveForLockScreen(false)` мог молча не сработать, пока сервис binder в состоянии BINDING → старый MediaSession/уведомление осиротевали (expo#47101/#48694). Очередь снимает класс проблемы: сессия одна на всё время жизни очереди, а teardown'ов при смене трека нет. `expo#41852` (утечка при `remove()`) закрыт освобождением очереди через `destroy()` на пересборке/unload.

**Подмена источника** (кэш ↔ сеть ↔ partial) идёт через `swapCurrentSource`: `insert` нового URI на текущий индекс + `remove` старого; при сбое нативной пары — fallback на one-track rebuild. Экземпляр очереди, MediaSession и foreground service при этом сохраняются.

Guard от устаревших событий (expo#34301): после смены источника старый `didJustFinish` мог выстрелить на новом. В очереди слушатели живут всё время её жизни (окна `cleanup()`/`setupListeners()` больше нет), поэтому защита сосредоточена на пути **конца очереди**: arming по первому «здоровому» статусу (`isLoaded && duration > 0 && !didJustFinish`), эвристика `isGenuineTrackEnd` (позиция в пределах 3с от длительности) и дедупликация `queueEndHandled` (см. `playlistStatusHandler.ts`).

### WebPlayerService.replaceAudio

На вебе `replaceAudio` делегирует `loadAudio(url, initialPositionMs)` — синтаксический сахар, позиция устанавливается после `loadedmetadata` через `audio.currentTime`.

Web-длительность синхронизируется в общий `durationAtom` (паритет с нативным `playlistStatusSync`): слушатели `loadedmetadata`/`durationchange` (`web/audioEvents.ts`, чистый wiring-модуль) прогоняют `Math.floor(audio.duration * 1000)` через guard `Number.isFinite && > 0` и делегируют в `handlers.onDuration`; запись делает `web/durationWriter` (`writeWebDuration`: `setDurationAction` + `webPlayerState` + AsyncStorage `CURRENT_SOUND_DURATION`) — web-флаши (`flushProgressAtCurrentTime`, `scheduleHistoryFlush`) пишут реальный `durationMs`, а не 0. Слушатели отвязываются на teardown/replace (cleanup-функция `attachWebAudioEvents`).

При смене трека `loadAudio` **сбрасывает длительность в 0 до создания/подключения элемента** (`resetWebDuration`: `setDurationAction(ctx, 0)` + `webPlayerState.setDuration(0)`) — зеркалит нативный путь (свежая очередь/источник), чтобы stale-длительность трека A не попала в запись трека B (иначе completion-детекция и границы скраба использовали бы неверный bound во время буферизации).

Веб-сервис покрыт юнит-тестами (`index.web.test.ts`, импорт по явному пути `./index.web` в обход jest-expo platform-resolution): identity-guard пауз-листенера, гейт `state.isPlaying`, flush-пути stop/unload/seekTo, no-op guard'ы `flushProgressAtCurrentTime`, duration-bridge (включая сброс длительности при replace до прихода реальной длительности).

### Web-прерывание: восстановление позиции и автовозобновление (Issue #106)

iOS Safari при системном прерывании (звонок, Siri, переключение приложений) сбрасывает `currentTime` HTMLAudioElement в 0 и «забывает» позицию. `web/interruptionResume.ts` (`createInterruptionResume`) хранит снапшот позиции и восстанавливает её при возврате:

- **Снапшот** — `noteLivePosition(ms)` пишется из каждого `timeupdate` (`web/audioHandlers.ts`), но значения ≤ 1с игнорируются (guard `RESUME_GUARD_MIN_MS = 1000` — не запоминать стартовый ноль); `noteExplicitPosition(ms)` фиксирует явный seek (`seekTo`), отрицательные клампаются в 0; `reset(ms)` ставит снапшот при `loadAudio`/`stop`/`unload`.
- **Восстановление** — `maybeRestore(audio)` вызывается из `play()` и из visibility-колбэка (`web/visibilityWatcher.ts`): если снапшот > 1с и `audio.currentTime` всё ещё < 1с (браузер сбросил позицию), применяется `applyRestore` — `audio.currentTime = snapshot`, `state.setPosition`, `mediaSession.updatePositionState()`. При `readyState === 0` (метаданные ещё не загружены) вешается **одноразовый** `loadedmetadata`-листенер, который повторяет `currentTime` только если браузер так и не продвинул позицию за 1с. Pending-`loadedmetadata`-ретрай отменяется явным seek (`noteExplicitPosition`) и `reset` — легитимный переход к 0 не перебивается устаревшим листенером; повторный `applyRestore` заменяет предыдущий pending-листенер.
- **Visibility-watcher** — `watchPageVisibility` живёт всё время жизни синглтона: `unload()` его не снимает (колбэк без `audio` — no-op), поэтому restore-on-visible и автовозобновление работают и после unload+reload.
- **Flush** — `flushProgressAtCurrentTime` пишет `max(currentTime, snapshot)`, чтобы пауза/stop/unload после сброса не затёрли историю нулём.
- **Media Session reassert** — `web/mediaSession.reassert()` перерегистрирует action-хендлеры и обновляет playback/position state; вызывается из visibility-колбэка и `play`-события (`web/audioHandlers.ts`), потому что iOS Safari теряет media-session-хендлеры при прерывании.
- **Признак намерения воспроизведения** — `web/pauseIntent.ts` (модульный синглтон) — веб-аналог нативного `wasPlayingBeforeInterruption`: `markInterruptedWhilePlaying()` выставляется в `audioHandlers.onPause` **только если к моменту pause-эджа воспроизведение реально шло** (`state.isPlaying` был true) — т.е. это ОС-прерывание, а не простая пауза. Событие `play` признак **не** выставляет: самого нажатия play недостаточно для автовозобновления. Сбрасывает признак `markUserPause()` — явная пауза (`transport.pause`, включая кнопку pause системного медиаплеера, и `transport.stop`); его вызов идёт после обработчика `pause`-события и перекрывает выставленный там признак. Pause-эдж при уже остановленном воспроизведении также сбрасывает признак.
- **Автовозобновление** — в visibility-колбэке (`web/interruptionResumeController.ts`) после `reassert()`/`maybeRestore()` вызывается `resumeInterruptedPlayback` (`web/interruptionAutoResume.ts`): если признак установлен, элемент на паузе и трек не завершён (`audio.paused && !audio.ended`), делается `audio.play()`. `NotAllowedError` (autoplay-policy) оставляет элемент на паузе и логируется через `reportError` без краха; `AbortError` — одна короткая повторная попытка (~75 мс). Если ОС приостановила воспроизведение без `pause`-эджа, признак не выставляется и автовозобновление не срабатывает — см. платформенные ограничения.
- **Платформенные ограничения** — возобновление невозможно, если ОС убила процесс PWA (извне запустить аудио нельзя); WebKit #212780/#295518: на iOS Safari прерывание может не выстрелить или браузер не разрешит `play()` — тогда воспроизведение остаётся на паузе и пользователь возобновляет вручную. Android Chrome сам возобновляет лишь transient focus loss, пока процесс жив.

Подробнее — [listening-history.md](./listening-history.md).

## Известные баги (Issue #45)

Пользовательский репорт после долгого прослушивания: (1) авто-переключённая проповедь без обложки, хотя в плейлисте она есть; (2) через некоторое время воспроизведение начинает ставиться на паузу, плеер исчезает из панели уведомлений и не возвращается; (3) после нескольких попыток resume + перезапуска приложения — crash loop (приложение открывается и сразу закрывается).

### Баг 1: Отсутствует обложка при авто-переходе (ИСПРАВЛЕНО)

Историческая причина: старый JS-авто-переход (`playNextTrack`) создавал `newAudio = { ...nextTrack, audioUrl }` — брал собственный artwork проповеди (может быть пустым), а не `playlist.artwork`. Та же ошибка была в `repeatCurrentTrack` и `playFirstTrackInQueue`.

Последствия:

- In-app UI (`MiniPlayer`, `ExpandablePlayer`) читает `audio.artwork` напрямую → пустая обложка после авто-переключения.
- `initializePlayer` восстанавливает lock-screen метаданные из `audio.artwork` → «плохой» персистнутый artwork переживает перезапуски.

Правило зафиксировано и перенесено в новую архитектуру: `TrackAutoAdvanceService.handleTrackChanged` собирает `newAudio` с `artwork: playlist.artwork` перед `setCurrentAudioAction`/`recordSermonSwitchAction` (ручные пути `playNewSermonAsync`/`executeTrackSwitch` делают то же для `currentAudio`, а в историю передают «history-аудио» с собственным artwork проповеди).

```typescript
const newAudio: AudioPlayerData = { ...newTrack, artwork: playlist.artwork }
```

`artwork` в домене — `string | null` (см. Баг 4): при `null` UI-компоненты показывают плейсхолдер через `CoverImage`, а lock screen подставляет иконку приложения.

### Баг 2: Плеер исчезает из панели уведомлений (ИСПРАВЛЕНО)

Историческая причина — **порядок вызовов** в JS-авто-переходе. Ручной путь работал: `replaceAudio` → `play()` → `setLockScreenMetadata` — плеер загружен И играет в момент `setActiveForLockScreen(true)`, что надёжно показывает уведомление. Авто-путь делал наоборот: `replaceAudio` → `setMetadata` → `play` — метаданные выставлялись на неиграющем MediaSession, и уведомление не появлялось.

Фикс исторического пути: порядок вызовов приведён к `replaceAudio → play → setMetadata`.

В нативной очереди класс проблемы снят иначе: при авто-переходе сессия уже активна и играет, а координатор обновляет метаданные in-place (`updateLockScreenMetadata`) на каждый `trackChanged`. Ручной путь (`executeTrackSwitch`) по-прежнему сохраняет порядок «переключить → play → метаданные».

Остаточный риск: если сборка очереди не удалась (`loadQueue` вернул `null` — 30с таймаут загрузки или ошибка `createAudioPlaylist`), воспроизведение не стартует, а уведомление может показать прежние метаданные до следующего успешного `setLockScreenMetadata`. Возврат в foreground триггерит `reassertLockScreenMetadata` (`useAppStatePlayback`), который принудительно проходит полный путь активации и перепривязывает сервис. Отслеживается в `docs/debt.md`.

### Баг 3: Crash loop при перезапуске (ИСПРАВЛЕНО)

**Подтверждённая корневая причина (из реального crash log):** фолбэк-обложка возвращала URI без протокола (`assets_fallbackartwork`) в release-сборке — `getLocalAppIconUri()` после `downloadAsync()` отдавал `asset.localUri` как голое имя ассета. expo-audio `setActiveForLockScreen` (синхронный JSI-вызов) бросал `MalformedURLException` (`Cannot cast value for field 'artworkUrl'` — натив ждёт `java.net.URL`), а необработанный throw из колбэка `setInterval` (retry-путь `setMetadata`) приводил к фатальному крашу при восстановлении плеера на старте — crash loop на каждом запуске.

Фикс (связка правок):

- **Санитизация на границе** (`LockScreenControls.applyMetadata`): `artworkUrl = [metadata.artworkUrl, getLocalAppIconUri()].find(hasUriProtocol)` — `hasUriProtocol` пропускает только значения с протоколом (`https://`, `http://`, `file://`, `asset:///`, `content://`), отбрасывает голые имена (`assets_fallbackartwork`), `''`, `null`. Ключ `artworkUrl` **полностью опускается**, если валидного значения нет (не отправляется даже как `undefined`).
- **Fail-safe** (`setActiveForLockScreen` в `applyMetadata` и `clear`): вызов обёрнут в try-catch — `console.error('[LockScreenControls] setActiveForLockScreen failed:', error)` + `reportError(error, 'Не удалось обновить данные плеера на экране блокировки')`. Метод никогда не бросает вверх: lock screen косметичен, ошибка показывает диалог, но не роняет процесс.
- **Валидация в app-icon** (`src/shared/lib/app-icon.ts`): `localAppIconUri` присваивается только если `asset.localUri` прошёл `hasUriProtocol`; `APP_ICON_URI` — live binding (`export let`), обновляется на валидный локальный uri после загрузки (плейсхолдер в UI начинает рендериться).

Ранее (до подтверждения корневой причины) считалось, что crash-loop вызывает нативный краш ExoPlayer/MediaSession:

- ~~`handleTrackEnd` **без try-catch**~~ — исправлено (Issue #45, Phase 1): тело метода вынесено в приватный `advanceToNextTrack`, а `handleTrackEnd` оборачивает вызов в try-catch с логированием (`console.error('[TrackAutoAdvanceService] handleTrackEnd failed:', error)`) и `reportError`, так что `void trackAutoAdvanceService.handleTrackEnd()` больше не даёт unhandled promise rejection.
- `GlobalErrorHandler` повторно вызывает `originalHandler(error, isFatal)` после `reportError` — фатальные ошибки по-прежнему убивают процесс (нативный краш не подавляется), но теперь перед этим показывается глобальный диалог ошибок (см. [error-handling.md](./error-handling.md)), а `markHistoryCompletedAction` снабжён `.catch` — асинхронная ошибка не роняет плеер. Это убирает симптом «показывает диалог, потом закрывается» для обрабатываемых ошибок.
- Коммит `ec69eeb` (20.08.2026) документирует проблемы уничтожения Android MediaSession/ExoPlayer («activity is no longer available», expo#46137, androidx/media#1928).
- Стартовые чтения хранилища все обёрнуты в safeParse — повреждённый JSON истории сам по себе краш старта НЕ вызовет.

Фикс: crash-loop устраняется связкой правок Issue #45 — `handleTrackEnd` обёрнут в try-catch (нет unhandled rejection), zod-схемы приведены к честному `artwork: string | null` (Баг 4), а ошибки сервисов/слушателей теперь идут в `reportError` → глобальный диалог вместо молчаливого краша. Необрабатываемый фатальный нативный краш по-прежнему завершает процесс (см. [error-handling.md](./error-handling.md) → GlobalErrorHandler).

Общий контракт передачи данных из JS в нативные модули (expo-audio, expo-asset), правила валидации на границе и диагностика нативного краша — в [../contracts/native-modules.md](../contracts/native-modules.md).

### Баг 4: Zod schema drift убивает auto-advance молча (ИСПРАВЛЕНО)

Историческая причина: `TrackAutoAdvanceService.handleTrackEnd` перечитывал `CURRENT_AUDIO`, `CURRENT_PLAYLIST`, `CURRENT_REPEAT_MODE` из AsyncStorage и парсил их zod-схемами (`parseAudioPlayerData`/`parsePlaylistData`). Если парсинг возвращал `undefined` (например, `sermonSchema` требовал `artwork: z.string()`, а API для некоторых проповедей отдаёт `null`/отсутствующее поле), обработчик молча выходил — авто-переход умирал **без единой ошибки в логах**. Сильный кандидат на симптом «воспроизведение встаёт на паузу и больше не возобновляется» после долгих сессий: расхождение (drift) между payload API и строгими zod-схемами.

Storage-first чтение сохранено в координаторе: `handleTrackChanged` читает `CURRENT_AUDIO`/`CURRENT_PLAYLIST` и парсит их теми же схемами, `queueContext` — плюс `CURRENT_REPEAT_MODE`. Пропуск `CURRENT_PLAYLIST` означает, что нативный переход уже состоялся, но JS не может его согласовать (история/метаданные) — поэтому `reportParseFailure` логирует `console.error` и показывает глобальный диалог через `reportError`; молчаливого выхода больше нет. `handleQueueEnd` от стореджа не зависит — работает от снапшотов движка.

Фикс drift: `sermonSchema.artwork` изменён на `z.string().nullable()`, `playlistDataSchema.artwork` — тоже `z.string().nullable()`: доменный тип `artwork` теперь честный `string | null` вместо пустой строки-заглушки. Маппер нормализует на границе API (`apiSermon.artwork ?? null`). Потребители null: `CoverImage` подставляет `IMAGE_PLACEHOLDER`, lock screen — иконку приложения (`metadata.artworkUrl || getLocalAppIconUri()`).

### Event-driven ожидание загрузки очереди (Issue #60)

**Историческая корневая причина:** при фоновом авто-переходе на Android (заблокированный экран) JS-таймеры (`setInterval`, `setTimeout`) замораживаются (`JavaTimerManager` паузится при host pause), но нативные события статуса **продолжают приходить**. Старый `waitForLoaded` использовал `setInterval(100ms)` polling — при фоновом `replace()` нативный плеер становился loaded и начинал воспроизведение, но polling стоял из-за замороженных таймеров. Когда пользователь открывал приложение, polling обнаруживал `isLoaded === true` и безусловно вызывал `seekTo(initialPositionMs)` — с `initialPositionMs=0` это `seekTo(0)` на уже играющем треке → **аудио перезапускалось с начала**. Дополнительно `isBufferingAtom` застревал в `true` → на кнопке play мелькал спиннер.

**Сейчас** загрузку очереди ждёт `awaitPlaylistLoaded` (`src/entities/player/lib/PlayerService/native/awaitPlaylistLoaded.ts`), `waitForLoaded` удалён вместе с `AudioLoader`:

1. **Sync fast-path:** `playlist.isLoaded === true` → сразу `true` (без подписок и таймеров).
2. **Event-driven primary path:** подписка на `playlist.addListener('playlistStatusUpdate', ...)` — событие приходит и в фоне. При `status.isLoaded === true` → resolve `true`, подписка снимается (double-completion guard через флаг `settled`).
3. **Safety-net timeout:** `setTimeout(30s)` fallback для foreground stall; в фоне таймеры не работают — это нормально, event path покрывает.
4. **Staleness guard:** `isCurrent()` callback (`() => state.playlist === playlist`) — если очередь уже пересобрана новее, resolve возвращает `false` без записи в глобальное состояние.
5. **Seek-семантика:** `buildQueue` делает seek **только** при `initialPositionMs > 0` и клампит цель к загруженной длительности — seek-to-zero (деструктивный рестарт уже играющего трека) и seek за длительность (ExoPlayer clamps к концу → `STATE_ENDED` → случайный auto-advance) исключены. На `trackChanged` resume-seek выполняет координатор (`seekToResume`), с пропуском near-end позиций.
6. **Буферизация не застревает:** `playlistStatusSync` синкает `isBufferingAtom`/`isPlayingAtom`/позицию/длительность на каждое статус-событие; подписки живут всё время жизни очереди, окна polling больше нет.

**Связанные файлы:** `native/awaitPlaylistLoaded.ts`, `native/playlistQueueOperations.ts` (`buildQueue`), `native/playlistStatusSync.ts`.
