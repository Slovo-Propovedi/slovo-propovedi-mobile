| Тактильный отклик                         | `expo-haptics`                                                                                                                             | Лёгкий тактильный отклик интерактивных элементов через базовые примитивы `PressableButton`/`TouchableButton`: вибрация запускается через ~120 мс после касания (`usePressHaptic`), поэтому нажатие ощущается сразу, но ранний отклик снимается по `pressOut` (скролл/отпускание), по смещению касания больше 6px (`onTouchMove`) — движение означает, что жест становится свайпом, поэтому свайпы, начатые с кнопок `PressableButton`, включая заголовок секции слайдера, остаются беззвучными, — или самим обработчиком `onPress` (`settlePress`): на Android `onPress` может прийти раньше `onPressOut`, и дедлайн 120 мс попадает между ними — на устройстве доказан призрачный импульс через +49 мс после press (press на pressIn+71 мс, импульс на pressIn+120 мс), поэтому `onPress` сначала гасит ожидающий таймер и только потом решает, нужна ли вибрация отпускания; завершённый тап после сработавшего раннего отклика не вибрирует повторно. Дубли гасятся на слое вибрации: импульсы в пределах 200 мс считаются одним жестом — одна вибрация (защита от двойного срабатывания при ремоунте посреди жеста или передаче жеста новому responder'у: dedup-флаг живёт в экземпляре хука и при пересоздании чист); `hapticTick` прогресс-бара намеренно остаётся без троттлинга — его тики и так идут с шагом в секунду. Элементы с долгим нажатием (`onLongPress`: контекстное меню, старт перетаскивания) ранний отклик пропускают — их фидбек остаётся end-of-gesture: тап по `onPress`, меню по `onLongPress`. При этом обёртка вибрации прикрепляется к `Pressable`/`TouchableOpacity` только когда у элемента есть реальное действие долгого нажатия: без этого RN Pressability всё равно взводит таймер долгого нажатия (~500 мс) при наличии пропа `onLongPress`, и медленное нажатие на обычной кнопке давало бы фантомную вибрацию поверх раннего отклика (и отменяло бы `onPress`). Исключение — плашки-скримы (`modal`/`AnchoredDropdown`/`PlayerMenu`/`DetailsOverlay`): закрываются по press-in с вибрацией, и тики прогресс-бара плеера (`hapticTick` по секундам). iOS — `impactAsync(ImpactFeedbackStyle.Light)` (системный Taptic Engine); Android — `performAndroidHapticsAsync(AndroidHaptics.Virtual_Key)` (`View.performHapticFeedback`, VIRTUAL_KEY), отклик следует настройкам системы конкретного устройства (короткий/сильный — как настроено пользователем); web — короткий импульс ~12 мс через Vibration API (`navigator.vibrate`) при наличии API, иначе тихий no-op (большинство десктопов, iOS Safari). Трейд-офф Android: если в системе выключен виброотклик, в приложении вибрации не будет (актуально для MIUI) — принято осознанно. |

> **Почему `@react-native/jest-preset` пиннится точно (под версию RN):** preset версионируется синхронно с `react-native` и его `jest/setup.js` резолвит внутренние модули пакета RN по конкретному пути. Прецедент: в RN 0.87 добавлен `react-native/src/setup-env.js`, которого нет в preset 0.86.3; при `@react-native/jest-preset@^0.87.1` и `react-native@0.86.3` setup падал с `Could not locate module react-native/setup-env … node_modules/react-native/src/setup-env.js` до старта **любого** сьюта (376/376). Диапазон `^0.87.1` для `0.x`-версий разрешает патч-релизы 0.87.x и не откатывается на 0.86.3, поэтому пин — точная строка без `^`. Правило: при бампе `react-native` бампать `@react-native/jest-preset` до той же версии и держать оба пинами (после апгрейда на RN 0.88 пин держится по этому правилу). (Аналогичная поломка уже случалась 2026-08-24 — commit `15a0e29`, откат `b592b53`; повтор 2026-10-07 — commit `0c6b7ac`.)

> **Почему `patch-package` (история):** gorhom 5.2.14 содержал sub-pixel-баг в derived-статусе шторки: состояние EXTENDED определялось точным равенством `animatedPosition.value === containerHeight - animatedSheetHeight.value` (`BottomSheet.tsx` ~L308). При дробном PixelRatio позиция пружины и измеренная высота расходятся на доли пикселя → `===` никогда не истинно → вложенный скроллящийся список остаётся LOCKED навсегда (`useScrollable.ts:41-76`), откатывая каждый программный скролл в 0 (линия issues #2737; master == 5.2.14, фикса нет). Патч заменял точное равенство на epsilon-сравнение `Math.abs(...) < 0.5` в трёх местах (EXTENDED, EXTENDED-with-keyboard, FILL_PARENT) — `patches/@gorhom+bottom-sheet+5.2.14.patch`. > **Патч expo-font (патч `patches/expo-font+58.0.9.patch`):** в `node_modules/expo-font/build/FontLoader.web.js` функция `loadSingleFontAsync` глотает **асинхронное** отклонение шрифта: к промису `ExpoFontLoader.loadAsync(name, input)` добавлен `.catch(() => {})`. Синхронный `try/catch` там уже был (ловит только синхронные броски), а вот async-отклонение из `FontObserver.load(..., 12000)` (12-сек таймаут на медленных сетях, напр. `MaterialCommunityIcons.ttf` ~1.3 МБ) утекало как unhandled promise rejection → `window.addEventListener('unhandledrejection')` в `GlobalErrorHandler` поднимал ложное модальное окно «Произошла ошибка асинхронной операции» на mobile-web (Android Chrome). Шрифт при этом всё равно рендерится через инъекцированный `@font-face` CSS, поэтому модалка — чистый шум. Патч пересоздан против 58.0.9 после переписывания апстримом `FontLoader.web.js` — правка (`.catch(() => {})`) и мотивация те же.

> **Патч RNGH (патч `patches/react-native-gesture-handler+3.3.0.patch`):** на web `PointerEventManager` вызывает `target.setPointerCapture(pointerId)`/`target.releasePointerCapture(pointerId)` без guard'а в `pointerDownCallback`/`pointerUpCallback`/`pointerMoveCallback`; при быстром клике (stale pointer id) или синтетических событиях (Vimium `f`-хинты) браузер кидает `NotFoundError` → `Web ERROR` в консоли (весь полноэкранный плеер обёрнут в `Gesture.Pan()`, поэтому триггерится на любой клик). Патч оборачивает вызовы в try/catch (потеря capture косметическая — RNGH фолбэчится на per-element tracking). Патчатся `src/web/tools/PointerEventManager.ts` (исходник) и `lib/module/web/tools/PointerEventManager.js` (web-сборка); `lib/commonjs` в RNGH 3.x отсутствует. Autolinking создаёт gradle-проект `:expo-audio` из `node_modules/expo-audio/android` на этапе конфигурации сборки — `expo prebuild` для этого не нужен. **Следствия:** `modules/audio-effects/android/build.gradle` зависит от `project(':expo-audio')`, а не от maven-координаты (динамическое чтение версии через `JsonSlurper` и репозиторий `local-maven-repo` удалены как ненужные); gradle-сборка чуть длиннее — Kotlin expo-audio компилируется из исходников; при апгрейде expo-audio патч может перестать применяться — `yarn check:patches` упадёт по дизайну, заставляя пересмотреть/пересоздать патч до сборки.

> **Почему локальный модуль `modules/apk-installer`:** для self-update через `PackageInstaller` на RN 0.88 / Expo SDK 58 нет поддерживаемого npm-пакета (существующие RN-библиотеки устарели/несовместимы с New Architecture). Локальный Expo-модуль (`file:`-зависимость) не добавляет новых npm-зависимостей, автолинкуется через `expo-modules-autolinking` и собирается в CI `prebuild --clean` автоматически. Причина замены `ACTION_VIEW`: системный установщик (Android 16) удалял APK до чтения (`FileNotFoundException` в `InstallRepository.stageForInstall`), т.к. `startActivityAsync` резолвится при старте интента, а не по завершении установки.

> **Почему локальный модуль `modules/audio-effects`:** `expo-audio` не предоставляет API эквалайзера, баланса и pitch — модуль подключается к ExoPlayer'у expo-audio напрямую: JS передаёт `AudioPlayer` (SharedRef), Kotlin берёт `player.ref`, читает `audioSessionId` и вешает системные эффекты `android.media.audiofx` (`Equalizer` — 5 полос; `DynamicsProcessing` — баланс через per-channel input gain, API 28+); pitch — `PlaybackParameters(speed, pitch)` на самом ExoPlayer (скорость сохраняется с плеера). Feature parity reference — плеер BoomingMusic. Жизненный цикл: expo-audio пересоздаёт плеер на каждый трек, поэтому `attach` повторяется из `PlaybackController.applyPreferences` при каждой загрузке (`loadAudio`/`replaceAudio`). **Caveat (expo-audio из исходников):** `modules/audio-effects/android/build.gradle` зависит от `project(':expo-audio')` (autolinking создаёт этот проект из `node_modules/expo-audio/android`, см. выше про `buildFromSource`), поэтому типы `expo.modules.audio.AudioPlayer` и нижележащий ExoPlayer берутся из той же сборки, что и у приложения; maven-координата, динамическое чтение версии (`JsonSlurper`) и репозиторий `local-maven-repo` удалены как ненужные. При апгрейде expo-audio версия подхватывается автоматически; следить нужно только за совместимостью патча — `yarn check:patches`. **Caveat (stale-копия в `node_modules`):** yarn 1 копирует `file:`-зависимость в `node_modules/audio-effects`, и обычный `yarn install` не обновляет её, пока запись в `yarn.lock` без integrity-хеша — после правок модуля освежать копию (`rm -rf node_modules/audio-effects && yarn install --check-files`; для Android-сборки безвредно, autolinking резолвит gradle-проект на `modules/audio-effects/android`). Подводные камни сборки модуля (stale runtime-jar, не попадающий в APK при свежем kotlinc-выводе) — [`features/player.md`](./features/player.md) → «Сборка модуля: подводные камни». Архитектура и возможности/ограничения — [`features/player.md`](./features/player.md) → «Настройки звука».

> **Reanimated / Worklets static feature flags (Android fast path, 2026-09):** в `package.json` добавлены верхнеуровневые блоки `reanimated.staticFeatureFlags.ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS = true` и `worklets.staticFeatureFlags.ENABLE_CROSS_RUNTIME_STACK_TRACES = false`. **Первый** — официальный статический флаг Reanimated (доступен с 4.0.0, по умолчанию `false`): на Android/Fabric Reanimated применяет пофреймовые обновления `transform` через полный `ShadowTree::commit` + mounting-пайплайн (~0.75 мс на вью), тогда как встроенный native-driver `Animated` использует быстрый путь `synchronouslyUpdateViewOnUIThread` — именно поэтому удалённый `react-native-text-ticker` скроллился плавно, а Reanimated-марквиз микро-дёргался. Флаг заворачивает не-layout стили (`opacity`/`transform`) на этот fast path — по официальным бенчмаркам до 4× FPS. **Второй** — рекомендация официальной документации Worklets: выключает dev-only cross-runtime stack-trace capture, который «can significantly hurt performance» для пофреймового планирования (влияет только на dev-режим). Источники: [Reanimated feature flags](https://docs.swmansion.com/react-native-reanimated/docs/guides/feature-flags/), PR [software-mansion/react-native-reanimated#7823](https://github.com/software-mansion/react-native-reanimated/pull/7823), issue [#10121](https://github.com/software-mansion/react-native-reanimated/issues/10121). **Caveat (#10121):** на Fabric тач-система может не учитывать анимированные transform'ы на fast path — в этом проекте прессаблы внутри анимированных вью идут через RNGH (`GestureDetector` / `AnimatedPressable`), это документированная митигация; если тап промахнётся во время анимации разворота мини-плеера — вернуться сюда. ⚠️ Флаг Reanimated применяется на этапе нативной сборки: нужен **нативный rebuild** (`expo run:android` / EAS dev client), одного JS-reload недостаточно.

## Other fixed decisions

- **Архитектура:** Feature-Sliced Design (слои app → pages → widgets → features → entities → shared) — см. [`architecture.md`](./architecture.md).
- **Стиль:** отсутствие точек с запятой; одинарные кавычки; до 130 строк на файл; стрелочные функции.
- **Экспорты:** именованные экспорты в `src/`, `export default` только в `app/` (expo-router).
- **Импорты:** абсолютные по слоям FSD (`entities/player`, `shared/ui/theme`); относительные между слоями запрещены.
- **Barrel:** один barrel `index.ts` на слайс; сегментные barrel-файлы запрещены; именованные реэкспорты вместо `export *`; экспортируется только то, что используется внешними потребителями.
- **@x cross-import:** кросс-слойные связи между слаями одного уровня (например, `entities/player` ↔ `entities/listening-history`) реализуются через папку `@x/` в корне слайса-поставщика. Файл `@x/<consumer>.ts` реэкспортирует узкий API для конкретного потребителя. Разрешено **только между `entities`**; мосты feature ↔ feature запрещены (dependency inversion на уровне страниц). Подробнее — [`architecture.md`](./architecture.md) → «@x cross-import».
- **Состояние:** Reatom; `ctx` из `src/shared/lib/reatom-ctx/ctx.ts`.
- **Платформы:** iOS, Android, Web; платформенные реализации через `.native.ts`/`.web.ts`.
- **Web-сборка:** Metro, `web.output` не задан (SPA-режим `single`: один `index.html` + клиентский роутинг). PWA-оболочка — `public/index.html` + `public/sw.js` (hand-rolled Service Worker: офлайн-оболочка + офлайн-аудио через Cache Storage). Dev-web запускается через `yarn web` (`EXPO_NO_METRO_LAZY=1` — обход бага ленивого бандлинга Metro на `import('expo-notifications')`). Деплой-хост обязан отдавать `index.html` на неизвестные пути — закрыто `nginx.conf` (`try_files`) в собственном Docker-образе (`Dockerfile`). Подробнее — [`features/web.md`](./features/web.md).
- **Web-деплой:** отдельное Docker-приложение `slovo-web` на общем VPS, по паттерну `slovo-frontend`/`slovo-docs` из `slovo-propovedi-playbook` (инфра — Traefik/Docker/buildx — от плейбука; сам деплой — Forgejo Actions по тегу `v*`, `scripts/vps-deploy-web.sh`, без registry). `release.yml`: job `web` (экспорт + деплой) и job `android` (APK) оба зависят только от `create-release`, друг от друга — нет.
- **Язык UI:** русский; технические термины — английским.
- **API:** контракт через OpenAPI + Orval; ручные типы под API не пишем.
- **Нотация ссылок на Писание: запятая = раздельные стихи, дефис = диапазон.** В нотации ссылки (`formatSermonReference` / `formatScripture`) запятая означает отдельные стихи (`9, 20` — два стиха), дефис — диапазон (`9-20`); перепутать их — значит изменить смысл ссылки. На проводе массив из двух целых чисел всегда читается как диапазон, поэтому одиночный стих оборачивается в `[n, n]` — в отображении невидимо. Список разрозненных отрезков — `[[9, 18], 20]` (отрезок 9-18 и стих 20). Бэкенд отклоняет комбинацию «диапазон глав + одиночный стих», поэтому отображение **честно деградирует** (показывает только диапазон глав), а не выдумывает несуществующую ссылку. Формы union-типов описаны в [`contracts/rest-api.md`](./contracts/rest-api.md) → «Главы и стихи».
- **Android debug keystore:** канонический `debug.keystore` лежит в корне репозитория (вне `android/`, поэтому переживает `prebuild --clean`), а `plugins/withDebugKeystore.ts` восстанавливает его в `android/app/debug.keystore` при каждом prebuild — `--clean` больше не вращает отладочную подпись (иначе Expo CLI удалял бы установленные dev/prod debug-сборки с `INSTALL_FAILED_UPDATE_INCOMPATIBLE`). Публичный debug-ключ, коммит допустим; осознанная ротация = принудительный uninstall обоих флейворов.
- **Android release signing:** release-сборки подписываются настраиваемым release-ключом. `plugins/withReleaseSigning.ts` при каждом prebuild добавляет в сгенерированный `android/app/build.gradle` release-`signingConfig`, читающий env `RELEASE_STORE_FILE`/`RELEASE_STORE_PASSWORD`/`RELEASE_KEY_ALIAS`/`RELEASE_KEY_PASSWORD` на этапе конфигурации Gradle; `buildTypes.release` берёт release-ключ только при заданном `RELEASE_STORE_FILE`, иначе подписывается debug-ключом (dev-only). CI (`release.yml`) декодирует keystore из секрета `ANDROID_KEYSTORE_BASE64` в `android/app/release.keystore` после `prebuild --clean` и экспортит `RELEASE_*` в `$GITHUB_ENV` — без секрета сборка остаётся зелёной на debug-подписи. **Причина:** debug-ключ публичен, поэтому debug-подписанный публичный релиз подделывается кем угодно и не принимается магазинами. **Цена:** переключение подписи у уже установленного приложения даёт `INSTALL_FAILED_UPDATE_INCOMPATIBLE` — нужна одноразовая переустановка. См. [`BUILD-LOCAL.md`](./BUILD-LOCAL.md) → «Signing for Production».
- **Android build flavors:** Gradle `productFlavors` `dev`/`prod` (dimension `env`). Dev: `applicationIdSuffix ".dev"`, имя «Dev Слово.Проповеди». Prod: базовый `ru.slovopropovedi`. `debuggableVariants = ["devDebug", "prodDebug"]`. Цель — dev-сборка не перезаписывает prod на одном устройстве. Кастомная схема тоже per-flavor — prod `slovo-propovedi`, dev `slovo-propovedi-dev` через source-set `AndroidManifest.xml`, генерируемые `plugins/withAndroidFlavors.ts`. Отдельно dev-схема `slovo-propovedi-dev` объявлена и в **главном** манифесте через `plugins/withDevClientScheme.ts`: Expo CLI читает схему dev-client (`scheme://expo-development-client/?url=...`) только из main-манифеста, и когда схемы вынесли оттуда во флейворные манифесты (77e7184), `yarn run:android` стал запускать prod-пакет — после регресса запуска схему вернули в main. Prod-флейворный манифест вычищает её фильтром-близнецом main-фильтра с `tools:node="remove"` на `<data>`: merger схлопывает фильтры с одинаковой сигнатурой action/category/data (tools-атрибуты на идентичность не влияют), remove срабатывает внутри слитого фильтра и убирает `<data>`, оставляя инертный VIEW-фильтр без data (VIEW без data не матчит ни одного URI). VIEW-фильтр prod'а с `slovo-propovedi` не задет. См. [`BUILD-LOCAL.md`](./BUILD-LOCAL.md).
- **CI: ограничение памяти Jest.** В `jest.config.ts` добавлен `workerIdleMemoryLimit: '1GB'` (перезапуск воркера при росте RSS), а в `.forgejo/workflows/ci.yml` шаг тестов запускается как `yarn testFinal --maxWorkers=2`. Причина: тяжёлые `jest-expo`/RN UI-сьюты вызывали OOM (SIGKILL от ОС) при параллельном запуске множества воркеров.
- **Тесты: `testTimeout: 15000` в `jest.config.ts`.** Дефолтные 5 с на тест оказались на грани для тяжёлых jest-expo-сьютов на медленном CI-раннере (`yarn testFinal --maxWorkers=2`): набор `AdminSermonsScreen` трижды падал по таймауту на разных тестах (2026-10-22 локально под 6 воркерами — два навигационных; 2026-10-24 в CI — рендер-тест), в изоляции набор проходит ~5 с. Глобальное поднятие таймаута вместо per-test правок убирает весь класс флейков; реально зависший тест по-прежнему падает за 15 с.
- **CI: OOM релизной сборки (exit 137) на 4 ГБ раннере.** На хосте раннера ≤4 ГБ RAM и два слота, поэтому тяжёлые задачи не должны пересекаться. Принятые меры: `kotlin.compiler.execution.strategy=in-process` в `android/gradle.properties` (прописывается после prebuild в release.yml) — дефолтная стратегия порождала отдельный Kotlin-daemon, который жил во время JS-бандла и съедал память; `org.gradle.jvmargs=-Xmx1536m -XX:MaxMetaspaceSize=512m (в раунде 2 повышено до 768m — см. ниже)`; `NODE_OPTIONS=--max-old-space-size=1536` для node/Metro; `metro.config.js` читает `CI_METRO_MAX_WORKERS` и ограничивает transform-воркеры Metro двумя только в CI (локально поведение не меняется); concurrency-группа `memory-heavy-jobs` в ci.yml (`checks`) и release.yml (`release`) — тяжёлые задачи выстраиваются в очередь вместо параллельного запуска. Страховкой для пиков служит swap на хосте (добавлен вручную, вне репозитория). **Раунд 2 (нативная фаза):** после того как JS-бандл прошёл, daemon умирал без исключения в логе (kernel/cgroup OOM-kill) во время clang/CMake-фазы для двух ABI, несмотря на 14 ГБ swap на хосте — подозрение на лимит памяти контейнера. Дополнительные меры: `-XX:MaxMetaspaceSize=768m` (in-process Kotlin поднимает использование metaspace; 768m — запас, metaspace коммитит только реально используемое); `org.gradle.workers.max=2` (ограничение параллельных compile-задач, чтобы сгладить пики памяти); сборка только под `arm64-v8a` (отказ от 32-битного `armeabi-v7a` — почти все устройства с ~2018 arm64; вдвое снижает пик памяти/времени нативной компиляции). **Раунд 3 (диагноз окончательный):** прогон с правками раунда-2 упал через 29 мин в `:app:buildCMakeRelWithDebInfo[arm64-v8a]` — `Gradle build daemon disappeared unexpectedly` без исключения в логе демона. dmesg хоста показал оба kill'а как `constraint=CONSTRAINT_MEMCG` (лимит job-контейнера 6 GiB, а не хоста); убит java-демон с anon-rss всего ~1.7–2.0 GiB — как крупнейший процесс в cgroup, пока 6 GiB забивали некапнутые clang-процессы (ninja -j выводится из числа ядер CPU). По исходникам react-native-gradle-plugin подтверждено: `org.gradle.workers.max` НЕ ограничивает ninja -j внутри одного CMake-таска — только параллельные Gradle-таски; комментарии в release.yml об этом исправлены. Хостовой swap (10 GiB свободно) не спасает: у job-контейнера swap-квота не позволяет выходить за memory.max. **Решение:** поднять лимит job-контейнера в конфиге act-runner (`--memory=12g --memory-swap=16g`); значения в workflow (Xmx1536, metaspace 768m, NODE_OPTIONS 1536, workers.max 2, arm64-v8a) оставлены как консервативный пол. **План Б** (если OOM повторится на 12g): инжект `CMAKE_JOB_POOLS` (`compile=N; link=1`) постпребилд-патчем `app/build.gradle`.
- **CI: job summaries в Forgejo Actions.** Все джобы трёх воркфлоу (`.forgejo/workflows/{ci,release,renovate}.yml`) пишут Markdown-фрагменты в `$GITHUB_STEP_SUMMARY` — Forgejo (server ≥ 17.0, runner ≥ 13.2) рендерит их над логами джобы, по блоку на шаг в порядке выполнения, с live-обновлением. Запись идёт только через `scripts/ci/step-summary.sh` (executable): он сводит guard «переменная не задана → no-op» в одно место и использует переносимое имя `$GITHUB_STEP_SUMMARY` (старые act-раннеры молча отбрасывают контент, GitHub Actions понимает то же имя). Два паттерна: (1) инлайн-фрагменты — шаги дописывают свои строки по ходу джобы (release.yml, dco); (2) консолидированная таблица в финальном шаге с `if: always()` из `steps.<id>.outcome` + длительности через `$EPOCHSECONDS` (ci checks, renovate) — переживает ранние падения и skipped-шаги. Лимит Forgejo — 1 MiB на шаг с тихой обрезкой; каждый шаг рендерится отдельным markdown-документом, поэтому сломанный фрагмент не ломает соседние.
